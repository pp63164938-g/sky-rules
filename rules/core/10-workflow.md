# 开发工作流

渐进式开发：通过多轮对话迭代，明确并实现需求。在着手任何设计或编码工作前，必须完成前期调研并厘清所有疑点。
结构化流程：严格遵循"构思方案 → 提请审核 → 分解为具体任务"的作业顺序。

## 需求文档读取规范

**核心原则**：当用户提供、指定或当前项目中存在与本次任务相关的需求文档时，开发前必须先读取需求文档，禁止跳过需求文档直接根据截图、文件名、路径、历史对话或个人推断开始开发。

**适用场景**：

- 用户明确提供 `/api`、`api.md`、`api-docs.md`、`api-word.md` 等本地文档路径
- 用户提供钉钉文档、在线文档、需求链接、工单链接
- 用户当前打开的文件是需求文档，或上下文明确提示“接口文档 / 需求文档在某路径”
- 项目根目录或约定目录下已有与当前任务相关的需求文档

**执行要求**：

1. 开发前必须先读取需求文档内容。
2. 读取后必须以需求文档为主要依据，再结合截图、原型、现有代码和接口文档开发。
3. 如果需求文档无法访问、内容为空、只包含目录或与当前任务无关，必须明确说明读取结果，不能假装已经掌握需求。
4. 禁止在未读取需求文档的情况下，直接进入编码、mock、字段占位或路由/API 生成。
5. 如果需求文档与用户口头描述冲突，必须先指出冲突并让用户确认，以用户最新确认结果为准。

## 需求文档与接口文档优先级

**核心原则**：联调时必须先区分“产品表现”和“数据契约”；页面表现以需求文档 / 原型 / 用户最新说明为准，接口字段链路以接口文档 / 抓包 / 后端确认为准。

**执行要求**：

1. **页面表现按需求文档**：页面展示、字段标题、按钮文案、交互流程、模块名称、字段是否展示、展示顺序，优先以需求文档 / 原型 / 用户最新说明为准。
2. **数据契约按接口文档**：接口路径、请求参数名、响应字段名、字段类型、枚举真实值、分页结构、提交结构，必须以接口文档 / 抓包 / 后端确认为准。
3. **接口说明不覆盖页面文案**：接口字段说明只能帮助理解字段含义，不能直接覆盖需求文档中的页面文案。例如接口字段名或说明是“备注”，但需求图写“等级说明”，页面标题应使用需求文档文案，代码绑定字段仍使用接口字段名。
4. **需求字段缺接口时显性处理**：需求要求展示但接口未提供字段时，不能用相似接口或其他字段硬凑；应保留需求位置，标记 `TODO无此联调字段_用途描述`，并反馈后端补字段或确认数据来源。
5. **动态文案缺字段禁止改语义**：需求文案、确认弹窗、提示语或按钮说明中包含动态占位（如数量、名称、金额、状态等）时，如果接口文档、抓包或后端未确认对应字段，禁止为了实现方便改成静态泛化文案、删除占位、替换成相近含义文案或用其他字段硬凑。必须先查询目标接口字段；查不到时保留原需求文案结构和占位位置，使用 `TODO无此联调字段_用途描述` 显性标记，或阻断操作并反馈缺少字段，等待后端补字段或用户确认降级方案。

```ts
// ❌ 禁止 - 因为拿不到数量字段，就把需求文案改成泛化文案
confirm('确认要处理本次全部记录吗？')

// ✅ 正确 - 已确认接口返回 count 字段时，保留需求中的数量语义
confirm(`确认要处理本次${count}条记录吗？`)

// ✅ 正确 - 查不到数量字段时，显性暴露缺口，不能静默改文案
const TODO无此联调字段_本次数量 = response.TODO无此联调字段_本次数量
```

6. **冲突必须拆开说明**：需求文档和接口文档冲突时，必须明确指出冲突点。展示文案、交互和展示顺序冲突按需求优先；字段名、类型和提交结构冲突按接口 / 抓包优先；无法分层处理时先问用户确认。

## 智能工作流调用机制

为了提升开发效率并防止因用户遗忘而导致的代码不规范，AI 助手需根据上下文**主动调用**相关工作流：

- **Figma 还原场景**：当用户的请求中包含 Figma 设计稿截图，或提及 Figma 的样式属性面板参数（如 `background: #xxx`, `font-style: 65 Medium`、各种绝对坐标间距等）时，无论用户是否显式输入了工作流指令，AI 都**必须自行调用 `@[/base.figma-to-code]` 工作流**，并以此作为后续 CSS 样式还原与属性智能映射的绝对准则。

## Git 操作规范

**核心原则**：**绝对禁止在未受明确指令要求的情况下，直接帮用户进行代码的缓存/暂存（add）、提交（commit）或推送（push）操作。**

- `git status`、`git diff`、`git log` 等**纯只读操作**：允许自行执行来分析上下文。
- `git add`：**绝对禁止**在修改完代码后擅自执行任何缓存/暂存操作，必须由用户主动提出（如"帮忙暂存"）才可执行。
- `git restore --staged` / `git reset HEAD` / 取消暂存：**绝对禁止擅自执行**。暂存区可能是用户用于对比、分批提交或保存工作边界的状态，AI 不得为了"整理状态""避免 staged 变更"或"方便查看 diff"主动取消缓存。只有用户明确提出"取消暂存 / 撤出缓存 / unstage"时才允许执行。
- 遇到已有暂存内容时，必须保持暂存区原状。需要分析变更时，只允许使用 `git status`、`git diff`、`git diff --cached` 等只读命令分别查看工作区和暂存区差异，并在回复中说明哪些是已暂存、哪些是未暂存。
- `git commit`：**绝对禁止擅自执行**，必须等用户确认变更内容并下达明确指令后才可执行。
- `git push`：**必须由用户明确提出后**才可执行。
- 服务器部署相关（Docker 构建、PM2 重启等）：仅允许在代码已经获得批准推送后才能自动执行相应构建。
