# 全局规则维护索引

`rules/` 用于维护跨项目、跨 AI 工具通用的规则正文。默认源文件是 `rules/global-rules.md`，同步脚本会把它转换为各 AI 工具实际读取的全局规则文件。

## 文件职责

| 文件 | 职责 |
| --- | --- |
| `global-rules.md` | 全局规则正文，承载跨项目通用的红线、开发规范、联调规范、样式规范等 |

## 规则归属

新增规则前先判断归属，避免所有内容都堆进全局规则。

| 规则类型 | 推荐位置 | 判断标准 |
| --- | --- | --- |
| P0 红线、事实依据、Git 禁止项 | `global-rules.md` 对应红线或通用章节 | 跨所有项目和任务都必须遵守 |
| 接口文档、字段、联调、Mock | `global-rules.md` 的需求 / 接口 / 联调相关章节 | 影响数据契约、接口字段、接口来源 |
| Vue / TypeScript / 组件 / Hook | `global-rules.md` 的组件、类型、Hook 相关章节 | 影响日常编码方式 |
| CSS / SCSS / UI 还原 | `global-rules.md` 的样式或 UI 相关章节 | 影响视觉还原、样式组织、组件默认样式 |
| i18n / Icon / 注释 / 文件头 | `global-rules.md` 对应专题章节 | 跨项目可复用的格式和维护约定 |
| 终端、同步、构建验证 | `global-rules.md` 的终端命令或同步验证章节 | 影响工具执行和验证方式 |
| 具体工作步骤 | `workflows/base.*.md` 或 `workflows/kl.*.md` | 更像流程，不是单条规则 |
| 单项目特例 | 对应项目规则文件 | 只服务某个项目，不应污染全局 |

## 新增规则流程

1. **查重**：先在 `rules/global-rules.md` 和 `workflows/` 中搜索关键词，确认是否已有相似规则。
2. **判定归属**：能补充现有章节就补充现有章节；只有新主题足够稳定时才新增章节。
3. **定位插入点**：按主题插入，不追加到文件末尾；检查目标位置前后上下文。
4. **预览确认**：写入前先给用户展示规则内容和插入位置。
5. **同步索引**：新增大章节或改变维护流程时，更新本文件或仓库根目录 `AGENTS.md`。
6. **同步验证**：写入后执行 `python3 sync-workflows.py --no-git`。

## 规则写法模板

```md
## 规则名称

**核心原则**：一句话说清楚这条规则解决什么问题。

**适用场景**：说明什么时候必须遵守。

**硬性红线**：

- 禁止 xxx。
- 禁止 xxx。

**正确做法**：

- 应该 xxx。
- 应该 xxx。

**代码示例**：

\```ts
// ❌ 禁止 - 抽象反例
const value = xxx

// ✅ 正确 - 抽象正例
const result = getXxxValue(xxx)
\```

**判断标准**：

- 是否满足 xxx。
- 是否避免 xxx。
```

## 示例要求

- 示例必须抽象化，不使用真实业务接口、真实权限标识、真实客户 / 供应商 / 金额等生产信息。
- 示例只保留能说明规则的最小结构，避免贴完整组件、完整接口或完整弹窗。
- 固定项目约定可以保留真实名称，但必须说明这是项目约定。

## 维护自检

- 新规则是否已经搜索查重。
- 新规则是否放在对应主题章节。
- 新规则是否比已有规则更清晰，而不是重复表达。
- 新规则是否包含明确的禁止项和判断标准。
- 新增大章节后是否更新了本索引。
- 修改后是否同步并验证目标工具可见性。
