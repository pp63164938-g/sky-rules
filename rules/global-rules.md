# 核心理念与原则

简洁至上：恪守 KISS（Keep It Simple, Stupid）原则，崇尚简洁与可维护性，避免过度工程化与不必要的防御性设计。
深度分析：立足于第一性原理（First Principles Thinking）剖析问题，并善用工具以提升效率。
事实为本：以事实为最高准则。若有任何谬误，恳请坦率斧正，助我精进。

# 开发工作流

渐进式开发：通过多轮对话迭代，明确并实现需求。在着手任何设计或编码工作前，必须完成前期调研并厘清所有疑点。
结构化流程：严格遵循"构思方案 → 提请审核 → 分解为具体任务"的作业顺序。

## 智能工作流调用机制

为了提升开发效率并防止因用户遗忘而导致的代码不规范，AI 助手需根据上下文**主动调用**相关工作流：

- **Figma 还原场景**：当用户的请求中包含 Figma 设计稿截图，或提及 Figma 的样式属性面板参数（如 `background: #xxx`, `font-style: 65 Medium`、各种绝对坐标间距等）时，无论用户是否显式输入了工作流指令，AI 都**必须自行调用 `@[/base.figma-to-code]` 工作流**，并以此作为后续 CSS 样式还原与属性智能映射的绝对准则。

## Git 操作规范

**核心原则**：**绝对禁止在未受明确指令要求的情况下，直接帮用户进行代码的缓存/暂存（add）、提交（commit）或推送（push）操作。**

- `git status`、`git diff`、`git log` 等**纯只读操作**：允许自行执行来分析上下文。
- `git add`：**绝对禁止**在修改完代码后擅自执行任何缓存/暂存操作，必须由用户主动提出（如"帮忙暂存"）才可执行。
- `git commit`：**绝对禁止擅自执行**，必须等用户确认变更内容并下达明确指令后才可执行。
- `git push`：**必须由用户明确提出后**才可执行。
- 服务器部署相关（Docker 构建、PM2 重启等）：仅允许在代码已经获得批准推送后才能自动执行相应构建。

# 禁止自行发散

**核心原则**：**严禁自行发散新增任何代码结构**。用户未明确指定的内容，一律不得自行生成。

**禁止范围**：

- **表单字段**：禁止自行新增 `searchForm` / `form` 中的字段
- **搜索项**：禁止自行新增搜索栏的筛选项
- **表格列**：禁止自行新增列配置、合并列插槽
- **接口参数**：禁止自行新增接口请求参数
- **接口 URL / Query 参数**：禁止自行编造 API 的 URL 路径或 Query 参数名。必须基于用户提供的浏览器抓包、接口文档或项目已有代码中的真实请求，严禁凭合理猜测拼出不存在的参数（如将 `sortType=0` 猜成 `listType=new`）
- **下拉数据源**：禁止自行新增下拉选项的数据源定义
- **模块导入路径**：禁止主观猜测无把握的模块导入路径（如 `import request from '@/utils/request'`）。对于基建工具类引入，必须参考同项目中现有代码的引用方式。

**正确做法**：

- 用户说"用 X 接口"→ 只替换数据源，不新增字段
- 用户说"加一列 X"→ 只加这一列，不自行扩展其他列
- 用户说"改成 X"→ 只做替换，不新增额外内容
- **不确定时先问**：如果用户的描述有歧义（如没说加在哪里、对应哪个字段），必须先询问确认，禁止自行猜测并生成代码

**反面案例**：

```
用户：客户状态，使用这个接口 customerSelectCustomerCategory
正确：替换客户状态下拉的数据源为该接口
错误：自行新增一个"客户类别"搜索项 + 表单字段 + 数据源（用户从未说要加新字段）
```

```
用户：帮我写一个拉取帖子列表的功能
正确：先让用户提供浏览器抓包或接口文档，按真实参数编写
错误：自行编造 listType=new 等不存在的 Query 参数（实际应为 sortType=0）
```

# 禁止擅自优化老代码

**核心原则**：拓展功能时，**严禁顺手优化或重写已有代码**。只做用户要求的变更，不改动老代码的写法。

**禁止行为**：

- 修改老代码的语法风格（如 `any` → `Omix`、`{ return {} }` → `=> ({})`）
- 重构老代码的逻辑结构（如拆函数、合并变量、调整顺序）
- 替换老代码的实现方式（如换 API、换组件、换工具函数）
- 删除已注释的老代码块（注释代码属于保留参考，禁止擅自清理）
- 改变老代码的格式排版（如单行写法改多行、多行改单行，保持原格式不动）
- 在替换代码时误删周围不相关的老代码（替换范围必须精确，只动目标代码，不波及上下文的已有逻辑）

**替换功能的正确做法**：

- **新增功能**：在老代码旁边新增，不动老代码
- **替换功能**：注释原来的代码，在旁边写新代码，而不是直接覆盖
- **必要注释格式**：`<!-- 原逻辑：描述 ... 原代码 ... -->` 或 `// 原逻辑：...`

**代码示例**：

```vue
<!-- ❌ 禁止 - 直接覆盖替换老代码 -->
<new-component v-model="form.field" />

<!-- ✅ 正确 - 注释原代码，新代码写在旁边 -->
<!-- 原逻辑：使用 com-form-select 下拉
<com-form-select v-model="form.field" :options="options" /> -->
<new-component v-model="form.field" />
```

**判断标准**：

- 如果改动不是用户明确要求的 → 不改
- 如果老代码能正常工作但风格不同 → 不改
- 不确定是否该改 → 先问用户

# AI 代码修改与替换规范

**核心原则**：在执行代码修改（特别是区块替换）时，必须做到“精准打击”，严禁由于粗心漏写而误删上下文中不相关的注释。

**行为准则**：

1. **精准定位目标区块**：选中待修改代码块时，只圈定真正需要修改的代码部分，不要贪图省事把周围的注释标签一并囊括。
2. **严格保持代码与注释完整性**：如果在替换过程中无可避免地包含了原有的注释（如 `<!-- 表单模块 -->`），在生成新代码时，必须**原封不动地将这些注释保留写回**，绝对禁止静默删减。

# Codex 代码格式化规范

**核心原则**：Codex 修改代码后，必须按当前项目已有的格式化 / lint 工具处理本次修改文件，禁止依赖编辑器保存时格式化。

**背景说明**：不同开发者不一定使用 VS Code，即使项目存在 `.vscode/settings.json`，其中的 `editor.formatOnSave` 也只会在 VS Code 保存文件时生效。Codex 直接修改文件，不会触发编辑器保存动作；其他编辑器也不一定读取 `.vscode` 配置。若只依赖编辑器自动格式化，页面代码最终可能不会被格式化。

**执行规则**：

1. **优先使用项目已有命令**：先查看 `package.json` 中是否存在 `lint:fix`、`format`、`prettier`、`eslint`、`biome`、`stylelint` 等脚本或配置。
2. **只处理本次修改文件**：除非用户明确要求，禁止全项目无差别格式化，避免产生大量无关 diff。
3. **禁止自行引入工具**：项目没有明确使用 ESLint / Prettier / Biome / Stylelint 时，禁止为了格式化自行新增依赖或配置，必须先询问用户。
4. **禁止依赖 `.vscode` 自动格式化**：`.vscode/settings.json` 只能作为编辑器配置参考，不能作为 Codex 已完成格式化的依据；不能因为项目配置了 `editor.formatOnSave` 就跳过格式化命令。
5. **只有编辑器配置时必须说明**：如果项目只有 `.vscode` 自动格式化配置，但没有项目级格式化命令，必须说明当前无法由 Codex 稳定触发格式化，并建议补充项目级 `format` / `lint:fix` 脚本。
6. **无法执行时必须说明**：如果项目缺少格式化命令、依赖未安装、命令执行失败，必须在回复中明确说明原因和未格式化的范围。
7. **Vite 项目不默认 build**：格式化验证优先使用轻量命令，不得把 `npm run build`、`pnpm build`、`vite build` 当作默认格式化或验证步骤。

**判断标准**：

- 修改代码后，必须主动检查项目已有格式化方式。
- 有明确格式化工具时，必须对本次修改文件执行对应格式化。
- 只有 `.vscode` 自动格式化配置时，不能视为已格式化完成。
- 没有明确工具时，必须暂停确认，不能按个人习惯生成新格式化配置。
- 最终回复必须说明是否已执行格式化，以及使用了哪个命令。
# 业务组件与二次封装组件使用规范

**核心原则**：严禁将项目内的二次封装组件（如 `com-*` / `sky-*` / `business-*` 等）完全等同于原生底层基础组件（如 Element/AntD）靠自行猜测去编写配置。

**行为准则**：

1. **使用前强制看源码/文档**：在首次调用不熟悉的业务封装组件，或准备传入复杂的、未曾见过的 `Props` 参数之前，**必须先使用工具去读取该组件的源码文件（或相关文档）**，明确其接口定义（`Props`、`Emits`）及内置默认特性。
2. **利用最佳实践糖**：很多二次封装组件自身已经对常见场景做了高度定制（如原生传递 `multiple` 便自动帮你配置折叠 tags）。严防因为不看源码而写出覆盖或破坏其自身特性的冗余代码。

# CSS/SCSS 样式规范

**核心原则**：

1. 禁止使用 `&__` 嵌套简写，必须书写完整的选择器路径
2. 禁止使用 `&--` 嵌套简写，必须书写完整的选择器路径（即便在嵌套结构中）
3. **结构嵌套反映 HTML 层级**：子元素样式必须嵌套到父元素内部。所谓“完整选择器路径”是指禁止使用 `&__xxx` / `&--xxx` 简写，而不是要求所有 BEM 类平铺到同一层；只要 HTML 存在父子结构，SCSS 中就必须按父子层级嵌套，并在嵌套内继续书写完整类名。
4. **同级修饰符必须物理嵌套**：修饰符样式（如 `.block--active`）必须物理嵌套在基础类内部，并使用 `&` 连接，但必须写全路径。
5. **样式注释必须具备业务语义且全覆盖（防漏机制）**：
   - **语义化要求**：严禁在样式中留下推导过程或废话参数（如 `/* 匹配 Figma 18px */`、`/* 还原倾斜感 */`）。注释必须清晰说明“这是什么业务模块”（如 `/* 进度条金额大号字体 */`、`/* 强调引流链接 */`）。
   - **强制全覆盖要求**：绝不允许为了偷懒只给最外层顶层容器写注释！在拆解组件或还原 Figma 样式时，**必须为每一个独立定义的子元素样式块（例如所有 BEM 的 `__header`、`__label`、`__val`、`__num`、`__unit` 等）全部加上对应业务说明的注释**。严禁在没有任何注释的情况下连续堆砌子元素样式类。
6. **状态枚举与变体类注释必须写全**：对于涉及多状态、多类型枚举的样式类（如多个相似的 BEM 修饰符变体 `.card--success`, `.card--fail`，或是同一容器内针对不同业务类型的样式分支），必须**逐个详细写明其代表的具体业务含义**（如 `/* 季军赛（青色） */`、`/* 淘汰赛（橙红色） */`），严禁为了省事只堆砌代码，以保证后续接手人员的高效维护。
7. **公共样式必须显式引入（拒绝幽灵样式）**：当抽离公共样式（如统一的弹窗按钮 `.wc-btn` 等）供多个独立子组件复用时，**必须在每个使用到该样式的子组件 `<style>` 中显式地 `@import` 对应的公共样式文件**。绝不允许为了省事，仅在页面最顶层入口隐式引入，导致单看子组件时出现“有类名却无处追溯”的幽灵样式现象，严重破坏代码可读性。

**目的**：保证代码可读性和层级清晰，便于全局搜索和快速定位样式。

**嵌套规则**：

| 场景                     | 是否嵌套    | 说明                                                                  |
| ------------------------ | ----------- | --------------------------------------------------------------------- |
| 父子元素关系             | ✅ 嵌套     | 子元素样式写在父元素样式块内                                          |
| BEM 修饰符（同元素状态） | ✅ 嵌套     | `.block--modifier` 物理嵌套在基础类内部，需写全名 `&.block--modifier` |
| 伪类/伪元素              | ✅ 允许 `&` | `&:hover`、`&::before`、`&:disabled`                                  |
| 元素选择器               | ✅ 允许嵌套 | 可直接嵌套 `img`、`span`、`i` 等                                      |

**代码示例**：

```scss
// ❌ 禁止 - 使用 &__ 简写
.card {
  &__title {
    font-size: 16px;
  }
}

// ❌ 不推荐 - 有父子关系却平铺
.card__header {
  margin-bottom: 20px;
}
.card__title {
  font-size: 16px;
} // title 是 header 的子元素，应嵌套

// ✅ 推荐 - 结构嵌套反映 HTML 层级
.card {
  // 父子关系嵌套
  .card__header {
    margin-bottom: 20px;

    .card__title {
      font-size: 16px;
    }
  }

  // BEM 修饰符必须物理嵌套在基础类内部
  // 且必须书写全路径选择器，方便全局搜索
  &.card--disabled {
    opacity: 0.5;
  }
}
```

**父子结构示例**：

```scss
// ❌ 错误 - 有父子关系却为了“全路径”平铺
.wc-ticker__live {
  display: flex;
}

.wc-ticker__live-dot {
  width: 8px;
}

.wc-ticker__live-title {
  font-size: 14px;
}

// ✅ 正确 - 按 HTML 父子关系嵌套，同时保留完整类名
.wc-ticker__live {
  display: flex;

  .wc-ticker__live-dot {
    width: 8px;
  }

  .wc-ticker__live-title {
    font-size: 14px;
  }
}
```

**判断标准**：

- 若 A 是 B 的 HTML 子元素 → B 的样式嵌套在 A 内部
- 若 A--modifier 是 A 的状态变体 → A--modifier 物理嵌套在 A 内部，且使用全名 `&.A--modifier`

# UI 与设计图还原规范

**核心原则**：在还原 Figma 等高质量 UI 设计稿时，严禁因为“图省事”而直接拼凑使用底层 UI 框架自带的通用图标（如 Element UI 的 `el-icon-circle-check`）去敷衍设计稿中的专属业务图形。必须使用原生 SVG 绘制或者专门的 UI 切图，确保视觉和质感的百分百精确还原。

# Vue 路由跳转规范

**核心原则**：路由跳转优先使用 `name` 方式，避免使用硬编码路径。

**目的**：路径变更时只需修改路由配置，无需全局搜索替换。

**代码示例**：

```javascript
// ❌ 不推荐 - 硬编码路径
this.$router.push("/agent/contractSign");

// ✅ 推荐 - 使用路由 name
this.$router.push({ name: "contractSign" });

// ✅ 带参数的跳转
this.$router.push({ name: "userDetail", params: { id: 123 } });
this.$router.push({ name: "search", query: { keyword: "test" } });
```

# 枚举映射规范

**核心原则**：只要涉及枚举值映射（无论数量多少），**禁止使用三元运算符**，必须使用映射对象。即便当前只有 1-2 个值，考虑到未来扩展性，也应强制使用 Map。

**代码示例**：

```javascript
// ❌ 禁止 - 三元嵌套超过2个
const statusText =
  status === 1
    ? "待审核"
    : status === 2
      ? "已通过"
      : status === 3
        ? "已拒绝"
        : "未知";

// ❌ 禁止 - 即使只有2个值也不允许三元（新增类型时需全局搜索替换）
const productLabel = productType === 1 ? "短信/语音" : "PWA";

// ✅ 推荐 - 使用映射对象
const STATUS_MAP = {
  1: "待审核",
  2: "已通过",
  3: "已拒绝",
};
const statusText = STATUS_MAP[status] || "未知";

// ✅ 推荐 - 类型→标签映射
const PRODUCT_LABEL_MAP = {
  1: "短信/语音",
  2: "PWA",
  3: "短信",
  4: "语音",
};
const productLabel = PRODUCT_LABEL_MAP[productType] || "未知";
```

**多类型条件判断**：当多个类型共享相同逻辑时，使用常量集合 + `includes` 判断：

```javascript
// ❌ 禁止 - 硬编码单值判断，新增类型时容易遗漏
v-if="rule.productType === 1"

// ✅ 推荐 - 提取常量集合，新增类型只需修改一处
const SMS_VOICE_PRODUCT_TYPES = [1, 3, 4]
v-if="SMS_VOICE_PRODUCT_TYPES.includes(rule.productType)"
```

**判断标准**：

- **枚举映射/多状态判断**：禁止使用三元运算符，必须使用映射对象（Map/Object）
- **多类型共享逻辑**：禁止硬编码单值判断，必须提取常量集合 + `includes`
- **真假二元判断 (Boolean)**：仅简单的 Yes/No 场景允许使用三元运算符

# 条件分支编写规范

**核心原则**：优先使用扁平的 `if → return` 提前退出风格，避免 `if-else` / `if-elseif-else` 链式嵌套。

**目的**：减少嵌套层级，提高可读性，新增分支时只需在末尾 `return` 前插入新的 `if` 块。

**代码示例**：

```javascript
// ❌ 不推荐 - if-else 链式嵌套
function getFilteredItems(type, items) {
  if (type === "a") {
    return items.filter((item) => item.parentId === 1);
  } else if (type === "b") {
    return items.filter((item) => item.value === 2);
  } else {
    return items;
  }
}

// ✅ 推荐 - 扁平 if + 最后 return
function getFilteredItems(type, items) {
  if (type === "a") {
    return items.filter((item) => item.parentId === 1);
  }
  if (type === "b") {
    return items.filter((item) => item.value === 2);
  }
  // 其他场景：返回全部
  return items;
}
```

**判断标准**：

- 每个分支独立判断，用 `if` + 提前 `return` 处理
- 默认行为放在函数/回调末尾作为最终 `return`
- 新增场景时只需在末尾 `return` 前插入新的 `if` 块，无需修改已有分支

# 变量命名规范

**核心原则**：在循环迭代（如 `map`、`forEach`、`find`）或复杂的业务逻辑方法中，**禁止使用含义不明的单字符变量名**（如 `s`、`t`、`i`、`item` 等）。必须使用完整、具有语义化的单词进行命名。

**目的**：解决复杂业务场景下变量指代不明、容易混淆的问题，同时便于后期全局搜索和维护。

**代码示例**：

```javascript
// ❌ 禁止 - 含义不明的单字符变量名
allSettlements.map((s, index) => {
  const tiers = parseAmountRange(s.amountRange || '')
  return tiers.map(t => ({ ... }))
})

// ✅ 推荐 - 语义明确的完整单词
allSettlements.map((settlementItem, index) => {
  const monthlyTiers = parseAmountRange(settlementItem.amountRange || '')
  return monthlyTiers.map(tierItem => ({ ... }))
})
```

**判断标准**：

- **禁止简写**：禁止使用 `s`、`t`、`v` 等缩写代替业务对象名
- **语义化**：变量名应准确描述其代表的数据内容（如 `settlementItem` 而非 `item`）
- **例外情况**：仅在极简的二行以内、逻辑单一的箭头函数中，且不涉及复杂对象属性访问时，才可视情况允许使用 `item` 或 `val`，但仍优先推荐完整命名。

# 静态接口开发规范

适用场景：后端未提供接口文档时，前端需进行静态开发。

开发原则：

- **组件代码**：正常调用接口，写法与正式接口一致，无需任何改动
- **API 文件**：在 API 定义中返回模拟数据，联调时仅需修改此处
- **禁止在组件中内联 mock 数据**：所有 mock 数据必须放在 API 函数中，保持组件代码干净

API 文件规范：

- 响应结构：{ code: 0, msg: "模拟数据", data: 业务逻辑数据, success: true }
- **mock 只关注响应数据**：不包含业务逻辑判断（如输入长度限制），业务逻辑由调用方控制
- 使用 `// @mock-start 联调时删除` 和 `// @mock-end` 标记包裹模拟数据代码块
- 在 `// @mock-end` 后保留被注释的正式请求代码
- 联调时删除 `@mock-start` 到 `@mock-end` 之间的代码（包括标记），取消注释正式请求

## TODO 字段标记规范

**核心原则**：待确认字段的后缀必须使用**中文用途描述**，让人一看就知道**这里需要什么数据**。

**两种前缀**：

| 前缀                | 适用阶段 | 含义                                   |
| ------------------- | -------- | -------------------------------------- |
| `TODO待联调_`       | 静态开发 | 字段名待后端确认，联调时替换为真实字段 |
| `TODO无此联调字段_` | 联调阶段 | 接口文档中不存在此字段，需与后端确认   |

**命名规则**：前缀 + **中文用途描述**，描述应说明该字段的业务含义。

**代码示例**：

```javascript
// ❌ 不推荐 - 后缀用英文字段名，看不出需要什么数据
TODO无此联调字段_rate;
TODO待联调_exchangeRate;

// ✅ 推荐 - 后缀用中文用途描述，一看就知道需要什么
TODO待联调_汇率;
TODO待联调_汇率日期;
TODO无此联调字段_客户状态;
TODO无此联调字段_客户创建时间;
```

**适用场景**：

| 场景                      | 示例                                            | 说明                       |
| ------------------------- | ----------------------------------------------- | -------------------------- |
| 静态开发-字段名未定       | `TODO待联调_用户名: res.data.TODO待联调_用户名` | 字段名待后端确认           |
| 静态开发-下拉选项未定     | `const TODO待联调_星级Options = ref([])`        | 下拉数据源待确认           |
| 联调-接口文档缺少字段     | `:value="row.TODO无此联调字段_客户状态"`        | 接口无此字段，需与后端确认 |
| 联调-不确定用哪个接口字段 | `:rate="summaryData.TODO无此联调字段_汇率"`     | 不确定该用哪个字段         |

**使用规则**：

1. 全局搜索 `TODO待联调_` 或 `TODO无此联调字段_` 即可找到所有待处理项
2. **禁止自行发散字段**：接口文档没有的字段，禁止自己编造字段名
3. `TODO待联调_` 适用于所有无接口文档依据的变更（新增字段、单选改多选、数据源变更等），已有页面中已确定的字段禁止改为 TODO
4. 表单字段名（`searchForm`/`formData` 的属性名）与提交接口时的参数字段名应保持一致，不要定义两个不同的名字来表示同一个字段
5. 联调/上线前，全局搜索确保已全部处理

# 联调开发规范

适用场景：与后端进行接口联调时。

接口文档查阅：

- 联调前，优先查看项目根路径下的接口文档文件
- 文档文件名：[api.md]、`api-docs.md`、`api-word.md`
- 根据文档中的字段定义进行精确映射

核心原则：

- **严格按接口文档映射**：字段名必须与文档完全一致
- **禁止自行发散字段**：遇到接口文档没有的字段，**禁止**自己发散直接生成字段名
- **待确认字段用 TODO无此联调字段\_ 标记**：使用 `TODO无此联调字段_用途描述` 格式占位，便于全局搜索和理解
- **前后端字段名一致**：表单字段名（`formData` 的属性名）必须与接口请求参数的字段名完全一致，禁止前端自定义一套字段名再在提交时映射为另一套。即使后端字段名有拼写错误（如 `amout` 而非 `amount`），前端也必须跟随后端字段名，保持一致。

```javascript
// ❌ 禁止 - 前端用 amount/reason，提交时映射为 amout/reson，两套名字
const formData = { amount: "", reason: "" };
const params = { amout: Number(formData.amount), reson: formData.reason };

// ✅ 正确 - 直接用后端字段名，提交时无需映射
const formData = { amout: "", reson: "" };
const params = { amout: Number(formData.amout), reson: formData.reson };
```

# 临时代码标记规范

用于标记需要在特定阶段移除的临时代码，便于全局搜索和批量清理。

标记格式：

- **Mock 数据**：`// @mock-start 联调时删除` ... `// @mock-end`
- **TODO 待办**：`// @todo-start 描述` ... `// @todo-end`
- **待确认字段**：`TODO待联调_用途描述`（静态开发）/ `TODO无此联调字段_用途描述`（联调阶段）

使用规则：

1. 开始标记后可添加简短描述，如 `// @mock-start 联调时删除`
2. 结束标记保持简洁，如 `// @mock-end`
3. 标记成对使用，包裹需要移除的完整代码块
4. 联调/上线前，全局搜索对应标记进行清理

# i18n 翻译规范

**核心原则**：**禁止自动生成翻译**，所有未由用户提供的翻译必须使用 `TODO翻译_` 前缀标记。

## 禁止自动生成翻译

- 当用户未提供某语言的翻译时，**绝对禁止自行发散生成翻译**
- 应使用 `TODO翻译_` 前缀 + 已提供的原文作为占位符
- 示例：`"TODO翻译_綁定推薦人"` 而非自行翻译为 `"Bind Referrer"`
- 便于后续全局搜索 `TODO翻译_` 进行翻译补充

## 扩展 i18n key 时的规则

当需要添加新的翻译 key 时（如替换硬编码中文为 i18n）：

1. **中文文件**：正常添加中文内容
2. **英文文件**：**必须使用 `TODO翻译_中文原文` 作为占位符**
3. **完成后**：主动告知用户新增了哪些待翻译的 key

```javascript
// ❌ 禁止 - 自行生成英文翻译
codeSent: "Verification code sent";

// ✅ 正确 - 使用 TODO翻译_ 标记
codeSent: "TODO翻译_验证码已发送";
```

## 使用规则

1. **已有翻译**：项目中已存在的完全匹配的翻译可直接使用
2. **新增翻译**：仅有中文时，英文**必须**使用 `TODO翻译_中文原文` 占位
3. **用户提供**：用户明确提供的翻译内容可直接使用
4. **发现问题**：如用户提供的翻译有错误（如翻译错位），应先询问用户确认再修正

## 注释规范

- **各语言文件注释保持一致**：所有 i18n 文件（cn.js、en.js 等）的注释内容必须与中文文件保持一致
- **使用简体中文注释**：便于阅读和定位对应模块
- **示例**：`// 合同签署页面` 而非 `// Contract Sign Page`

# i18n 文件扩展规范（通用）

**核心原则**：扩展 i18n 翻译时，**必须先查看项目的 i18n 入口文件**（通常是 `src/i18n/langs/index.js` 或 `src/i18n/index.js`），确定当前实际使用的语言文件，只扩展被引用的文件。

**操作步骤**：

1. **先查看 i18n 入口**：确认哪些语言文件被实际引用
2. **只扩展被引用的文件**：避免修改未使用的语言文件
3. **记录发现**：如果发现有文件未被使用，应在对话中说明

**目的**：避免扩展未被使用的语言文件，减少无效工作和潜在错误。

## 禁止在 i18n 中编写 HTML 结构与样式

**核心原则**：禁止在 i18n 语言文件中混入复杂的 HTML 结构（如 `<div>`、`<p>`）或任何 CSS 样式（如 `style="..."`、`class="..."`）。

**目的**：保持 i18n 文件的纯粹性，确保结构与内容分离，降低后续翻译和维护的难度。

**操作要求**：

- **纯文本为主**：i18n 文件中尽量只保留纯文本，长文本与特殊结构建议通过数组或多个独立属性进行拆分。
- **允许的轻量标签**：仅在特殊需要时，允许在 i18n 中使用极少量的行内基础占位标签（如 `<strong>`、`<br/>`）。
- **样式分离**：需要特殊样式（如特定颜色高亮）的文本，必须将其拆分为独立的 i18n 变量，并交由 Vue 模板（如 `<span class="xxx">{{ $t('...') }}</span>`）来负责渲染样式。**绝对禁止**在 i18n 文件中硬编码 `style="..."` 或长篇大论的 DOM 结构。

**反面案例**：

```javascript
// ❌ 禁止 - 在 i18n 中硬编码样式和复杂 HTML 结构
contentHtml: '<div class="wc-rule"><span style="color: #E57200">$100,000</span></div>';
```

**正确做法**：

```javascript
// ✅ 正确 - i18n 仅保留纯文本
prefix: '瓜分',
amount: '$100,000',
suffix: '现金'
```

```vue
<!-- ✅ Vue 模板中处理结构与样式 -->
<div class="wc-rule">
    {{ $t('prefix') }}<span class="highlight-amount">{{ $t('amount') }}</span>{{ $t('suffix') }}
</div>
```

2. **删除/修改组件引用时**：检查被引用的资源（翻译、图标、样式）是否还有其他地方使用，没有则删除
3. **修改完成后**：使用搜索工具确认旧代码/翻译确实无引用

# 注释规范

**Vue 组件/弹窗必须包含业务说明注释**：

- **格式**：在组件最外层节点内部（如 `<template>` 开头处）或 `export default` 上方，必须添加明确的中文业务名称或功能说明注释。
- **目的**：保持极高的可读性，让接手人员无需阅读内部实现细节，也能快速明确该组件的业务用途。
- **代码示例**：
  ```vue
  <template>
    <!-- 预约活动报名提醒弹窗 -->
    <WcDialog :visible="visible"></WcDialog>
  </template>
  ```
  或
  ```javascript
  /**
   * 预约报名弹窗
   * 业务场景：点击 Hero 横幅区的“立即预约”时弹出
   */
  export default { ... }
  ```

**变量名、函数名使用 JSDoc 注释**：

- **格式**：使用 `/** xxx */` 的方式添加注释
- **适用场景**：变量声明、函数定义、类型定义、接口属性（包括函数内部的变量定义）
- **目的**：鼠标移入时可以看到描述，提升代码可读性和开发体验

**代码行内注释**：

- **格式**：使用 `// xxx` 的方式添加注释
- **适用场景**：函数内部的逻辑说明、步骤解释、条件分支说明
- **目的**：解释代码执行逻辑，便于阅读理解

示例：

```javascript
/** 绑定赠送金额 */
giftAmount: ''

/** 获取绑定赠送金额 */
async fetchGiftAmount() {
    // 先校验参数
    if (!this.userId) return

    /** 接口响应数据 */
    const res = await api.getGiftAmount()
    this.giftAmount = res.data
}
```

**注释位置与内容分层规范**：

**核心原则**：注释应贴近它解释的代码。顶部/块级注释只说明“这是什么”，具体分支、状态判断、兜底逻辑的业务原因，应写在对应判断过程里，避免把细节规则堆在远离代码的顶部注释中。

**分层要求**：

- **顶部注释 / JSDoc**：说明变量、函数、组件、模块的业务身份，即“这是什么”。
- **过程注释 / 行内注释**：说明关键判断、特殊分支、兜底逻辑的业务原因，即“为什么这样做”。
- **禁止规则漂移**：不要在函数顶部写一大段具体业务规则，而实际判断只留一行代码；规则变化时这类注释最容易过期。
- **注释紧贴代码**：如果注释解释的是某个 `if`、`return`、`v-if`、兜底值或特殊状态，注释必须放在该代码附近。

**代码示例**：

```javascript
// ❌ 不推荐 - 具体规则堆在顶部，和实际判断分离
/**
 * 底部实时竞猜动态挂载标识
 * 业务规则：活动未结束时挂载并常驻底部；活动结束后隐藏，避免与最终排行榜重复展示
 */
isTickerFooterVisible() {
    return this.campaignState !== 'ended'
}

// ✅ 推荐 - 顶部说明“是什么”，过程里说明“为什么”
/** 底部实时竞猜动态挂载标识 */
isTickerFooterVisible() {
    if (this.campaignState === 'ended') {
        // 活动结束页已展示最终排行榜，底部实时动态不再挂载，也不保留底部占位
        return false
    }
    // 活动未结束时挂载底部实时动态，组件内部负责无消息时常驻底栏
    return true
}
```

**判断标准**：

- 注释读起来像“字段/函数名称补充” → 放顶部或 JSDoc。
- 注释读起来像“这个分支为什么要这样处理” → 放到对应分支内部。
- 注释如果离开对应代码仍无法判断是否过期 → 应移动到具体代码附近。

**HTML/Vue 模板注释规范**：

**核心原则**：对于复杂的组件结构（如卡片、列表项、左右布局容器等），**必须为关键的 HTML 节点添加包裹式或起手式注释**，以清晰标明业务含义，与 CSS 样式全覆盖注释相呼应。

**强制要求**：

- 严禁在没有任何注释的情况下连续堆砌大量的 `<div>` 等无语义标签。
- 注释必须说明“这是什么业务模块”（例如：`<!-- 战绩详情数据列 -->`、`<!-- 头部左侧：汇总场次与日期 -->`）。
- 尤其是使用了 Flex/Grid 布局的大型结构骨架，其主要父容器必须拥有明确的业务说明注释。

**目的**：提高模板的结构可读性，防漏、防错，方便接手人员能够做到“仅看模板注释就能秒懂业务布局结构”。

**代码示例**：

```vue
<!-- ❌ 禁止 - 无任何结构说明，纯标签堆砌 -->
<div class="wc-history-card__inner">
    <div class="wc-history-card__teams">
        <img src="xxx" />
        <span>巴西</span>
    </div>
</div>

<!-- ✅ 推荐 - 具备结构化的业务说明注释 -->
<div class="wc-history-card__inner">
    <!-- 球队对阵信息：左右国家队国旗及名称 -->
    <div class="wc-history-card__teams">
        <img src="xxx" />
        <span>巴西</span>
    </div>
</div>
```

# 文件头部注释规范

**核心原则**：所有代码文件顶部需添加功能描述注释，说明该文件是哪个页面或功能。

**格式要求**：

| 文件类型   | 注释格式            | 示例                         |
| ---------- | ------------------- | ---------------------------- |
| .vue       | `<!-- 功能描述 -->` | `<!-- 提现/充值抽屉组件 -->` |
| .js/.ts    | `/** 功能描述 */`   | `/** 公共接口定义 */`        |
| .jsx/.tsx  | `/** 功能描述 */`   | `/** 用户列表页面 */`        |
| .scss/.css | `/* 功能描述 */`    | `/* 全局公共样式 */`         |

**注意事项**：

- 注释放在文件最顶部（第一行）
- 描述应简洁明了，说明文件的用途或所属功能模块
- 不要放文件路径，而是描述功能

# 终端文件操作编码规范

**核心原则**：在终端（PowerShell/CMD）中操作文件时，**必须保证 UTF-8 编码不被破坏**。

**背景**：PowerShell 的 `Get-Content`、`Set-Content`、`-replace` 等命令默认使用系统编码（GBK/CP936），会导致 UTF-8 文件中的中文字符变成乱码。

**规则**：

| 操作     | ❌ 禁止                                         | ✅ 正确                                                                                                          |
| -------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 复制文件 | `Copy-Item` + `Set-Content`                     | `[System.IO.File]::ReadAllBytes/WriteAllBytes`（二进制复制）                                                     |
| 文本替换 | `Get-Content -Raw` + `-replace` + `Set-Content` | 优先使用代码编辑工具（`replace_file_content`），或用 `[System.IO.File]::ReadAllText/WriteAllText` 显式指定 UTF-8 |
| 读取文件 | `Get-Content`                                   | `[System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8)`                                             |

**优先级**：修改文件内容时，**优先使用代码编辑工具**（`replace_file_content` / `multi_replace_file_content`），避免经过终端处理文本。仅在批量操作或搜索替换等场景才使用终端命令，且必须显式指定 UTF-8。

# 终端命令执行规范

**终端环境设定**：

- 如果命令代码块标记为 `bash`，或上下文要求在 Git Bash / MINGW64 中执行：
  - ❌ 禁止输出 Windows 反斜杠路径：`D:\self\Ai\sky-rules\sync-workflows.py`

- 如果命令代码块标记为 `powershell`，才允许使用 Windows 反斜杠路径：`D:\self\Ai\sky-rules\sync-workflows.py`

**判断标准**：给用户的命令必须能在其当前终端中直接复制执行；不要把 PowerShell 路径格式放进 Bash 命令块。

**核心原则**：禁止命令在编辑器中"假死"（显示 Running 但实际已完成或无响应）。

当当前项目可识别为 Vite 前端项目（如存在 `vite.config.*`，或 `package.json` scripts 中使用 `vite build`）时，日常页面开发、接口联调、Mock 替换、样式调整、规则同步等任务默认不执行 full build。

| 命令类型                                   | WaitMsBeforeAsync | 说明                                            |
| ------------------------------------------ | ----------------- | ----------------------------------------------- |

# 错误处理与用户感知规范

**核心原则**：严禁在核心业务、交互动作或外部系统对接环节“静默吞噬”错误。发生异常（如 Token 失效、HTTP 报错、构建提取失败等）时，必须通过合理的方式建立**明确的用户感知触点**。

**目的**：绝对禁止“出了错但系统没有任何反应/仅仅打印一行日志”的“黑盒现象”。确保发生问题时，不论是前台点击还是后台默默轮询，最终都能通过 UI 交互或推送通道把问题暴露给用户或运维，引导其人为干预。

**具体要求与做法**：

1. **前台交互场景**：用户发生点击操作（Click）后，所有的失败分支（`catch` 异常、非 200/成功返回），必须通过 `Toast`/`Notice`/`Message` 框显式提示用户出错原因及解决建议，而不能吞没在控制台内。
2. **后台异步/轮询场景**：当自动化任务遇到无法自行突破的“死结”（如通过 `catch` 捕获到网络异常、或者自动挽回失败的 Token 401 过期），不要只写 `console.error` 了事。应该将该错误**具象化为一个特定的终态/异常态**（例如将状态扭转为 `TOKEN_EXPIRED` 或 `FETCH_FAILED`），并由系统主动利用钉钉、邮件等通知通道推送给干预人。
3. **关于 `try-catch` 的吞噬**：仅有绝对不影响主流程分支且已经具备正确兜底数据的边缘场景，才允许使用空 `catch (e) {}` 块，并强制在内加上明确注释（如 `// ignore: 可降级，使用默认配置`）。

**代码示例**：

```typescript
// ❌ 禁止 - 静默吞噬错误，既不反馈推屏也不推送告警，系统成黑盒
try {
  await triggerPipeline();
} catch (error) {
  console.error("执行崩溃", error); // 用户点击后页面没反应，也收不到任何失败通知
}

// ✅ 推荐 [后台调度] - 自动化长驻任务遇到不可恢复异常时，将其推送触达用户
if (response.status === 401) {
  const newToken = await autoLoginRefresh();
  if (!newToken) {
    // 不仅打印日志，还通过通知链路主动告诉用户“Token已彻底过期，需要人为登录”
    await notificationManager.notify({
      status: "TOKEN_EXPIRED",
      pipelineName: sub.pipelineName,
    });
    return;
  }
}

// ✅ 推荐 [前台交互] - 用户在页面上触发的点击请求，必须给予明确失败 UI 反馈
try {
  await api.updateConfig();
  this.$message.success("更新成功");
} catch (err) {
  this.$message.error(err.message || "网络或凭证已失效，更新失败");
}
```
