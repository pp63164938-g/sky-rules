# CSS/SCSS 样式规范

**核心原则**：

**适用场景**：业务样式、BEM 结构、UnoCSS 与 SCSS 取舍、组件默认样式覆盖、设计稿还原、状态变体、公共样式复用。

**硬性红线**：禁止 `&__` / `&--` 简写；禁止无业务注释堆样式；禁止无明确设计依据覆盖基础组件默认样式；禁止把有业务语义的复杂结构强行堆成大量 UnoCSS 原子类。

1. 禁止使用 `&__` 嵌套简写，必须书写完整的选择器路径
2. 禁止使用 `&--` 嵌套简写，必须书写完整的选择器路径（即便在嵌套结构中）
3. **结构嵌套反映 HTML 层级**：子元素样式必须嵌套到父元素内部。所谓“完整选择器路径”是指禁止使用 `&__xxx` / `&--xxx` 简写，而不是要求所有 BEM 类平铺到同一层；只要 HTML 存在父子结构，SCSS 中就必须按父子层级嵌套，并在嵌套内继续书写完整类名。
4. **同级修饰符必须物理嵌套**：修饰符样式（如 `.block--active`）必须物理嵌套在基础类内部，并使用 `&` 连接，但必须写全路径。
5. **同元素修饰符禁止并列书写**：只要类名表达的是同一个元素的状态 / 变体，例如 `.xxx__item` 与 `.xxx__item--active`、`.xxx-button` 与 `.xxx-button--disabled`，修饰符必须写在基础类内部，使用 `&.完整修饰符类名`。禁止把基础类和修饰符类作为同级选择器并列书写，即使它们已经嵌套在同一个业务根类下也不允许。只有修饰符类本身对应独立 DOM 根节点、不是同元素状态时，才允许独立书写；此时应优先改名避免 `--` 伪装成 BEM 修饰符。
6. **`:deep()` 层级必须反映子组件 DOM 结构**：当使用 `:deep()` 覆盖子组件内部结构时，也必须遵循 HTML 层级嵌套。先用 `:deep(.业务根类)` 命中子组件根节点，再在内部嵌套其后代节点、伪元素和状态类；禁止把同一组件内部的多个后代选择器全部平铺成同级 `:deep(.root .child)`。
7. **样式注释必须具备业务语义且全覆盖（防漏机制）**：
   - **语义化要求**：严禁在样式中留下推导过程或废话参数（如 `/* 匹配 Figma 18px */`、`/* 还原倾斜感 */`）。注释必须清晰说明“这是什么业务模块”（如 `/* 进度条金额大号字体 */`、`/* 强调引流链接 */`）。
   - **强制全覆盖要求**：绝不允许为了偷懒只给最外层顶层容器写注释！在拆解组件或还原 Figma 样式时，**必须为每一个独立定义的子元素样式块（例如所有 BEM 的 `__header`、`__label`、`__val`、`__num`、`__unit` 等）全部加上对应业务说明的注释**。严禁在没有任何注释的情况下连续堆砌子元素样式类。
   - **注释放置位置要求**：说明“这个选择器 / 样式块是什么业务模块”的注释，必须放在选择器外部并紧贴选择器上一行；如果选择器在父级内嵌套，则注释放在父级内部、子选择器外部。只有解释某一条具体 CSS 声明为什么这样写时，才放在样式块内部并紧贴对应声明。
   - **禁止把块级业务注释放进样式声明内部**：例如 `/* 业务模块标题 */` 这类说明整个 `.xxx__title` 样式块含义的注释，禁止写在 `{}` 内部第一行，应写在 `.xxx__title` 上方，避免注释和具体声明层级混淆。

```scss
/* 业务模块标题 */
.business-section__title {
    font-size: 14px;
    line-height: 22px;
    color: #222;
}

.business-section {
    /* 业务提示图标 */
    .business-section__notice-icon {
        flex-shrink: 0;
        font-size: 14px;
    }

    .business-section__header {
        display: flex;
        align-items: center;
        /* 右侧操作按钮固定贴边，避免标题过长时挤压 */
        justify-content: space-between;
    }
}
```
8. **状态枚举与变体类注释必须写全**：对于涉及多状态、多类型枚举的样式类（如多个相似的 BEM 修饰符变体 `.card--success`, `.card--fail`，或是同一容器内针对不同业务类型的样式分支），必须**逐个详细写明其代表的具体业务含义**（如 `/* 季军赛（青色） */`、`/* 淘汰赛（橙红色） */`），严禁为了省事只堆砌代码，以保证后续接手人员的高效维护。
9. **公共样式必须显式引入（拒绝幽灵样式）**：当抽离公共样式（如统一的弹窗按钮 `.wc-btn` 等）供多个独立子组件复用时，**必须在每个使用到该样式的子组件 `<style>` 中显式地 `@import` 对应的公共样式文件**。绝不允许为了省事，仅在页面最顶层入口隐式引入，导致单看子组件时出现“有类名却无处追溯”的幽灵样式现象，严重破坏代码可读性。

**目的**：保证代码可读性和层级清晰，便于全局搜索和快速定位样式。

## 样式结构交付前自检门禁

**核心原则**：凡是新增、重构或大幅调整 `<style scoped lang="scss">` / `<style lang="scss" scoped">`，交付前必须回读最终样式块，检查 selector 结构是否符合 HTML 层级，禁止只凭生成时的记忆认为已经符合规范。

**执行要求**：

1. 如果存在页面 / 组件业务根类，例如 `.xxx-page`、`.xxx-card`、`.xxx-dialog`，同一业务块下的子元素样式必须嵌套在业务根类内部；除非该选择器本身就是独立根节点，禁止把 `.xxx__header`、`.xxx__body`、`.xxx__item` 等平铺成顶层选择器。
2. 子元素样式必须按模板中的真实父子关系嵌套到最近的父级选择器下；“完整选择器路径”只表示禁止 `&__xxx` / `&--xxx` 简写，不表示 BEM 类可以全部顶层平铺。
3. 同元素状态修饰符必须嵌套在基础类内部，例如 `.xxx__item` 内写 `&.xxx__item--active`；禁止把 `.xxx__item--active` 单独平铺成顶层选择器。
4. `:deep()` 覆盖必须放在对应业务父级下，并优先先命中子组件根节点，再嵌套其内部节点；禁止在文件顶层散落多个无归属的 `:deep(.xxx .yyy)`。
5. 交付前必须至少做一次结构自检：回读最终 `<style>` 或查看本次 diff，若同一业务前缀的根类和子元素类同时出现在顶层，必须先修正再交付。
6. **同前缀选择器必须归属到同一业务根**：如果模板存在业务根类 `.xxx-panel`，则同一业务前缀下的 `.xxx-panel__header`、`.xxx-panel__body`、`.xxx-panel-item` 等选择器默认都必须嵌套在 `.xxx-panel` 内部，并继续按真实 HTML 父子关系分层；禁止因为写了完整类名，就把同前缀选择器拆成多个顶层块。只有该选择器本身对应独立根节点、全局覆盖入口或跨组件公共根时，才允许顶层平铺，并必须在注释中说明独立原因。
7. **先按模板结构搭样式骨架，再填 CSS 属性**：新增或大幅调整 SCSS 时，必须先根据模板父子关系建立选择器骨架，再补充定位、尺寸、颜色等属性；禁止按视觉区域或 Figma 图层顺序随手追加一批顶层选择器，导致样式看似分块、实际没有层级归属。
8. **交付前必须做同前缀顶层扫描**：回读最终样式时，如果发现同一业务前缀的根类和多个子元素类同时位于文件顶层，例如 `.xxx-panel`、`.xxx-panel__header`、`.xxx-panel__body` 并列，必须先判断是否真实独立根；不是独立根就必须收回到对应父级下再交付。
9. **交付前必须做同元素修饰符并列扫描**：回读最终样式时，如果发现 `.xxx__item` 与 `.xxx__item--状态`、`.xxx-block` 与 `.xxx-block--状态` 处在同一缩进层级或同一父级下并列，必须先改为基础类内部的 `&.xxx__item--状态` / `&.xxx-block--状态` 再交付。禁止只因为选择器写在同一个业务根类里，就认为修饰符层级合格。

**错误示例**：

```scss
/* ❌ 禁止：根块和子元素平铺 */
.xxx-page {
    min-height: 100%;
}

.xxx-page__header {
    display: flex;
}

.xxx-page__item--active {
    color: #1677ff;
}
```

**正确示例**：

```scss
/* ✅ 正确：根块下按 HTML 层级嵌套，BEM 完整类名保留 */
.xxx-page {
    min-height: 100%;

    /* 页面头部 */
    .xxx-page__header {
        display: flex;
    }

    /* 页面条目 */
    .xxx-page__item {
        color: #333;

        &.xxx-page__item--active {
            color: #1677ff;
        }
    }
}
```

**`:deep()` 示例**：

```scss
/* ✅ 正确：覆盖归属于当前业务区域 */
.xxx-page {
    /* 业务筛选区域 */
    .xxx-page__filter {
        :deep(.xxx-select) {
            .xxx-select__inner {
                min-width: 0;
            }
        }
    }
}
```

**同前缀归属示例**：

```scss
/* ❌ 禁止：同一业务块的子元素按视觉区域平铺在顶层 */
.xxx-panel {
    position: relative;
}

.xxx-panel__header {
    display: flex;
}

.xxx-panel__body {
    padding: 16px;
}

.xxx-panel-item {
    display: flex;
}

/* ✅ 正确：同一业务块归属到业务根，并按真实父子结构嵌套 */
.xxx-panel {
    position: relative;

    /* 面板头部 */
    .xxx-panel__header {
        display: flex;
    }

    /* 面板内容区 */
    .xxx-panel__body {
        padding: 16px;

        /* 面板内容条目 */
        .xxx-panel-item {
            display: flex;
        }
    }
}
```

**同元素修饰符示例**：

```scss
/* ❌ 禁止：同元素状态修饰符和基础类并列 */
.xxx-panel {
    .xxx-panel__value {
        color: var(--xxx-text-color);
    }

    .xxx-panel__value--success {
        color: var(--xxx-success-color);
    }
}

/* ✅ 正确：修饰符物理嵌套在基础类内部 */
.xxx-panel {
    .xxx-panel__value {
        color: var(--xxx-text-color);

        &.xxx-panel__value--success {
            color: var(--xxx-success-color);
        }
    }
}
```

## 样式公共变量优先规范

**核心原则**：编写颜色、边框、背景、阴影、文字色、布局间距、圆角等样式前，必须先查项目已有公共变量；能使用变量时优先使用变量，禁止上来直接写硬编码，导致后续系统风格调整困难。

**执行要求**：

1. 写样式前必须先查当前项目公共样式入口、主题变量和组件库变量，例如 `src/styles/index.scss`、主题覆盖文件、组件库变量或项目约定变量；禁止不查变量直接写颜色、边框、背景、阴影、常用间距。
2. 如果硬编码值与公共变量值和语义完全一致，必须使用 `var(--xxx)`；例如主要文字、次要文字、线条色、页面背景、成功/失败/告警色、系统主色、页面通用间距等。
3. 禁止“先硬编码写出来，后面再统一替换”的做法；新增样式时就必须完成变量查证和变量复用。
4. 同一组件或页面内重复出现 2 次及以上的设计专属值，如果没有全局公共变量承载，应优先在当前业务根类下定义局部 CSS 变量，再在子样式中复用，避免散落多处硬编码；仅使用 1 次的值不抽局部变量，应直接写在使用位置，禁止为了“看起来统一”把单次值声明成 `--xxx-*` 后只使用一次。
5. 如果设计稿颜色与公共变量只是“接近”但不等价，禁止为了变量化强行替换成相近变量；应保留设计值，并用业务注释说明这是当前设计专属色或当前组件专属视觉。
6. 禁止跨模块借用专属变量；某业务模块私有的 `--xxx-*` 变量不能被其他模块直接拿来当全局变量使用，除非已经被项目明确定位为跨模块公共变量。
7. 禁止为了单个页面随手新增全局变量；只有跨页面复用、语义稳定且用户确认需要沉淀时，才允许补充公共变量。
8. 交付前必须回看本次新增 / 修改样式中的硬编码颜色和常用尺寸，确认没有遗漏可直接复用的公共变量；如果存在保留的硬编码，应能说明是单次设计专属值或局部变量不适用。
9. 使用 CSS 变量前必须同时确认“存在性、语义、作用对象”三件事：变量在当前项目或组件上下文中真实存在；变量命名语义与使用场景一致；变量适用于当前 CSS 属性。禁止只因为变量值接近或名字里包含颜色含义，就直接用于不匹配的属性。
10. 背景 / 填充类变量不能随意拿来当文字色、边框色或图标色；文字色、背景色、边框色、状态色必须优先选择语义匹配的变量。例如填充背景变量只适合 `background` / `background-color`，不应作为按钮文字色使用。
11. 覆盖 Element Plus、`sky-*`、`com-*` 等组件样式时，必须先按“组件 props / 默认样式 → 已确认组件变量 → 精准局部样式”的顺序判断。只有组件源码、文档或 DevTools 已确认存在对应 CSS 变量，且变量语义正好承载当前状态（默认、hover、active、disabled、focus 等）时，才优先覆盖组件变量。
12. 禁止为了“看起来变量化”而滥用组件变量：如果只是当前页面单次视觉微调、结构布局调整、局部边距 / 宽高 / 圆角 / 背景覆盖，或使用变量反而隐藏了真实修改点，应直接在对应业务选择器 / `:deep()` 结构中写具体样式，不要绕到 Element Plus 变量上。
13. 禁止使用未确认存在的 CSS 变量。IDE、浏览器 DevTools 或构建结果提示变量未定义时，必须立刻回查来源；查不到真实定义时应改用已确认存在且语义匹配的变量，或直接写当前局部样式。禁止保留不存在变量、猜变量名、或用 fallback 掩盖未查证问题。
14. 局部 CSS 变量只在“同一值复用 2 次及以上”“表达稳定业务 / 设计语义”“确实需要统一驱动多个子状态”时使用；仅使用 1 次、或只是为了少写一个颜色 / 尺寸的值，不抽局部变量。
15. 删除或替换 CSS 变量时，必须用搜索确认该变量没有剩余引用；禁止只删定义不删使用，导致页面回退到无效变量或浏览器默认值。
16. CSS 变量查证不能只看“库里好像有”或“别的项目这样写过”。必须以当前项目、当前页面运行上下文可解析为准：源码定义、当前项目已有确定用法、组件文档、DevTools computed 结果至少满足其一。DevTools 提示变量未定义时，视为当前交付阻断项，必须当场改掉，禁止继续说“理论上应该存在”。
17. 禁止凭 UI 库默认变量名猜项目变量名。项目存在封装前缀、主题改名或二次构建时，例如 `--xxx-*` / `--xxx-sky-*` 这类变量，必须先查当前项目实际变量前缀和已生效变量；禁止把原库变量名直接套进业务样式。
18. 对白色、黑色、透明、固定设计色这类单次局部视觉值，如果没有已确认存在且语义匹配的项目变量，应直接写设计值，例如 `#ffffff`，不要为了“变量化”猜一个不存在的 `var(--xxx-white)`。

**错误示例**：

```scss
/* ❌ 禁止：项目已有主要文字和线条变量时继续硬编码 */
.xxx-card {
    color: #222222;
    border: 1px solid #e7e7e7;
}
```

**正确示例**：

```scss
/* ✅ 正确：命中项目公共变量时使用变量 */
.xxx-card {
    color: var(--primary-text-color);
    border: 1px solid var(--line-color);
}
```

**变量语义示例**：

```scss
/* ❌ 禁止：填充背景变量语义不等于按钮文字白色 */
.xxx-button {
    --xxx-button-text-color: var(--xxx-fill-blank);
}

/* ✅ 正确：使用已确认的文字白色变量 */
.xxx-button {
    --xxx-button-text-color: var(--xxx-color-white);
}
```

**变量存在性示例**：

```scss
/* ❌ 禁止：凭经验猜 UI 库变量，当前项目未确认存在 */
.xxx-button {
    color: var(--xxx-color-white);
}

/* ✅ 正确：当前局部固定白色，变量未确认时直接写设计值 */
.xxx-button {
    color: #ffffff;
}
```

**组件变量示例**：

```scss
/* ❌ 禁止：组件内部走变量控制时，只写普通 color */
.xxx-button {
    color: var(--xxx-color-white);
}

/* ✅ 正确：按组件变量同时覆盖对应状态 */
.xxx-button {
    --xxx-button-text-color: var(--xxx-color-white);
    --xxx-button-hover-text-color: var(--xxx-color-white);
    --xxx-button-active-text-color: var(--xxx-color-white);
}
```

**设计专属色示例**：

```scss
.xxx-card {
    /* 当前卡片图表强调色：设计稿专属色，公共主色不等价 */
    color: #2f6bff;
}
```

**局部变量示例**：

```scss
.xxx-card {
    /* 卡片图表强调色：当前组件设计专属色，公共主色不等价 */
    --xxx-card-chart-color: #2f6bff;

    .xxx-card__chart-line {
        stroke: var(--xxx-card-chart-color);
    }

    .xxx-card__chart-value {
        color: var(--xxx-card-chart-color);
    }
}
```

```scss
/* ❌ 禁止：单次使用的值抽成局部变量 */
.xxx-card {
    --xxx-card-divider-border: 1px dashed #eeeeee;

    .xxx-card__divider {
        border-top: var(--xxx-card-divider-border);
    }
}

/* ✅ 正确：没有复用时直接写在使用处 */
.xxx-card {
    .xxx-card__divider {
        border-top: 1px dashed #eeeeee;
    }
}
```

## 组件变量与直接样式选择规范

**核心原则**：改 Element Plus、`sky-*`、`com-*` 等组件样式时，禁止默认上来就改组件变量，也禁止默认直接写样式；必须先判断本次改动的作用范围和语义。

**判断顺序**：

1. **组件 props / 默认样式能满足时**：优先用 props 或默认样式，不额外写 CSS。
2. **需要改变组件内建状态，并且组件已暴露语义变量时**：优先改组件变量。适用于同一个组件状态链路，如默认、hover、active、disabled、focus 都由组件变量统一控制。
3. **只是当前业务局部样式时**：直接写在对应业务选择器或 `:deep()` 结构里，不绕到组件变量上。
4. **变量不存在、语义不匹配或只使用一次时**：禁止改变量，应直接写局部样式。
5. **结构、布局、间距、宽高、圆角、滚动、分栏等样式**：默认直接改具体样式，不通过组件变量表达，除非组件官方变量就是专门控制该结构。

**适合改组件变量的场景**：

- 组件源码 / 文档 / DevTools 已确认变量真实存在。
- 变量语义正好对应当前样式目标，例如按钮文字色、hover 背景色、输入框 focus 边框色。
- 需要让组件内部多个状态保持一致。
- 不改变量会导致普通 `color` / `background` 被组件内部状态覆盖。

**适合直接改样式的场景**：

- 只影响当前页面、当前弹窗、当前业务块。
- 只是单次视觉还原，不具备复用语义。
- 改的是布局结构，如 `padding`、`gap`、`width`、`height`、`border-radius`、滚动区域。
- 使用变量会让维护者看不出真正改了哪个 CSS 属性。
- 需要覆盖的是具体 DOM 节点或具体状态，而不是组件整体主题。

**错误示例**：

```scss
/* ❌ 禁止：只是当前弹窗单次按钮样式，却绕到组件变量 */
.xxx-dialog {
    --xxx-dialog-button-hover-bg: #2f6bff;

    .xxx-dialog__button {
        --el-button-hover-bg-color: var(--xxx-dialog-button-hover-bg);
    }
}
```

**正确示例**：

```scss
/* ✅ 正确：单次局部样式直接写在对应状态 */
.xxx-dialog {
    .xxx-dialog__button:hover {
        background: #2f6bff;
    }
}
```

```scss
/* ✅ 正确：组件已确认通过变量统一控制多状态时，才改组件变量 */
.xxx-dialog {
    .xxx-dialog__button {
        --el-button-text-color: var(--xxx-color-white);
        --el-button-hover-text-color: var(--xxx-color-white);
        --el-button-active-text-color: var(--xxx-color-white);
    }
}
```

## 布局尺寸弹性优先规范

**核心原则**：布局尺寸优先使用内容自适应、`flex: 1`、`minmax()`、百分比、CSS 变量等弹性表达，避免写固定宽高或固定 flex-basis；只有设计稿、组件规范、业务格式或对齐约束明确要求固定尺寸时，才允许写固定值。

**执行要求**：

- 表格、表单、弹窗、筛选区等布局容器内，优先让子项通过 `flex: 1` / `width: 100%` / `min-width: 0` 自然分配空间。
- 多个控件需要对齐时，优先通过父级布局约束实现，例如统一 `gap`、统一列轨道、统一剩余空间分配；不要先给每个控件写死 `width: 128px`、`flex-basis: 126px`。
- 固定值只用于稳定格式场景，例如图标按钮尺寸、序号列宽、操作列宽、固定规格图片、设计稿明确标注且必须还原的尺寸。
- 写固定值时必须能说明原因；如果只是为了当前截图“看起来差不多”，应改用弹性布局。
- 不确定是否必须固定时，默认先使用弹性布局，再根据实际溢出、对齐或设计要求补充最小/最大约束。

**代码示例**：

```scss
/* ❌ 禁止：没有必要时写死两个控件宽度 */
.xxx-row {
    display: flex;
    gap: 8px;

    .xxx-select {
        flex: 0 0 128px;
    }

    .xxx-input {
        flex: 0 0 126px;
    }
}

/* ✅ 正确：让控件按父级空间自然分配 */
.xxx-row {
    display: flex;
    gap: 8px;

    .xxx-select,
    .xxx-input {
        flex: 1;
        min-width: 0;
    }
}
```

**判断标准**：

- 删除固定宽高后，布局是否仍能通过弹性规则自然对齐；能则不写固定值。
- 固定值是否来自明确设计 / 规范 / 业务格式；不是则优先用弹性布局。
- 固定值是否会导致不同屏幕、不同文案长度、不同控件组合下出现错位或截断；会则改为弹性约束。

## 组件默认样式优先规范

**核心原则**：使用 Element Plus、`sky-*`、`com-*` 等已有组件时，优先使用组件默认样式和组件 props，禁止为了“看起来更完整”自行覆盖按钮、文字、输入框、弹窗等基础视觉样式。

**执行顺序**：

1. 先确认组件是否已有语义 props，例如 `type`、`size`、`plain`、`link`、`text`、`loading`、`disabled`。
2. 需求值与组件默认样式一致时，不写额外 class / SCSS。
3. 只是按钮高度、最小宽度、字号、颜色、边框、背景等基础视觉，不要自行覆盖组件默认样式。
4. 只有明确设计稿、业务场景或系统既有规范要求区别于默认组件样式时，才允许单独写样式。
5. 需要自定义时，应优先通过组件 props 实现；props 无法满足时，再写局部样式，并在样式注释中说明业务原因。
6. 页面局部布局只影响位置时，优先给外层容器写布局，不要直接改组件本体视觉。

**禁止行为**：

```vue
<!-- ❌ 禁止：没有明确设计要求时，自行覆盖按钮尺寸和字号 -->
<el-button class="min-w-64 h-34 text-16" type="primary" plain>下载</el-button>

<!-- ❌ 禁止：Element Plus 已有语义色时，自行写颜色 class -->
<span class="text-#2eb270">成功 10 条</span>
```

**正确做法**：

```vue
<!-- ✅ 使用组件默认按钮样式 -->
<el-button type="primary" plain>下载</el-button>

<!-- ✅ 使用组件语义能力 -->
<el-text type="success">成功 10 条</el-text>
<el-text type="danger">失败 2 条</el-text>
```

**判断标准**：

- 如果删除自定义 class 后组件仍符合系统默认风格，应删除该 class。
- 如果只是让组件“更大 / 更小 / 更像截图”，但没有明确设计参数或既有规范，不应覆盖默认样式。
- 如果样式作用在 `el-button`、`el-input`、`el-select`、`el-text`、`sky-dialog` 等基础组件本体上，必须先说明为什么组件 props 和默认样式不够。
## UnoCSS 与专用样式边界

**核心原则**：简单原子样式优先直接使用 UnoCSS，只有样式具备结构、状态、复用或覆盖语义时，才单独编写 SCSS 类。

**优先使用 UnoCSS 的场景**：

- 单个节点仅涉及 1-3 个简单原子样式，如 `mb-8px`、`w-full`、`flex items-center`。
- 只是调整间距、宽高、对齐、字号、颜色、显示隐藏等纯表现属性。
- 样式只作用于当前节点，不涉及子元素、伪类、状态、组件内部覆盖。
- 临时局部布局微调，且 class 不会过长、不影响模板可读性。

**应单独写 SCSS 的场景**：

- 同一组样式具备业务语义、结构语义、状态语义，或原子类数量较多，并在当前组件内复用 2 次及以上。
- 单个节点 UnoCSS 超过 5-6 个原子类，模板可读性明显下降。
- 涉及 `:hover`、`:disabled`、激活态、业务状态变体等状态样式。
- 涉及子元素层级、BEM 结构、`:deep()` 覆盖组件内部结构。
- 涉及复杂尺寸计算、CSS 变量、滚动区域、固定布局、遮挡修复等结构性样式。
- 需要通过业务类名表达模块语义，方便全局搜索和后续维护。

**数量判断补充**：

- 计数口径：模板 `class` 中按空格分隔的 UnoCSS 原子类逐个计数；业务类名不计入。
- 单个节点 1-3 个 UnoCSS 原子类：使用 UnoCSS。
- 单个节点 4-5 个 UnoCSS 原子类：默认仍可使用 UnoCSS，但必须同时满足“一次性、纯表现、无状态、无子元素覆盖、无复用语义”。
- 单个节点 6 个及以上 UnoCSS 原子类：默认抽为 SCSS 业务类，避免模板可读性下降。
- 只要涉及业务结构根节点、`:deep()` 覆盖、伪类、状态样式、子元素层级、复用结构，即使原子类数量未超过 6 个，也应优先写 SCSS。
- 禁止为了减少 SCSS，把一个有明确业务含义的结构块堆成大量 UnoCSS 原子类。

**代码示例**：

```vue
<!-- ✅ 简单间距直接用 UnoCSS -->
<div class="common-info-title mb-8px">筛选列表</div>

<!-- ❌ 禁止为了一个 margin 单独写样式块 -->
<div class="common-info-title supplier-dialog__section-title">筛选列表</div>

<style scoped lang="scss">
.supplier-dialog__section-title {
    margin-bottom: 8px;
}
</style>
```

**嵌套规则**：

| 场景                     | 是否嵌套    | 说明                                                                  |
| ------------------------ | ----------- | --------------------------------------------------------------------- |
| 父子元素关系             | ✅ 嵌套     | 子元素样式写在父元素样式块内                                          |
| BEM 修饰符（同元素状态） | ✅ 嵌套     | `.block--modifier` 物理嵌套在基础类内部，需写全名 `&.block--modifier` |
| `:deep()` 覆盖子组件结构 | ✅ 嵌套     | 先命中子组件根节点，再在内部嵌套其后代节点和伪元素                    |
| 伪类/伪元素              | ✅ 允许 `&` | `&:hover`、`&::before`、`&:disabled`                                  |
| 元素选择器               | ✅ 允许嵌套 | 可直接嵌套 `img`、`span`、`i` 等                                      |

**代码示例**：

```scss
// ❌ 禁止：&__ 简写、父子结构平铺
.card {
    &__title {}
}
.card__header {}
.card__title {}

// ✅ 正确：完整类名 + 按 HTML 层级嵌套
.card {
    .card__header {
        .card__title {}
    }

    &.card--disabled {}
}
```

**`:deep()` 结构示例**：

```scss
// ❌ 禁止：子组件内部节点全部平铺
.page-card {
    :deep(.custom-select .inner-value) {}
    :deep(.custom-select .inner-body) {}
}

// ✅ 正确：先命中子组件根节点，再按内部层级嵌套
.page-card {
    :deep(.custom-select) {
        .inner-value {}
        .inner-body {}
    }
}
```

**判断标准**：

- 若 A 是 B 的 HTML 子元素 → B 的样式嵌套在 A 内部
- 若 A--modifier 是 A 的状态变体 → A--modifier 物理嵌套在 A 内部，且使用全名 `&.A--modifier`
- 使用 `:deep()` 覆盖子组件内部节点时，后代选择器也必须嵌套在被覆盖的子组件根选择器内部

# UI 与设计图还原规范

**核心原则**：在还原 Figma 等高质量 UI 设计稿时，严禁因为“图省事”而直接拼凑使用底层 UI 框架自带的通用图标（如 Element UI 的 `el-icon-circle-check`）去敷衍设计稿中的专属业务图形。必须使用原生 SVG 绘制或者专门的 UI 切图，确保视觉和质感的百分百精确还原。
