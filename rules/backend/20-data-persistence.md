# 后端数据持久化与事务规范

**核心原则**：数据库结构、写入流程和事务边界必须服务真实业务一致性，禁止用临时 SQL、隐式字段或无确认迁移掩盖数据模型问题。

**适用场景**：新增或修改表结构、Migration、Repository、SQL、ORM 查询、事务、批量写入、数据修复脚本、软删除和审计字段。

**硬性红线**：

- 禁止无迁移脚本直接依赖本地数据库字段；结构变更必须可追踪、可回滚或有明确发布说明。
- 禁止拼接未参数化 SQL，尤其是搜索、排序、筛选、批量 ID 和动态表名场景。
- 禁止在多表写入、状态流转、余额 / 库存 / 次数等一致性场景中缺失事务或幂等控制。
- 禁止为了让查询“先能跑”而跨表硬凑字段语义；字段来源必须属于当前数据模型。
- 禁止破坏历史数据语义，例如用当前配置覆盖历史快照、用软删除数据参与正常统计。

**正确做法**：

- 表结构变更必须配套 Migration / 变更说明，并明确默认值、可空性、索引和历史数据处理方式。
- 查询条件、排序字段和分页参数应通过白名单或类型约束进入 SQL / ORM。
- 涉及多资源写入时明确事务范围；涉及重复提交、消息重试或定时补偿时补幂等键。
- 数据修复脚本必须先只读预览影响范围，再执行写入，并保留执行结果。
- 统计、快照和审计字段必须区分当前值、历史值和派生值，禁止互相兜底。

**代码示例**：

```ts
// ❌ 禁止 - 动态排序字段直接拼 SQL
const rows = await db.query(`select * from xxx order by ${sortField}`)

// ✅ 正确 - 排序字段走白名单
const sortColumnMap = {
    createTime: 'create_time',
    updateTime: 'update_time'
}
const sortColumn = sortColumnMap[sortField]
if (!sortColumn) return []
```

**判断标准**：

- 数据结构变更是否可追踪，发布后是否能在其他环境复现。
- 写入失败时是否会留下半成功状态。
- 重试、并发和重复请求是否会造成重复数据或状态倒退。
- 查询条件是否经过白名单、参数化或类型约束。
