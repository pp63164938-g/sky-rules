# 禁止自行发散

**核心原则**：**严禁自行发散新增任何代码结构**。用户未明确指定的内容，一律不得自行生成。

**适用场景**：新增字段、搜索项、表格列、接口参数、下拉数据源、权限标识、路由参数、详情模块、弹窗入口等所有会扩大需求范围的变更。

**硬性红线**：没有用户明确要求、接口文档、抓包、项目已有真实代码或后端确认时，不得把推断写成确定代码；必须先问，或在需求已确认的最终使用位置使用可搜索 TODO 标记。

## 禁止静默发散规范

**核心原则**：AI 不得将自行推断、补全、兼容、扩展出来的内容，静默写成确定代码。只要不是用户明确要求、接口文档明确说明、项目已有代码可证明、或后端明确确认的内容，都属于发散。发散可以作为临时方案，但必须主动通知用户，不能只依赖用户自己从代码 diff 中发现。

**执行要求**：

1. **先区分事实与推断**：有依据的按确定逻辑写；无依据的不能伪装成确定业务规则。
2. **能不发散就不发散**：优先保留接口原值、展示空值、暴露缺失字段，避免为了“看起来完整”补逻辑。
3. **必须发散时主动通知**：在动手前或最终回复中明确列出发散点、发散依据、影响范围、需要确认的问题。
4. **代码中同步标记**：发散点必须使用 `TODO待确认_用途描述` / `TODO待联调_用途描述` / `TODO无此联调字段_用途描述` 标记，确保后续可搜索。
5. **高风险发散先确认**：凡是会影响接口参数、提交数据、金额、权限、业务分支、状态流转的数据逻辑，禁止先写后说，必须先问用户。
6. **最终交付必须交代**：本次如果存在发散点，最终回复必须单独列出“发散点”；如果没有，也应说明“无额外发散”。
7. **字段存在不等于能力确认**：需求、截图、接口路径或响应字段只确认了“字段名 / 展示位置”时，只能按已确认部分实现；查询入参、响应场景、字段类型、控件单选/多选、提交结构、枚举值、数据源返回结构等未明确部分，仍然视为未确认。禁止从同页相似字段、历史页面写法或组件惯用写法推断成确定逻辑。
8. **属性级待确认也必须标记**：同一个业务字段可以“字段名已确认，但类型/入参/控件形态未确认”。已确认部分正常实现，未确认部分必须用 `TODO待联调_用途描述` / `TODO无此联调字段_用途描述` 标记，或在动手前反馈用户确认；禁止因为字段名看起来合理就把整条链路写成确定代码。
9. **待确认内容只允许 TODO 命名预留，禁止衍生临时逻辑**：字段名、查询参数、提交字段、响应字段、枚举值、Options 或动作标识尚未确认时，必须在其最终使用位置使用 `TODO待联调_用途描述` 显性占位，禁止伪装成正式名称。预留仅代表该名称或值需要在联调时原位替换；页面结构、控件绑定、交互、校验、查询、提交和业务流程必须按真实需求实现。禁止仅因“不确定联调是否需要”新增参数过滤函数、`omit`、映射层、影子状态、重复字段、禁用态、待联调提示、特殊分支或临时兜底。确有需求依据的业务逻辑正常保留，不得当作预留逻辑处理。
10. **待确认内容不得默认抽常量**：接口字段、查询参数、提交字段、响应字段、下拉数据源、枚举真实值等未确认内容，禁止为了“统一引用”或“方便后续替换”默认抽成普通常量。常量只适合承载已确认且稳定的前端场景标识、跨文件复用标识、真实业务枚举或项目约定值；如果不确定内容本质是后端契约缺口，应在最终使用位置使用 `TODO待联调_用途描述` / `TODO无此联调字段_用途描述`，静态成功统一放在 API 层 Mock。需要可拓展结构时，可以定义前端本地 payload / type，但其中未确认字段仍必须用 TODO 属性名暴露，禁止用普通字段名加注释伪装成已确认契约。
11. **缺失数据源不得硬凑**：当需求需要下拉、弹窗、筛选项、详情模块等功能，但接口文档、抓包、后端确认或项目已有真实接口中没有对应数据源时，禁止拿相似页面、分页接口、列表接口或名称相近接口硬凑成确定功能。例如没有“业务下拉接口”时，禁止用“业务列表分页接口”包装成 `xxxOptions`。
12. **缺失接口不得改变需求已确认的交互**：需求明确存在的页面入口、搜索项、按钮、页签、表格列、弹窗区域和控件形态，在接口或字段尚未提供时，仍应保持真实功能应有的结构、绑定和交互。禁止仅因接口待开发就擅自禁用按钮或控件、改成只读、隐藏入口、增加“接口待联调”文案或建立另一套临时流程。静态阶段缺接口时，按静态接口开发规范在 API 层 Mock，组件继续走正式流程；联调时只替换 TODO 字段、枚举值和真实接口契约。
13. **需求存在但接口缺失必须预留，禁止改功能**：只要需求、原型、截图或用户确认中明确存在某个功能、入口、字段、控件、表格列、弹窗区域、计算结果或数据来源，即使接口文档暂未提供，也必须按原需求保留页面结构、真实交互、目标 API 调用位置和 API 文件 Mock。禁止因为“没有接口 / 没有字段 / 没有数据源”就删除入口、隐藏字段、改变控件形态、改变路由参数、改用列表行快照、改成本地计算、改成相似接口、改成手填输入，或把原本依赖接口的功能改成另一套实现。静态阶段未确认契约使用 `TODO待联调_用途描述` 原位预留；进入联调后仍缺失的契约改为 `TODO无此联调字段_用途描述` 并反馈待提供接口，不得改组件功能链路。
14. **联调前发散必须前置告知**：凡是需要临时替代接口、临时禁用入口、临时使用空 Options、临时展示占位、临时保留 TODO 的，必须在动手前或最终回复中明确告知用户：位置、临时处理内容、依据、影响范围、待确认事项。禁止只让用户从 diff 或代码注释里反查。
15. **禁止为了完成目标伪造完整性**：没有接口、字段、枚举、图片、图表数据或数据源时，禁止使用静态默认值、相似字段、本地计算或假兜底伪造真实结果。需求已确认的结构和交互正常实现，未确认契约只在最终使用位置使用 `TODO待联调_用途描述` 预留；禁用、空态、提示或特殊分支只有在需求、用户确认或真实业务规则明确要求时才允许增加。
16. **任何兜底逻辑必须交付告知**：本次新增、修改或保留的兜底逻辑，无论是展示占位、空数组、默认枚举、兼容旧字段、静态 Mock、异常返回还是接口缺字段处理，都必须在最终回复中列出位置、策略、依据、影响和后续处理。禁止只在代码注释或 diff 中体现。

**通知格式**：

```md
发散点：
- 位置：xxx
  内容：临时按 xxx 处理
  依据：目前只有 xxx，缺少 xxx
  影响：影响 xxx 展示/提交/判断
  待确认：需要后端/用户确认 xxx
```

**判断标准**：

- 用户是否不看 diff 也能知道哪些内容是 AI 推断出来的。
- 回复里是否明确说明了发散点、依据、影响和待确认事项。
- 代码里的变量名、注释、映射、兜底是否把未确认内容包装成了确定规则。
- 最终回复是否列出所有兜底逻辑；如果用户只能靠审代码才发现兜底，说明交付不合格。
- 如果用户只能靠仔细审核代码才发现推断，说明已经构成静默发散。

**禁止范围**：

- **表单字段**：禁止自行新增 `searchForm` / `form` 中的字段
- **搜索项**：禁止自行新增搜索栏的筛选项
- **表格列**：禁止自行新增列配置、合并列插槽
- **接口参数**：禁止自行新增接口请求参数
- **接口 URL / Query 参数**：禁止自行编造 API 的 URL 路径或 Query 参数名。必须基于用户提供的浏览器抓包、接口文档或项目已有代码中的真实请求，严禁凭合理猜测拼出不存在的参数（如把文档里的 `queryType` 猜成 `listType`）
- **下拉数据源**：禁止自行新增下拉选项的数据源定义
- **模块导入路径**：禁止主观猜测无把握的模块导入路径（如 `import request from '@/utils/request'`）。对于基建工具类引入，必须参考同项目中现有代码的引用方式。

**正确做法**：

- 用户说"用 X 接口"→ 只替换数据源，不新增字段
- 用户说"加一列 X"→ 只加这一列，不自行扩展其他列
- 用户说"改成 X"→ 只做替换，不新增额外内容
- **不确定时先问**：如果用户的描述有歧义（如没说加在哪里、对应哪个字段），必须先询问确认，禁止自行猜测并生成代码

**反面案例**：

```
用户：业务状态，使用 `getXxxStatusOptions` 接口
正确：只替换已有业务状态下拉的数据源
错误：自行新增“业务类型”搜索项 + 表单字段 + 数据源
```

```
用户：帮我写一个拉取帖子列表的功能
正确：先让用户提供浏览器抓包或接口文档，按真实参数编写
错误：自行编造文档不存在的 Query 参数
```

# 禁止擅自优化老代码

**核心原则**：拓展功能时，**严禁顺手优化或重写已有代码**。只做用户要求的变更，不改动老代码的写法。

**适用场景**：在已有页面、组件、API、样式、判断分支旁边新增或替换功能时。

**硬性红线**：禁止为了风格统一、代码更好看、减少行数、顺手清理而改动用户未要求的老代码；替换功能必须保留原逻辑注释。

**禁止行为**：

- 修改老代码的语法风格（如 `any` → `Omix`、`{ return {} }` → `=> ({})`）
- 重构老代码的逻辑结构（如拆函数、合并变量、调整顺序）
- 替换老代码的实现方式（如换 API、换组件、换工具函数）
- 删除已注释的老代码块（注释代码属于保留参考，禁止擅自清理）
- 改变老代码的格式排版（如单行写法改多行、多行改单行，保持原格式不动）
- 在替换代码时误删周围不相关的老代码（替换范围必须精确，只动目标代码，不波及上下文的已有逻辑）

**维护旧判断的最小侵入原则**：维护已有功能时，默认保持老代码原有判断语义、分支关系和默认行为。新增逻辑应优先以前置拦截、独立函数或独立分支实现；只有在不改变旧分支含义和执行结果的前提下，才允许为减少重复收尾逻辑而调整判断结构。

- 新增高优先级逻辑时，优先在老判断前增加独立分支，避免改动老判断内部逻辑
- 禁止为了新增逻辑改变老判断的业务含义、默认分支、触发条件或执行顺序
- 允许在不改变旧逻辑结果的前提下，将判断整理为 `if / else if / else`，用于共享统一收尾逻辑或避免重复副作用
- 禁止把两个独立业务弹窗、路由动作或状态判断耦合到同一个旧函数里
- 简单的新跳转参数、一次性带入数据等轻量扩展，可以复用已有函数并通过可选参数实现，但必须保证老调用的入参、返回数据和行为完全不变
- 新弹窗、新业务动作如果会改变旧函数职责、引入业务分支耦合或让旧函数语义变模糊，应新增独立函数，老函数保持原语义不变
- 修改完成后必须回看 diff，确认旧判断的业务结果没有变化，只是被新增逻辑前置拦截或共享收尾

**替换功能的正确做法**：

- **新增功能**：在老代码旁边新增，不动老代码
- **替换功能**：注释原来的代码，在旁边写新代码，而不是直接覆盖
- **必要注释格式**：`<!-- 原逻辑：描述 ... 原代码 ... -->` 或 `// 原逻辑：...`

**代码示例**：

```vue
<!-- ❌ 禁止 - 直接覆盖替换老代码 -->
<new-component v-model="form.field" />

<!-- ✅ 正确 - 注释原代码，新代码写在旁边 -->
<!-- 原逻辑：使用 com-form-select 下拉
<com-form-select v-model="form.field" :options="options" /> -->
<new-component v-model="form.field" />
```

**判断标准**：

- 如果改动不是用户明确要求的 → 不改
- 如果老代码能正常工作但风格不同 → 不改
- 不确定是否该改 → 先问用户

# AI 代码修改与替换规范

**核心原则**：在执行代码修改（特别是区块替换）时，必须做到“精准打击”，严禁由于粗心漏写而误删上下文中不相关的注释。

**行为准则**：

1. **精准定位目标区块**：选中待修改代码块时，只圈定真正需要修改的代码部分，不要贪图省事把周围的注释标签一并囊括。
2. **严格保持代码与注释完整性**：如果在替换过程中无可避免地包含了原有的注释（如 `<!-- 表单模块 -->`），在生成新代码时，必须**原封不动地将这些注释保留写回**，绝对禁止静默删减。
