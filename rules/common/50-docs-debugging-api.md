# 静态接口开发规范

适用场景：后端未提供接口文档时，前端需进行静态开发。

**硬性红线**：静态阶段可以保留可搜索 TODO 和 API 文件 mock，但禁止在组件内联 mock，禁止把未确认字段伪装成正式字段；缺接口时只允许在 API 文件中按目标接口契约 mock 或占位，禁止改组件功能链路、路由传参、交互形态、本地计算逻辑或提交结构来绕过接口缺失。

开发原则：

- **组件代码**：正常调用接口，写法与正式接口一致，无需任何改动
- **API 文件**：在 API 定义中返回模拟数据，联调时仅需修改此处
- **禁止在组件中内联 mock 数据**：所有 mock 数据必须放在 API 函数中，保持组件代码干净

API 文件规范：

- 响应结构：{ code: 0, msg: "模拟数据", data: 业务逻辑数据, success: true }
- **mock 只关注响应数据**：不包含业务逻辑判断（如输入长度限制），业务逻辑由调用方控制
- 使用 `// @mock-start 联调时删除` 和 `// @mock-end` 标记包裹模拟数据代码块
- 在 `// @mock-end` 后保留被注释的正式请求代码
- 联调时删除 `@mock-start` 到 `@mock-end` 之间的代码（包括标记），取消注释正式请求

## TODO 字段标记规范

**核心原则**：待确认字段的后缀必须使用**中文用途描述**，让人一看就知道**这里需要什么数据**。

**两种前缀**：

| 前缀                | 适用阶段 | 含义                                   |
| ------------------- | -------- | -------------------------------------- |
| `TODO待联调_`       | 静态开发 | 字段名待后端确认，联调时替换为真实字段 |
| `TODO无此联调字段_` | 联调阶段 | 接口文档中不存在此字段，需与后端确认   |

**命名规则**：前缀 + **中文用途描述**，描述应说明该字段的业务含义。

**代码示例**：

```javascript
// ❌ 不推荐 - 后缀用英文字段名，看不出需要什么数据
TODO无此联调字段_rate;
TODO待联调_exchangeRate;

// ✅ 推荐 - 后缀用中文用途描述，一看就知道需要什么
TODO待联调_汇率;
TODO待联调_汇率日期;
TODO无此联调字段_客户状态;
TODO无此联调字段_客户创建时间;
```

**适用场景**：

| 场景                      | 示例                                            | 说明                       |
| ------------------------- | ----------------------------------------------- | -------------------------- |
| 静态开发-字段名未定       | `TODO待联调_用户名: res.data.TODO待联调_用户名` | 字段名待后端确认           |
| 静态开发-下拉选项未定     | `const TODO待联调_星级Options = ref([])`        | 下拉数据源待确认           |
| 联调-接口文档缺少字段     | `:value="row.TODO无此联调字段_客户状态"`        | 接口无此字段，需与后端确认 |
| 联调-不确定用哪个接口字段 | `:rate="summaryData.TODO无此联调字段_汇率"`     | 不确定该用哪个字段         |

**使用规则**：

1. 全局搜索 `TODO待联调_` 或 `TODO无此联调字段_` 即可找到所有待处理项
2. **禁止自行发散字段**：接口文档没有的字段，禁止自己编造字段名
3. `TODO待联调_` 适用于所有无接口文档依据的变更（新增字段、单选改多选、数据源变更等），已有页面中已确定的字段禁止改为 TODO
4. 表单字段名（`searchForm`/`formData` 的属性名）与提交接口时的参数字段名应保持一致，不要定义两个不同的名字来表示同一个字段
5. 联调/上线前，全局搜索确保已全部处理
6. `TODO待联调_` / `TODO无此联调字段_` 不只用于字段名缺失；字段类型、查询参数、响应场景、下拉数据源、枚举真实值等关键属性未确认时也必须标记或反馈确认。
7. 联调阶段的 TODO 清理、临时命名替换、缺接口入口保留、缺数据源处理，统一按“联调开发规范”的硬性红线执行，避免在多个章节重复维护同一规则。
8. **待确认字段名必须显式暴露在属性名中**：字段名未确认时，`TODO待联调_` / `TODO无此联调字段_` 必须作为属性名、参数名或绑定字段名的一部分，禁止只写在注释里。仅注释标记会让字段看起来像已联调确认的正式字段。

```javascript
// ❌ 禁止 - 属性名像正式接口字段，只有注释暴露待确认
const searchForm = {
    xxxTypeList: undefined // TODO待联调_业务类型筛选参数
}

// ✅ 正确 - 待确认状态直接体现在属性名中，避免误认为已联调
const searchForm = {
    TODO待联调_业务类型筛选参数: undefined
}

// 查询前必须剔除未确认字段，禁止提交给接口
const params = { ...searchForm }
delete params.TODO待联调_业务类型筛选参数
```

# 联调开发规范

适用场景：与后端进行接口联调时。

**硬性红线**：联调范围内禁止遗留 `TODO待联调_`；文档缺失字段必须改为 `TODO无此联调字段_用途描述` 并反馈待确认项；字段名必须与接口文档一致；需求已确认但接口缺失时必须预留原功能位置和目标接口链路，禁止通过删除入口、改变交互、改变路由传参、改用其他数据来源、本地计算或相似接口来绕过接口缺失。

**联调缺口禁止静态兜底过关**：联调阶段发现接口未提供字段、枚举值、数据源或稳定标识时，必须暴露缺口并等待补充，禁止用静态默认值、示例数据、前端推断、中文文案判断或本地计算让联调结果看起来已经完整。

**静态预留内容不得因后端缺口被删除**：如果页面在静态开发阶段已经根据需求文档、原型、截图或用户确认预留了入口、搜索项、表格列、弹窗区域、下拉控件、按钮或 API 占位，联调时发现后端接口未提供字段、字段类型不符、结构不一致、数据源缺失或返回异常，禁止直接移除这些预留内容来绕过后端问题。必须保留用户可感知预留位或目标接口链路，将静态阶段的 `TODO待联调_` 改为 `TODO无此联调字段_用途描述`，并在交付中明确说明后端缺口、影响范围和待确认事项。

接口文档查阅：

- 联调前，优先查看项目根路径下的接口文档文件
- 文档文件名：[api.md]、`api-docs.md`、`api-word.md`
- 根据文档中的字段定义进行精确映射

核心原则：

- **严格按接口文档映射**：字段名必须与文档完全一致
- **禁止自行发散字段**：遇到接口文档没有的字段，**禁止**自己发散直接生成字段名
- **待确认字段用 TODO无此联调字段\_ 标记**：使用 `TODO无此联调字段_用途描述` 格式占位，便于全局搜索和理解
- **前后端字段名一致**：表单字段名（`formData` 的属性名）必须与接口请求参数的字段名完全一致，禁止前端自定义一套字段名再在提交时映射为另一套。即使后端字段名有拼写错误（如 `amout` 而非 `amount`），前端也必须跟随后端字段名，保持一致。
- **兜底逻辑必须告知**：联调中任何展示占位、空 Options、默认值、兼容旧字段、缺字段 TODO、禁用入口、静态 Mock 或异常返回，都必须在最终回复中列出位置、策略、依据和影响范围，禁止只让用户审代码才发现。

## API 函数入参类型定义规范

**核心原则**：API 文件中的请求入参类型必须服务接口契约本身，禁止为了省事用 `Omix` 兜底，也禁止为一次性简单入参机械抽类型。

**执行要求**：

1. **1-3 个已确认字段的一次性入参**：优先在 API 函数参数处使用内联对象类型，并给字段添加 JSDoc 注释说明业务含义、可选语义和关键枚举值。
2. **字段较多、结构嵌套、跨函数复用或会被外部显式引用的入参**：再定义具名 `type` / `interface`；仅当前 API 文件内部使用时不导出，确实被外部复用时才导出。
3. **`Omix` 只用于真实动态结构**：例如透传动态筛选条件、后端字段开放且无法枚举、组件 / 工具函数需要接收不固定对象等场景。不能因为字段多、懒得写类型、接口文档没读全，就把明确接口入参写成 `Omix`。
4. **已确认接口字段必须写进类型结构**：字段名、字段类型、枚举值以接口文档 / 抓包 / 后端确认为准；未确认字段不得用看似正式的类型字段名包装，必须按 TODO 字段标记规范处理。
5. **不传值有业务含义时必须注释**：例如“不传表示全部”“不传表示默认规则”等，必须写在字段注释里，避免调用方误以为空值和缺省值等价。

**代码示例**：

```ts
// ❌ 禁止 - 单字段已确认入参用 Omix 兜底
export function getXxxList(data?: Omix) {}

// ❌ 禁止 - 单次使用的简单入参机械抽类型
export type XxxListParams = {
    /** 业务状态：0 禁用，1 启用；不传表示全部 */
    status?: 0 | 1
}

export function getXxxList(data?: XxxListParams) {}

// ✅ 正确 - 一次性简单入参直接内联，并说明缺省语义
export function getXxxList(data?: {
    /** 业务状态：0 禁用，1 启用；不传表示全部 */
    status?: 0 | 1
}) {}
```

**判断标准**：

- 调用方是否能直接从 API 函数签名看懂可传字段。
- 这个类型是否会复用；不会复用且字段很少，就不要单独抽类型。
- 字段是否真实动态；不是动态结构，就不要用 `Omix`。

## 跨接口字段归属规范

**核心原则**：字段必须归属于当前页面实际使用的目标接口及其响应路径；严禁拿其他接口、其他页面位置、相似模块、配置接口、预览接口或字典接口中的字段结构，反推并写入当前接口的响应类型、表格列、详情展示或提交结构。目标接口没有的字段就是没有，必须按缺失处理，不能为了让页面看起来完整而硬凑。

**硬性红线**：

- 禁止用预览接口字段补详情接口字段。
- 禁止用配置接口字段补快照接口字段。
- 禁止用列表接口字段补详情接口字段。
- 禁止用详情接口字段补列表接口字段。
- 禁止用字典 / Options 接口字段补主数据接口字段。
- 禁止因为字段名相同、字段含义相似、页面文案相近，就写入当前接口类型、表格列、详情展示或提交结构。
- 禁止把未使用、未确认、仅其他接口存在的字段保留在当前接口类型里，避免误导后续开发。
- 当前接口缺字段时，必须使用 `TODO无此联调字段_用途描述` 显性标记，并反馈后端补字段或确认来源；禁止用其他接口字段硬凑。

**执行要求**：

1. **先锁定主数据接口**：开发前必须明确当前页面展示数据来自哪个接口、哪个响应路径，例如 `data.xxxList[]`。只有该路径文档、抓包真实响应或后端确认存在的字段，才允许作为正式字段使用。
2. **相邻接口不能互证字段**：A 接口出现的字段，只能证明 A 接口支持该字段；不能证明 B 接口、详情接口、列表接口、预览接口、配置接口、快照接口也支持该字段。
3. **字典接口只做翻译**：Options / 枚举 / 字典接口只能用于把当前主数据接口已经返回的 code 转成 label；禁止用字典接口补主数据字段、补表格列、补详情内容。
4. **配置接口不得补快照字段**：当当前页面展示的是历史快照、任务快照、审批快照等数据时，必须以快照接口返回为准；禁止调用当前配置接口硬拼缺失字段，否则会破坏历史快照语义。
5. **预览接口不得补详情字段**：预览、草稿、试算、计算类接口返回的字段，只能用于对应预览 / 试算位置；禁止拿来补详情、列表、快照等正式展示位置，除非接口文档、抓包或后端明确确认该位置也返回同一字段。
6. **当前接口类型只保留当前字段**：类型定义、表格列、详情展示、提交结构只保留当前目标接口已确认且当前代码实际消费的字段；未使用、未确认、仅其他接口存在的字段应删除或按缺字段显性标记，禁止为了“以后可能用”保留。
7. **字段缺失必须显性处理**：如果需求要展示某字段，但目标接口响应路径没有该字段，应保留可感知预留位或按当前已确认字段展示，并标记 `TODO无此联调字段_用途描述`，同时反馈需要后端补字段或确认数据来源。
8. **跨接口关联必须先确认**：只有接口文档、抓包或后端明确说明关联键、数据时效和来源语义时，才允许跨接口 join；否则禁止前端自行拼接。

**错误示例**：

```ts
// ❌ 错误：详情接口 records[] 没有 desc，配置接口有 desc，于是直接把 desc 写进详情展示
const columns = [
    { label: '说明', prop: 'desc' }
]
```

```ts
// ❌ 错误：字典接口只返回 code/label，却用来补主表行数据
const rowText = dictMap[row.TODO无此联调字段_类型]
```

```ts
// ❌ 错误：预览接口有 previewXxx，于是详情页直接用它补详情字段
const detailInfo = {
    xxx: previewData.previewXxx
}
```

**正确示例**：

```ts
// ✅ 正确：只展示详情接口 records[] 已确认返回的字段
const columns = [
    { label: '名称', prop: 'name' },
    { label: '等级', prop: 'grade' }
]
```

```ts
// ✅ 正确：需求需要“说明”，但详情接口缺字段，先显性标记并反馈后端
const columns = [
    { label: '说明', prop: 'TODO无此联调字段_说明' }
]
```

```ts
// ✅ 正确：详情页只使用详情接口已确认字段
const detailInfo = {
    xxx: detailData.xxx
}
```

**判断标准**：

- 当前字段能否在当前页面主数据接口的明确响应路径中找到。
- 其他接口是否只是“看起来相关”，但没有说明可作为当前页面数据来源。
- 字典接口是否只用于翻译已有字段，而不是补不存在的数据。
- 快照页面是否错误使用了当前配置接口补历史快照内容。

## 接口与需求结构不一致沟通门禁

**核心原则**：联调时只要发现需求交互、页面结构、提交结构、接口入参、接口响应、字段含义、批量 / 单条语义之间存在不一致、缺失或疑似对不上，必须及时沟通，禁止自行消化成“看起来可用”的实现。

**硬性红线**：

- 禁止在接口文档只支持单条时，自行补成批量提交结构，或在接口文档只支持批量时，自行拆成单条循环。
- 禁止在接口缺字段、缺结构、缺入口、缺返回值时，用前端本地状态、列表快照、兜底字段、相似字段或自定义字段把页面做成“没有问题”的样子。
- 禁止把未确认的字段、结构、参数或批量语义写成正式提交参数；即使页面内部需要临时状态，也必须和接口提交结构明确隔离。
- 禁止联调阶段只在代码里留 TODO，而不向用户说明问题；用户不看 diff 也必须知道当前哪里对不上、影响什么、需要后端或需求确认什么。
- 禁止联调阶段只在代码里留兜底逻辑，而不向用户说明兜底位置、依据、影响范围和后续处理。
- 禁止因为后端接口未实现、字段缺失、字段类型不符或响应结构不一致，就删除静态阶段按需求预留的页面入口、控件、列、按钮、弹窗区域或 API 调用链路。

**正确处理方式**：

1. 先指出不一致点：说明是需求、接口、交互、字段还是提交结构对不上。
2. 说明影响范围：影响展示、提交、保存、详情回显、审批流流转还是批量操作。
3. 保留可感知预留位：页面入口、表格列、表单项、按钮或结果区域不能直接消失；应禁用、空状态、提示或占位。
4. 代码显式标记：使用 `TODO无此联调字段_用途描述` 或明确的待确认注释，不能伪装成已确认字段。
5. 最终回复显式告知：列出缺口、兜底策略、影响范围和待确认事项，不能要求用户从 diff 或代码注释中反查。
6. 等确认后再实现：需要后端补接口、调整字段、确认批量语义或确认降级方案时，必须先沟通，不能自行决定。
7. 静态预留回溯：联调发现接口对不上时，必须先回看静态预留依据，包括需求文档、原型、截图、用户确认、TODO 标记和 API mock；确认该预留属于需求范围后，应保留预留位并暴露后端缺口，不能把预留内容移除成“页面无此需求”。

**判断标准**：

- 如果用户需要看代码 diff 才知道接口和需求对不上，说明处理错误。
- 如果页面表现得像已经联调完成，但实际依赖前端自定义字段或本地兜底，说明处理错误。
- 如果接口文档没有的结构进入了请求体，说明处理错误。
- 如果用户需要审代码才知道本次存在兜底逻辑，说明处理错误。

```javascript
// ❌ 禁止 - 前端用 amount/reason，提交时映射为 amout/reson，两套名字
const formData = { amount: "", reason: "" };
const params = { amout: Number(formData.amount), reson: formData.reason };

// ✅ 正确 - 直接用后端字段名，提交时无需映射
const formData = { amout: "", reson: "" };
const params = { amout: Number(formData.amout), reson: formData.reson };
```

# 临时代码标记规范

用于标记需要在特定阶段移除的临时代码，便于全局搜索和批量清理。

标记格式：

- **Mock 数据**：`// @mock-start 联调时删除` ... `// @mock-end`
- **TODO 待办**：`// @todo-start 描述` ... `// @todo-end`
- **待确认字段**：`TODO待联调_用途描述`（静态开发）/ `TODO无此联调字段_用途描述`（联调阶段）

使用规则：

1. 开始标记后可添加简短描述，如 `// @mock-start 联调时删除`
2. 结束标记保持简洁，如 `// @mock-end`
3. 标记成对使用，包裹需要移除的完整代码块
4. 联调/上线前，全局搜索对应标记进行清理
5. **静态缺接口优先走正式组件流程**：静态开发阶段缺少接口时，组件应尽量按最终正式流程编写，正常调用 API 函数并处理成功 / 失败回调；禁止在组件中用“接口待联调”告警直接中断流程，导致后续联调还要重写组件主流程。
6. **Mock 只能放在 API 层**：缺接口时只能在 API 文件中用 `// @mock-start 联调时删除` / `// @mock-end` 包住模拟成功返回，并在 mock 标记中保留 `TODO待联调_用途描述`；禁止在组件内联 mock 成功、改本地状态伪造真实后端结果或串联相似接口。
7. **静态预留遵循最小包裹原则**：需求已确认、后续正式联调仍会保留的业务入口、函数声明、模板入口、API 函数名和业务 JSDoc 不应整体包进临时标记；只包裹 API mock 返回、临时空数据或临时缺口实现等需要联调替换的最小代码块。
8. **生命周期标记必须写清替换范围**：`@mock-start` / `@todo-start` 描述必须明确是“联调时替换本块”还是“联调时删除整个入口”。默认只能替换本块；只有入口本身不是需求确认内容、或用户明确要求临时入口时，才允许删除整个入口。
9. **静态成功必须交付告知**：只要当前成功路径来自 API mock，最终回复必须说明 mock 位置、不会产生真实业务副作用、联调时需要替换的真实接口和字段；禁止让用户误以为已经完成真实链路。
10. **联调清理顺序必须明确**：进入联调时先全局搜索 `@mock-start`、`@todo-start`、`TODO待联调_`、`TODO无此联调字段_`，逐项确认替换、删除或升级为 `TODO无此联调字段_用途描述`；禁止把静态 mock 或静态预留标记原样保留到联调交付结果中。

```javascript
// ❌ 禁止 - 组件中断正式流程，联调时还要重写主流程
/** xxx 操作入口 */
async function handleXxx() {
    message.warning('接口待联调')
}

// ✅ 正确 - 组件按正式流程调用 API，临时成功只在 API 层 mock
/** xxx 操作入口 */
async function handleXxx() {
    await submitXxx(params)
    message.success('操作成功')
    refreshList()
}

/** xxx 操作 */
function submitXxx(params = {}) {
    // @mock-start 联调时删除：TODO待联调_xxx操作接口方法路径参数
    return Promise.resolve({ code: 0, data: true, msg: '模拟成功' })
    // @mock-end
    // 联调时替换为接口文档、抓包或后端确认的真实 request 调用
}
```
