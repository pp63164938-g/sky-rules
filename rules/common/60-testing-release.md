# 全栈测试、迁移与发布规范

**核心原则**：跨端需求必须通过分层验证和可回滚交付形成闭环；禁止以“前端可操作”或“后端接口可调用”单方面代替完整验收。

**适用场景**：前端、后端、接口契约、数据库 Migration、鉴权、缓存、队列、第三方系统、CI、发布和回滚相关变更。

## 分层测试要求

**硬性红线**：

- 禁止用单一层级测试代替完整风险验证；前端页面、后端接口、数据库和异步任务涉及哪一层，就必须验证哪一层。
- 禁止只验证正常路径；权限拒绝、参数错误、重复请求、并发、事务回滚和外部依赖异常必须按实际风险覆盖。
- 禁止编造测试命令、测试框架、Fixture、环境变量或测试账号；必须来自项目脚本、依赖、文档或用户确认。
- 禁止在缺少真实验证结果时写成“已通过 / 已验收”；无法执行的验证必须说明原因、影响和替代证据。
- 禁止使用生产密钥、生产连接或未经脱敏的生产数据作为普通测试资源。

**执行要求**：

- 纯业务计算、数据转换和状态规则优先通过单元测试验证输入、输出和边界。
- Service、Repository、数据库、缓存和队列协作通过集成测试验证真实交互、异常与回滚。
- 接口变更必须验证请求方法、路径、参数、响应结构、错误码、鉴权和兼容语义；契约来源只能是接口文档、OpenAPI、抓包、后端确认或项目已有真实实现。
- 前后端共同参与的核心流程应执行端到端验证；环境不支持时，以契约测试和逐步联调覆盖可确认部分，并显式列出未覆盖项。
- 只影响单层的变更使用与风险匹配的最小验证集；禁止为了形式完整机械执行无关的全项目测试或构建。

## 数据库迁移要求

**核心原则**：Migration 必须同时说明目标结构、历史数据、执行影响和恢复路径，不能只证明新结构可以创建。

**执行要求**：

- 结构变更必须说明字段可空性、默认值、索引、历史数据处理和新旧代码兼容窗口。
- 执行写入前必须先预览受影响的数据范围、执行计划和锁表 / 性能风险；高风险生产写入必须获得明确授权。
- 破坏性变更应与兼容发布拆分，优先完成可兼容的新增、回填和切换，再清理旧结构。
- 必须提供可执行回滚方案；数据变更无法安全回滚时，应提供前向修复方案并明确不可逆风险。
- Migration、数据修复和回填脚本必须验证重复执行、部分失败和中断恢复的行为，避免留下半完成状态。

## 兼容发布与回滚

**硬性红线**：

- 禁止默认前端、后端和数据库能够同时发布；发布顺序必须以实际兼容关系为依据。
- 禁止在没有健康检查、观察指标、失败判定或恢复路径时宣告可发布。
- 禁止把“回滚代码”默认等同于“恢复数据”；数据库和外部副作用必须单独说明恢复方式。

**执行要求**：

- 接口、字段和数据库结构变更应优先保持过渡期兼容；无法兼容时必须明确维护窗口、阻断范围和发布顺序。
- 发布前必须列出环境配置、密钥来源、依赖服务、Migration 顺序、健康检查和回滚触发条件。
- 发布后必须验证核心接口、关键页面、任务状态、错误日志和监控指标；异常必须进入可感知终态。
- 灰度、分批或一次性发布方式只能依据项目已有发布能力选择，禁止为了规则完整自行假设平台能力。

## 交付要求

最终交付必须说明：

- 实际执行的单元、集成、契约和端到端验证。
- 未执行验证的原因、影响和替代证据。
- Migration、历史数据处理和恢复方案。
- 前端、后端、数据库及异步任务的发布顺序。
- 健康检查、观察指标、失败判定和回滚条件。

## 判断标准

- 每项需求是否能关联到对应测试层和验收结果。
- Migration 是否能解释历史数据、执行影响、重复执行和恢复路径。
- 任一端先发布时，系统是否仍能保持兼容，或已明确维护窗口和阻断范围。
- 用户是否无需查看代码即可知道未验证项、发布风险和回滚条件。
