# 开发工作流

## 任务类型分级

**核心原则**：开始开发前先区分“即时对话型任务”和“正式需求型任务”。只有正式需求型任务进入“构思方案 → 提请审核 → 分解为具体任务”的结构化流程，禁止把所有局部修改都机械升级为需要二次确认的正式方案。

**即时对话型任务**：用户意图明确、范围局部、执行路径清晰的一次性操作，或连续对话中的细节调整，例如调整单个样式值、文案、字段注释或继续执行已确认方案。完成必要查证后直接执行、验证并汇报，不重新发起方案审核。

**正式需求型任务**：涉及需求文档、完整功能、多模块改造、接口契约、多阶段交付、验收标准或发布安排时，执行“构思方案 → 提请审核 → 分解为具体任务”的结构化流程。方案已经由用户明确给出、审核通过或用户明确要求按既定方案继续时，视为方案已确认，不得重复提请审核。

**风险例外**：无论属于哪类任务，涉及删除数据、权限、生产发布、外部消息、不可逆操作或需要新增授权时，仍按对应安全规则单独确认；该确认只针对具体风险，不应将整个即时任务重新包装成正式需求流程。

## 异议与疑问对比门禁

**核心原则**：只有存在真实异议、事实冲突、多个会产生不同结果的可行方案，或缺少会改变实现结果的关键决策时，才请求用户确认。请求确认时必须同时提供对比依据、关键差异、影响范围和明确建议，禁止只把问题原样抛给用户。

**适用场景**：

- 用户描述、需求文档、接口文档、现有代码、设计稿或实际响应之间存在冲突。
- 存在两个及以上会产生不同业务结果、维护成本或交付风险的实现方案。
- 临时方案与正式方案并存，需要用户决定是否接受临时影响、技术债和后续清理成本。
- 缺少的信息会影响接口参数、数据提交、权限、状态流转、页面交互或需求范围。
- AI 无法仅凭已查证事实确定用户真实意图。

**输出要求**：

1. 先列出已确认事实，禁止把推测写成事实。
2. 明确指出异议或疑问发生在哪个页面、功能、字段、接口或操作。
3. 将冲突来源或可选方案并列展示，说明具体差异。
4. 说明各方案对展示、交互、数据、维护成本、联调或交付风险的影响。
5. 必须给出推荐方案及推荐理由，禁止只写“都可以，请选择”。
6. 用户只确认其中一项时，只关闭对应疑问，不得推断其他事项也已确认。
7. 查证后不存在真正的方案差异，或已有唯一明确依据时，应直接执行，不得为了流程形式要求用户确认。

存在两个及以上疑问或需要逐项确认时，使用以下表格：

| 疑问位置 | 依据/方案 A | 依据/方案 B | 关键差异与影响 | 建议 |
| --- | --- | --- | --- | --- |
| 业务位置 | 已确认事实或方案 | 冲突事实或另一方案 | 对展示、提交、交互或维护的影响 | 明确推荐及理由 |

只有一个简单疑问时可以使用简短分点说明，但仍必须包含已确认事实、待确认内容、差异影响和建议。接口联调场景继续使用“联调差异预览格式”，本规则作为所有开发场景的通用确认门禁。

## 需求文档读取规范

**核心原则**：当用户提供、指定或当前项目中存在与本次任务相关的需求文档时，开发前必须先读取需求文档，禁止跳过需求文档直接根据截图、文件名、路径、历史对话或个人推断开始开发。

**适用场景**：

- 用户明确提供 `/api`、`api.md`、`api-docs.md`、`api-word.md` 等本地文档路径
- 用户提供钉钉文档、在线文档、需求链接、工单链接
- 用户当前打开的文件是需求文档，或上下文明确提示“接口文档 / 需求文档在某路径”
- 项目根目录或约定目录下已有与当前任务相关的需求文档

**执行要求**：

1. 开发前必须先读取需求文档内容。
2. 读取后必须以需求文档为主要依据，再结合截图、原型、现有代码和接口文档开发。
3. 如果需求文档无法访问、内容为空、只包含目录或与当前任务无关，必须明确说明读取结果，不能假装已经掌握需求。
4. 禁止在未读取需求文档的情况下，直接进入编码、mock、字段占位或路由/API 生成。
5. 如果需求文档与用户口头描述冲突，必须先指出冲突并让用户确认，以用户最新确认结果为准。

## 需求文档与接口文档优先级

**核心原则**：联调时必须先区分“产品表现”和“数据契约”；页面表现以需求文档 / 原型 / 用户最新说明为准，接口字段链路以接口文档 / 抓包 / 后端确认为准。

**执行要求**：

1. **页面表现按需求文档**：页面展示、字段标题、按钮文案、交互流程、模块名称、字段是否展示、展示顺序，优先以需求文档 / 原型 / 用户最新说明为准。
2. **数据契约按接口文档**：接口路径、请求参数名、响应字段名、字段类型、枚举真实值、分页结构、提交结构，必须以接口文档 / 抓包 / 后端确认为准。
3. **接口说明不覆盖页面文案**：接口字段说明只能帮助理解字段含义，不能直接覆盖需求文档中的页面文案。例如接口字段名或说明是“备注”，但需求图写“等级说明”，页面标题应使用需求文档文案，代码绑定字段仍使用接口字段名。
4. **需求字段缺接口时显性处理**：需求要求展示但接口未提供字段时，不能用相似接口或其他字段硬凑；应保留需求位置，标记 `TODO无此联调字段_用途描述`，并反馈后端补字段或确认数据来源。
5. **动态文案缺字段禁止改语义**：需求文案、确认弹窗、提示语或按钮说明中包含动态占位（如数量、名称、金额、状态等）时，如果接口文档、抓包或后端未确认对应字段，禁止为了实现方便改成静态泛化文案、删除占位、替换成相近含义文案或用其他字段硬凑。必须先查询目标接口字段；查不到时保留原需求文案结构和占位位置，使用 `TODO无此联调字段_用途描述` 显性标记，或阻断操作并反馈缺少字段，等待后端补字段或用户确认降级方案。

```ts
// ❌ 禁止 - 因为拿不到数量字段，就把需求文案改成泛化文案
confirm('确认要处理本次全部记录吗？')

// ✅ 正确 - 已确认接口返回 count 字段时，保留需求中的数量语义
confirm(`确认要处理本次${count}条记录吗？`)

// ✅ 正确 - 查不到数量字段时，显性暴露缺口，不能静默改文案
const TODO无此联调字段_本次数量 = response.TODO无此联调字段_本次数量
```

6. **冲突必须及时沟通，禁止自行消化**：需求文档和接口文档冲突时，必须在进入方案或编码前明确指出冲突点。展示文案、交互和展示顺序冲突按需求优先；字段名、类型和提交结构冲突按接口 / 抓包优先。只有“页面文案”和“接口字段名”这类可明确分层的差异，才允许按分层原则处理并在产物中说明；如果冲突会影响页面是否改、字段是否传、下拉是否展示、接口是否调用、范围是否包含，必须停下来询问用户确认。禁止先按其中一个来源改代码，再在最终回复中补充说明。

## 智能工作流调用机制

为了提升开发效率并防止因用户遗忘而导致的代码不规范，AI 助手需根据上下文**主动调用**相关工作流：

- **Figma 还原场景**：当用户的请求中包含 Figma 设计稿截图，或提及 Figma 的样式属性面板参数（如 `background: #xxx`, `font-style: 65 Medium`、各种绝对坐标间距等）时，无论用户是否显式输入了工作流指令，AI 都**必须自行调用 `@[/base.figma-to-code]` 工作流**，并以此作为后续 CSS 样式还原与属性智能映射的绝对准则。

## 生效规则显性告知门禁

**核心原则**：当全局规则、项目规则或工作流会实质改变本次实现选择、阻止常见方案、增加额外步骤或改变交付边界时，AI 必须在实施前主动说明生效约束及正确路径；禁止依赖用户自行翻阅规则后才发现实现被限制。

**执行要求**：

1. 开发前完成适用规则识别后，只列出真正影响本次实现的约束，不机械复述全部通用规则。
2. 告知内容必须包含规则名称或约束主题、触发依据、被限制的行为、对本次实现的影响和正确实现路径。
3. 开发过程中才发现新的实质性约束时，必须在应用该约束前补充告知；禁止先静默改变方案，再在最终回复中补充规则理由。
4. 规则依赖的项目事实与源码、配置、文档或实际运行结果不一致时，必须暂停套用旧结论，指出规则可能失效并进入规则更新或事实确认流程。
5. 不影响实现选择的基础格式、命名或常规检查可以在最终自检中统一说明，避免每轮输出大量规则噪音。
6. 最终交付必须说明本次有哪些规则实际改变了实现路径；没有时明确“无实质性规则限制”。

**告知格式**：

```md
本次生效约束：
- 规则名称 / 约束主题：
- 触发依据：
- 限制内容：
- 对本次实现的影响：
- 正确实现路径：
```

**禁止行为**：

- 禁止使用未告知的规则静默拒绝用户方案、删除需求、改变数据链路或增加兼容逻辑。
- 禁止只说“按全局规则处理”，却不说明具体限制和正确路径。
- 禁止把规则告知变成二次确认；已有唯一正确路径时，告知后直接执行，只有存在真实冲突或关键决策时才请求确认。

## 可复用问题识别与经验沉淀门禁

**核心原则**：执行过程中发现已经查明原因、解决方式可复现且可能再次发生的问题时，必须优先复用已有经验；尚未沉淀时，应向用户显性提出经验沉淀候选。禁止让同类问题在后续任务中反复从零排查，也禁止未经用户确认直接修改规则。

**触发条件**：

- 相同原因或解决方式已经出现两次及以上。
- 虽然首次出现，但排查成本较高、再次发生概率较高，且解决方式已经验证。
- 当前问题暴露出全局规则、项目规则、工作流或工具说明存在缺口、错误或过期事实。
- 已有经验能够明显减少后续失败尝试、无效命令、重复查证或用户沟通。

**不适用场景**：

- 根因尚未确认，解决方式只是猜测。
- 一次性业务 Bug、临时网络波动或不可复现的外部异常。
- 仅适用于当前机器、当前版本或当前临时环境，但尚未提炼出稳定边界。
- 已有规则已经完整覆盖，当前只是正常应用。

**执行要求**：

1. 遇到问题时，先搜索现有全局规则、项目规则、工作流和相关历史，确认是否已有解决方式。
2. 已有经验时，核对当前前提仍然成立后直接复用；如果该经验实质改变执行路径，应告诉用户本次复用了什么经验以及依据。
3. 没有已有经验时，先完成当前问题排查；确认根因和有效解法后，再判断是否满足沉淀条件。
4. 满足条件时，向用户输出“经验沉淀候选”，说明问题、根因、已验证解法、适用范围、失效信号和建议归属。
5. 归属必须按稳定边界判断：
   - 跨项目原则进入全局规则；
   - 项目事实进入项目规则；
   - 操作步骤进入对应工作流或引用文件；
   - 单机环境问题进入本地诊断记录，不写成全局事实。
6. 未经用户确认，不得直接修改规则或工作流；用户确认后使用 `base-update-rules` 完成源文件修改、同步和验证。
7. 后续复用时发现环境、版本或源码已经变化，必须说明旧经验可能失效并重新验证，禁止机械套用。

**告知格式**：

```md
经验沉淀候选：
- 问题：
- 已验证根因：
- 可复用解法：
- 适用范围：
- 失效信号：
- 建议归属：
- 当前状态：建议沉淀 / 暂不沉淀
```

## 代码生成后全局规范自检门禁

**核心原则**：每次生成、修改或替换代码后，必须先按全局规则做规范自检，再给出最终交付；禁止只做格式化、语法或构建检查，而漏掉字段依据、场景边界、发散范围、兜底说明等全局规范检查。

**适用场景**：

- 新增或修改业务代码、页面、组件、接口、表格列、搜索项、弹窗、样式、工具函数、Hook。
- 根据需求文档、接口文档、截图、用户口头说明进行联调或改造。
- 修复 Bug 时改动了业务判断、字段映射、枚举分支、兜底逻辑或公共组件调用。

**执行要求**：

1. **开发前后双重规则认证**：开始编码前必须先根据任务类型确定本次适用的全局规则、项目规则和工作流，例如需求读取、禁止发散、组件函数查证、样式结构、联调、权限或 Git 规则；代码修改完成后，必须再按同一批规则回看最终 diff 做二次复查。禁止只在开发前口头遵守规则，交付前只跑技术检查而不复查规则。
2. **字段依据检查**：新增或调整的接口字段、表格列、搜索项、枚举值、权限标识、路由参数、导入路径，必须能对应到用户要求、需求文档、接口文档、抓包、项目已有代码或后端确认；缺依据时必须使用 `TODO无此联调字段_用途描述` 或先向用户确认。
3. **场景边界检查**：遇到 `scene`、`type`、`status`、`mode`、`source` 等业务枚举或场景字段时，必须显式判断每个已知业务场景；禁止只判断一个场景，再把剩余分支默认当成另一个具体场景。
4. **需求范围检查**：回看本次 diff，确认没有顺手新增需求外字段、删除旧展示、重构旧逻辑、改变旧默认行为或扩大业务影响范围。
5. **全局规则交叉检查**：根据本次改动内容，主动对照相关全局规则，包括但不限于禁止发散、组件函数查证、枚举分支、兜底值、公共能力复用、注释、样式结构、接口联调和格式化规则。
6. **待确认与兜底检查**：本次存在临时占位、缺字段、兼容旧字段、展示占位、空 Options、默认值或异常兜底时，必须在最终回复中说明位置、依据、影响范围和后续待确认事项。
7. **技术检查不能替代规范检查**：`git diff --check`、SFC 解析、lint、format、build 等只证明技术层面可运行，不能替代全局规范自检。

**交付要求**：

- 简单改动可以用一句话说明“已做全局规范自检，无额外发散 / 无待确认项”。
- 涉及接口、枚举、多场景共用组件、字段映射或兜底逻辑时，最终回复必须列出关键自检结果。
- 如果发现规范风险，必须先修正；不能修正时，必须明确列为待确认项，禁止静默交付。

**检查清单**：

```md
全局规范自检：
- 规则双重认证：开发前已确认适用规则 / 开发后已按同一批规则复查最终 diff
- 字段依据：已确认 / 待确认项如下
- 场景边界：已显式判断 / 不涉及
- 需求范围：未扩大 / 存在范围变更并已说明
- 兜底逻辑：无 / 已列出
- 技术检查：已执行 xxx / 未执行原因
```

**禁止行为**：

- 禁止开发前提到规则，但交付前不按最终 diff 做规则复查；也禁止用 SFC 编译、lint、build、`git diff --check` 代替开发后规则复查。
- 禁止只回复“已通过格式化 / 已通过编译”，但没有检查字段依据和场景边界。
- 禁止等用户指出后才补做枚举分支、字段依据、兜底说明等全局规范检查。
- 禁止把“当前项目没报错”当作符合全局规范的依据。

## Git 操作规范

**核心原则**：**绝对禁止在未受明确指令要求的情况下，直接帮用户进行代码的缓存/暂存（add）、提交（commit）或推送（push）操作。用户明确要求“提交 / 提交推送”时，默认按暂存区是否已有内容确定提交范围；用户另行指定分批提交范围时，以用户指令为准。**

- `git status`、`git diff`、`git log` 等**纯只读操作**：允许自行执行来分析上下文。
- `git add`：**绝对禁止**在修改完代码后擅自执行任何缓存/暂存操作。只有用户主动提出暂存，或用户明确要求提交且当前暂存区为空时，才允许执行。
- `git restore --staged` / `git reset HEAD` / 取消暂存：**绝对禁止擅自执行**。暂存区可能是用户用于对比、分批提交或保存工作边界的状态，AI 不得为了"整理状态""避免 staged 变更"或"方便查看 diff"主动取消缓存。只有用户明确提出"取消暂存 / 撤出缓存 / unstage"时才允许执行。
- 遇到已有暂存内容时，必须保持暂存区原状。需要分析变更时，只允许使用 `git status`、`git diff`、`git diff --cached` 等只读命令分别查看工作区和暂存区差异，并在回复中说明哪些是已暂存、哪些是未暂存。
- 用户明确要求“提交 / 提交推送”，且暂存区已有内容时，必须只提交当前暂存区内容；禁止补充暂存任何未暂存或未跟踪文件。
- 用户明确要求“提交 / 提交推送”，且暂存区没有内容时，默认暂存并提交当前仓库全部变更，包括修改、删除和未跟踪文件。
- 用户明确要求按文件、功能或批次分批提交时，以用户指定范围为最高优先级；只暂存和提交该范围，不适用上述默认范围。
- 提交信息、差异核对和调试代码检查必须基于最终暂存区；仓库没有任何变更时，直接说明无可提交内容，禁止创建空提交。
- `git commit`：**绝对禁止擅自执行**，必须等用户确认变更内容并下达明确指令后才可执行。
- `git push`：**必须由用户明确提出后**才可执行。
- 服务器部署相关（Docker 构建、PM2 重启等）：仅允许在代码已经获得批准推送后才能自动执行相应构建。
