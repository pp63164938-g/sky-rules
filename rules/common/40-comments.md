# 代码清理规范

修改代码时同步清理废弃资源：

1. **替换 i18n 翻译 key 时**：同时删除被替换的旧 key
2. **删除/修改组件引用时**：检查被引用的资源（翻译、图标、样式）是否还有其他地方使用，没有则删除
3. **修改完成后**：使用搜索工具确认旧代码/翻译确实无引用

**目的**：避免遗留无用代码和翻译，保持代码库整洁。

# 注释规范

**Vue 组件/弹窗必须包含业务说明注释**：

**适用场景**：Vue 模板结构、业务组件、函数 / 变量 / 类型、条件分支、兜底值、数据转换、复杂 Map / Record / 缓存结构、样式块。

**硬性红线**：注释必须贴近代码并说明业务含义或分支原因；禁止空泛注释、远离代码的规则堆叠、无注释堆复杂结构。

- **格式**：在组件最外层节点内部（如 `<template>` 开头处）或 `export default` 上方，必须添加明确的中文业务名称或功能说明注释。
- **目的**：保持极高的可读性，让接手人员无需阅读内部实现细节，也能快速明确该组件的业务用途。
- **代码示例**：
  ```vue
  <template>
    <!-- 预约活动报名提醒弹窗 -->
    <WcDialog :visible="visible"></WcDialog>
  </template>
  ```
  或
  ```javascript
  /**
   * 预约报名弹窗
   * 业务场景：点击 Hero 横幅区的“立即预约”时弹出
   */
  export default { ... }
  ```

**变量名、函数名使用 JSDoc 注释**：

- **格式**：使用 `/** xxx */` 的方式添加注释
- **适用场景**：变量声明、函数定义、类型定义、接口属性（包括函数内部的变量定义）
- **目的**：鼠标移入时可以看到描述，提升代码可读性和开发体验
- 函数内部通过 `const` / `let` 声明、且后续会被 `if` 判断、接口调用、弹窗确认、提交参数、组件 props 或模板引用的业务变量，也必须在声明上方使用 JSDoc 注释说明业务含义。
- 禁止只给函数、表单字段或顶部状态加注释，而让内部承载关键业务结果的中间变量裸露。
- 极短作用域且无业务含义的临时变量可不机械注释；但承载业务判断、展示文案、接口参数、权限状态、提交数据的变量必须注释。

**代码行内注释**：

- **格式**：使用 `// xxx` 的方式添加注释
- **适用场景**：函数内部的逻辑说明、步骤解释、条件分支说明
- **目的**：解释代码执行逻辑，便于阅读理解

**注释内容边界**：

- 代码注释只服务后续维护者理解业务含义、数据来源和分支原因，并且只描述当前代码需要长期维持的业务事实；禁止记录任务执行过程。
- 禁止将 AI 与用户的交流留痕写进业务代码，包括“用户已确认”“按本轮沟通”“参考本次截图”“查证后发现组件默认支持”“为了遵守规则”等过程性说明。
- 需求澄清、用户确认、方案取舍、组件 / Hook 默认能力查证和代码审查结论，应记录在对话、需求决策台账、方案文档或交付说明中。如果沟通结论形成代码无法自行表达、且需要长期维护的业务约束，必须改写成不包含沟通过程的业务事实后再添加注释。
- 如果组件类型、Prop、校验规则、变量命名或代码结构已经完整表达约束，禁止为了证明 AI 已理解、已查证或已执行而重复添加注释。
- 禁止写“禁止使用 xxx”“按规则 xxx”“避免违反 xxx”这类给 AI 自己看的规则执行说明。
- 禁止把本次排错、复盘、审查提醒、工具判断过程写成代码注释；这些内容应放在对话回复、方案文档或规则复盘中。
- 禁止用注释替代最终回复中的发散点、待确认项或兜底说明；代码注释和用户交付说明是两件事。
- 禁止把本次改动交代、字段收口说明、方案取舍过程写进代码注释。例如“统一使用同一接口字段”“已确认业务类型都走该字段”“兼容新旧字段后收口”“按审查意见调整”。这些是给用户的交付说明，只能写在对话回复里。
- 判断标准：不看本次对话，只看注释，能否把它理解成当前代码需要长期维持的业务事实；如果只能理解成“这次为什么这么改”，就必须删除，或改写成不包含改动过程的业务事实。
- 字段归并、函数抽取、Options 复用等代码结构变化，禁止再用注释复述改动过程。代码能看出来的，注释不要再讲一遍。
- **正式注释与临时预留说明必须分离**：JSDoc、字段说明、函数说明、模板业务注释等正式注释只说明稳定业务含义，例如“业务字段”“操作入口”“数据结构”。待联调原因、后端缺口、临时值来源、联调时删除 / 替换范围等临时说明，必须放在 `@todo-start` / `@mock-start` 标记行、独立 TODO 字段名或最终交付说明中。禁止把 `TODO待联调_` / `TODO无此联调字段_`、“最终以后端为准”、“待后端确认”等内容混进正式 JSDoc，导致联调时还要判断正式注释是否需要修改。
- 注释应写业务事实，例如接口字段来源、业务分支含义、特殊兜底原因。

```ts
// ❌ 禁止 - 向用户交代本次字段收口
/** 已确认业务类型统一使用详情字段 xxx */

// ✅ 正确 - 只说明长期业务事实
/** 详情 xxx，来自接口字段 xxx */
```

```ts
// ❌ 禁止 - 共用同一结果时，注释写成改动说明
// 人工处理、自动处理、定时处理（mode = 1、2、3）：统一使用同一接口字段。

// ✅ 正确 - 共用同一结果时，只写业务结果
// 人工处理、自动处理、定时处理（mode = 1、2、3）：展示业务字段。
```

```javascript

giftAmount: ''

/** 获取绑定赠送金额 */
async fetchGiftAmount() {
    // 先校验参数
    if (!this.userId) return

    /** 接口响应数据 */
    const res = await api.getGiftAmount()
    this.giftAmount = res.data
}
```

```javascript
// ❌ 禁止 - 把规则提醒写进业务代码
// 使用 code 判断，禁止用 name 文案做业务判断
return optionItem.value === TARGET_SCENE_CODE

// ✅ 正确 - 只说明当前业务事实
// 目标场景：接口 code = TARGET_SCENE_CODE

```

**注释位置与内容分层规范**：

**核心原则**：注释应贴近它解释的代码。顶部/块级注释只说明“这是什么”，具体分支、状态判断、兜底逻辑的业务原因，应写在对应判断过程里，避免把细节规则堆在远离代码的顶部注释中。

**分层要求**：

- **顶部注释 / JSDoc**：说明变量、函数、组件、模块的业务身份，即“这是什么”。
- **过程注释 / 行内注释**：说明关键判断、特殊分支、兜底逻辑的业务原因，即“为什么这样做”。
- **禁止规则漂移**：不要在函数顶部写一大段具体业务规则，而实际判断只留一行代码；规则变化时这类注释最容易过期。
- **注释紧贴代码**：如果注释解释的是某个 `if`、`return`、`v-if`、兜底值或特殊状态，注释必须放在该代码附近。
- **函数注释不替代过程注释**：函数名或 JSDoc 只说明函数用途；当函数内部存在关键条件分支、接口选择、跨系统调用、数据组装、兜底返回等逻辑时，必须在对应代码附近添加过程注释，说明该分支为什么这样处理。
- **字段级处理细节必须贴近字段**：函数 / 变量顶部注释只描述整体业务身份、整体输入输出或稳定职责；字段转换、接口格式、兼容逻辑、兜底策略、特殊枚举处理等细节，必须写在对应赋值、判断、`map`、`return` 分支附近。禁止把多个字段级细节堆到函数顶部，导致后续拓展时无法判断每条说明对应哪一段逻辑。
- **过程注释必须贴近判断**：不要只在函数顶部写“获取业务员下拉”之类的总说明，而让内部 `if`、`return []`、接口选择逻辑没有任何解释。
- **if 分支说明写在 if 上方**：当注释解释的是某个 `if` 分支代表的业务场景、接口来源、枚举含义或进入该分支的原因时，注释应紧贴写在 `if` 语句上一行，而不是写在 `{}` 内第一行。
- **枚举分支注释聚焦当前命中场景**：当分支条件依赖枚举、状态码或类型字段时，使用“真实业务名称（字段 = 枚举值）：处理原因或业务结果”的短句，只说明当前分支为什么这样处理。完整枚举表、字段类型及其他分支含义应统一放在类型、Options、常量或接口契约处，禁止在单个分支注释中重复展开。
- 多个枚举值共用同一结果时，注释只写业务结果；禁止写成“统一使用同一字段”“已收口”等本次改动交代。
- **枚举默认值注释只说明实际兜底项**：当 `??`、`||`、默认参数或初始化赋值只为某个枚举字段提供一个已确认默认值时，注释只说明兜底触发场景、默认项的真实业务名称和具体值，不展开完整枚举表、其他枚举项或字段类型。完整枚举定义应继续归属于类型、Options、常量或接口契约。
- **多个枚举分支按处理结果组织**：不同枚举值对应不同业务结果时，每个实际存在的分支分别说明；多个枚举值共用同一结果时，合并说明命中范围；未知值存在兜底分支时，明确说明真实兜底行为。禁止为了注释完整而补写代码中不存在的业务分支。
- **禁止使用占位业务名称**：正式代码注释必须使用维护者可直接理解的真实业务含义，禁止使用“类型A”“状态B”“场景一”等需要反查的占位名称。规则文档中的抽象示例也应使用“人工处理”“自动处理”等可直接理解的通用语义。
- **分支内部步骤写在分支内部**：当注释解释的是进入分支后的某个具体操作、转换、兜底或副作用时，注释应写在分支内部对应代码附近。
- **多分支 / 多返回过程必须逐段说明**：当函数内部存在连续 `if`、多个 `return`、表格合并、数据过滤、状态转换、参数组装等多步骤过程时，禁止只给函数名或 JSDoc 写总说明。必须在每个关键分支、关键返回值或关键步骤附近添加过程注释，说明该分支对应的业务表现、输入输出或副作用，方便后续维护者不用反推代码意图。
- **内联判断必须说明关键分支含义**：当三元表达式、布尔表达式或内联条件同时承担业务判断和兜底含义时，必须在表达式附近写明每个关键分支的业务含义，尤其要说明 `undefined`、空数组、空字符串、`false` 等值代表“无规则 / 不限制 / 异常 / 兼容”等哪一种场景，禁止只靠表达式让读者猜。
- **复杂数据结构变量必须说明功能、结构和关键含义**：当变量承载 Map/Record/缓存/索引表/分组结果/多状态集合等复杂结构，或会被多个步骤复用时，必须在声明处使用 JSDoc 写明业务用途、数据结构和关键值含义。数据结构应说明 key/value 代表什么，例如 `{ 收件/抄送邮箱: 允许发件邮箱交集 }`；关键值含义仅在存在空值、空数组、枚举值、特殊状态时补充，例如 `undefined = 无规则`、`[] = 有规则但无共同可用数据`。如果只是一次性局部临时变量，保持简洁即可，避免机械注释。
- **复杂函数注释必须说明关键入参和返回含义**：当函数包含布尔开关、枚举参数、可选参数、联合返回值，或 `undefined/null/[]` 等具有业务含义的返回值，并会影响 UI 状态、提交拦截、缓存写入等关键流程时，必须在函数 JSDoc 中说明关键入参含义和返回值含义。不要机械给所有简单函数补 `@param/@returns`；只有参数或返回值脱离实现过程不易理解时才补充。

```ts
// ❌ 不推荐 - 在单个分支中重复字段类型和整套枚举
// 处理模式 mode 为 String（'manual'=人工处理，'auto'=自动处理）；人工处理需要保留确认步骤。
if (mode === 'manual') {
    retainConfirmation()
}

// ✅ 推荐 - 每个实际分支只说明自己的业务场景、真实值和处理原因
// 人工处理（mode = 'manual'）：保留人工确认步骤。
if (mode === 'manual') {
    retainConfirmation()
}

// 自动处理（mode = 'auto'）：直接进入执行流程。
if (mode === 'auto') {
    executeAutomatically()
}

// 未识别处理模式：不套用任何已知流程。
return
```

```ts
// ❌ 不推荐 - 当前代码只兜底人工处理，却展开字段类型和全部枚举
// 处理方式为 string：人工处理（mode = 'manual'）、自动处理（mode = 'auto'）；历史数据未返回时默认人工处理。
mode: data.mode ?? 'manual'

// ✅ 推荐 - 只说明当前代码实际使用的默认枚举项
// 历史数据未返回处理方式时，按人工处理（mode = 'manual'）回显。
mode: data.mode ?? 'manual'
```

**转换类注释规范**：

- **转换说明集中归属**：凡代码改变数据的结构、字段集合、层级、类型、格式、单位、精度、序列化形式、值集合或业务语义，都属于数据转换。原始格式、最终格式和具体示例必须由承载实际转换职责的函数、computed、派生变量或局部表达式集中说明；禁止只写“转换数据”“格式化列表”“处理接口参数”等无法看出转换结果的空泛说明。
- **抽象转换说明允许保留，但必须给出具体示例**：类型名、占位字段、抽象路径或概括性描述可以保留，用于说明通用规则；同时必须补充最小具体输入 / 输出示例。例如 `string[][] -> string[]` 说明结构，`[['1', '2']] -> ['1,2']` 说明实际值变化，两者共同表达路径分隔、层级保留或字段裁剪规则。示例使用抽象业务字段和普通测试值，禁止使用真实生产数据。
- **转换说明优先使用 JSDoc**：函数、computed、派生变量或独立转换结果承载完整转换职责时，应使用 `/** */` JSDoc 说明。字段赋值、请求参数、map 回调等局部转换，应使用贴近对应代码的行内注释，避免把字段细节堆到函数顶部。
- **抽象转换函数由函数注释承担细节**：转换已抽成具名函数时，函数 JSDoc 可以保留抽象的转换两端说明，但必须同时给出具体示例；调用处只说明当前业务用途和转换动作，例如“筛选值转换为接口路径”，禁止重复数组结构、分隔符、字段路径或示例。后续格式变化时，只修改转换函数注释。
- **简单转换使用简洁 JSDoc**：输入、输出和转换结果能够通过一句话完整表达，且不存在多数据源、复杂分支或特殊业务语义时，使用一行 JSDoc 写明 `原始格式 -> 最终格式` 和具体示例即可，不要求机械补充 `@param`、`@returns`。
- **复杂转换使用标准 JSDoc 标签**：存在多个输入参数、嵌套结构、树 / Map / Record 转换、多步骤处理、业务分支、字段裁剪或重命名、接口契约转换、单位 / 精度处理、空值语义变化，或仅看函数签名无法理解结果时，必须使用标准 JSDoc：
  - 使用 `@param` 分别说明每个输入参数的来源、作用和原始结构。
  - 使用 `@returns` 说明最终结构、返回语义和特殊值含义。
  - 当参数与返回值类型相同但内容规则发生变化，或仅靠 `@param` / `@returns` 仍难以理解时，使用 `@example` 展示最小前后结果；转换说明包含抽象结构时必须使用具体示例消除歧义。
  - 禁止在 JSDoc 正文中自造“输入：”“对照：”“输出：”等格式替代标准标签。
- **多输入转换禁止歧义表达**：注释中的 `+`、`合并`、`拼接`等词必须与代码真实操作一致。多个参数只是用于比较、识别差异或提供转换依据时，禁止写成 `输入A + 输入B -> 输出`。应通过多个 `@param` 分别说明参数作用，再通过 `@returns` 和必要的 `@example` 说明结果。
- **字段级转换必须贴近字段**：一个函数包含多项独立字段转换时，每项转换都必须在对应赋值、map、return 或请求字段附近说明转换动作和业务用途。字段直接实现转换、没有调用已说明清楚的具名转换函数时，字段注释必须自行说明转换两端并给出具体示例。
- **避免重复注释同一转换**：同一逻辑转换已经由所属函数、computed 或派生变量的 JSDoc 完整说明时，调用处不重复格式和示例，只保留当前业务动作。内部存在独立字段格式、单位、精度、序列化或空值语义转换时，仍须单独说明。
- **非运行时转换不按数据转换处理**：TypeScript 类型标注、`as Xxx` 类型断言，以及不改变结构和业务语义的直接透传、同结构 clone / spread，不属于运行时数据转换，无需编写转换注释。

- **注释表达优先可扫描**：注释不是越多越好。已有注释难读时，应优先优化原注释的表达，而不是额外新增一行解释。注释推荐使用“对象 / 来源：含义”的短句结构，例如“业务对象回显：同步选中项”“回显字段：业务对象编号”“接口结果：业务对象选中项”。只有同一段代码里确实需要强区分多个来源时，才使用少量视觉标签；禁止为了制造层次感滥用 `【】`、长破折号、括号套括号或多行说明，导致注释比代码更费劲。

**注释可扫描示例**：

```ts
// ❌ 不推荐 - 信息堆在一行里，读者难区分对象、来源和用途
/** 接口返回的关联业务对象下拉选中项 **/

// ✅ 推荐 - 用“来源：含义”保持短句可扫描
/** 接口结果：业务对象选中项 **/

// ✅ 推荐 - 函数注释说明业务动作
/** 业务对象回显：同步选中项 **/

// ✅ 推荐 - TODO 行只说明联调替换点
// @todo-start 联调时替换本字段：业务对象回显查询参数
```

**注释一次性交付门禁**：

- 开发或调整业务函数后，交付前必须主动回看本次新增 / 修改的函数，先判断哪些函数需要过程注释，再一次性补齐，禁止等用户逐个追问后才补。
- 对包含 `if`、`else if`、`switch`、三元表达式或提前 `return` 的业务函数，交付前必须逐个盘点实际分支；每个会改变业务结果的分支都必须在对应语句上一行说明业务原因，未知 / 异常兜底也必须单独说明。纯结构性早退且不承载业务语义的判断可不机械补注释。
- 需要补过程注释的函数包括：
  - 会修改多个响应式状态、表单字段、缓存快照或查询条件的函数；
  - 会触发表单校验、清理校验、弹窗关闭、刷新列表、路由跳转等副作用的函数；
  - 会调用接口并把接口结果映射成页面数据、表格行、详情回显或提交参数的函数；
  - 会按业务类型、状态、报表类型、来源等字段切换展示列、接口参数、计算口径或文案的函数；
  - 会计算展示派生值、比对百分比、金额 / 数量 / 比率等容易被误解来源的函数；
  - 会处理空值、缺字段、兜底、TODO、Mock 或待联调数据的函数。
- 不需要机械补复杂 JSDoc 的函数包括：
  - 输入输出和转换规则能够通过一句简洁 JSDoc 完整表达的简单转换函数；
  - 简单单字段 getter、同结构 clone / spread、直接透传和 TypeScript 类型断言；
  - 不存在业务分支、副作用、接口映射、派生计算或数据转换的简单函数。
- 简单转换可以不写 `@param`、`@returns`，但仍必须通过简洁 JSDoc 说明转换两端；复杂转换必须按“转换类注释规范”使用标准 JSDoc 标签。
- 过程注释必须贴近对应赋值、判断、接口映射、派生计算或副作用；禁止只在函数顶部写一段概括后让关键代码裸露。
- 如果某个函数被判断为“不需要过程注释”，最终自检时必须能说明原因：它是简单取值、无运行时转换或无业务副作用，而不是遗漏。

**判断标准**：

- 注释读起来像“字段/函数名称补充” → 放顶部或 JSDoc。
- 注释读起来像“这个分支为什么要这样处理” → 放到对应分支内部。
- 注释如果离开对应代码仍无法判断是否过期 → 应移动到具体代码附近。

**HTML/Vue 模板注释规范**：

**核心原则**：对于复杂的组件结构（如卡片、列表项、左右布局容器等），**必须为关键的 HTML 节点添加包裹式或起手式注释**，以清晰标明业务含义，与 CSS 样式全覆盖注释相呼应。

**强制要求**：

- 严禁在没有任何注释的情况下连续堆砌大量的 `<div>` 等无语义标签。
- 注释必须说明“这是什么业务模块”（例如：`<!-- 战绩详情数据列 -->`、`<!-- 头部左侧：汇总场次与日期 -->`）。
- 尤其是使用了 Flex/Grid 布局的大型结构骨架，其主要父容器必须拥有明确的业务说明注释。
- 当页面 / 弹窗已经拆成多个页面专属业务子组件后，主入口模板仍必须为关键子组件和布局容器添加起手式注释，说明该子组件承载的业务区块。
- 子组件名不能完全替代业务注释；禁止主入口只连续堆叠多个 `<Xxx />`，让读者必须逐个打开子组件才能理解页面结构。
- 注释粒度以业务区块和布局骨架为单位，例如头部、主内容、侧边栏、底部操作、左侧配置区、右侧预览区；不要给普通字段、普通按钮、单个简单组件机械补注释。
- 如果子组件名称已经非常清楚，注释应补充“位置 + 业务职责”，不要重复组件名本身。

**目的**：提高模板的结构可读性，防漏、防错，方便接手人员能够做到“仅看模板注释就能秒懂业务布局结构”。

# 文件头部注释规范

**核心原则**：所有代码文件顶部需添加功能描述注释，说明该文件是哪个页面或功能。

**格式要求**：

| 文件类型   | 注释格式            | 示例                         |
| ---------- | ------------------- | ---------------------------- |
| .vue       | `<!-- 功能描述 -->` | `<!-- 提现/充值抽屉组件 -->` |
| .js/.ts    | `/** 功能描述 */`   | `/** 公共接口定义 */`        |
| .jsx/.tsx  | `/** 功能描述 */`   | `/** 用户列表页面 */`        |
| .scss/.css | `/* 功能描述 */`    | `/* 全局公共样式 */`         |

**注意事项**：

- 注释放在文件最顶部（第一行）
- 描述应简洁明了，说明文件的用途或所属功能模块
- 不要放文件路径，而是描述功能
