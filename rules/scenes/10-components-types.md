# 组件 / 函数 / Hook 使用前查证规范

**核心原则**：使用任何非当前文件内定义的组件、函数、Hook、工具方法时，禁止按原生组件、个人经验或其他页面用法盲目推断。必须先查源码、类型定义、文档或项目已有用法，并以源码/类型定义为最终依据，确认可用参数、合法值、默认值、返回值和副作用后再编写配置。

**适用场景**：首次使用或首次传入不熟悉参数的项目组件、业务函数、Hook、工具方法、UI 库二次封装。

**硬性红线**：其他页面用法只能作为线索，不能替代源码 / 类型定义确认；查不到定义或合法值时，必须暂停确认，不能靠经验补配置。

**适用范围**：

- 项目二次封装组件：`com-*` / `sky-*` / `business-*` 等
- 项目业务组件：页面内弹窗、抽屉、选择器、表格、表单项等
- 项目 Hooks / Composables：如 `useTable`、`useForm`、`useSimpleSelecter`
- 工具函数 / 业务函数：格式化、枚举转换、请求封装、表单工具等
- UI 库组件在当前项目中的封装用法

**使用前必须确认**：

1. **参数 / Props 定义**：是否真的支持该配置，类型是什么
2. **可用值范围**：枚举、模式、布尔开关、数字阈值分别允许哪些值
3. **默认值**：是否已经内置默认值，避免重复传入默认配置
4. **返回值结构**：数组解构、对象字段、回调参数分别是什么
5. **副作用和触发时机**：是否会自动请求、自动校验、自动清空、自动回填
6. **项目已有用法**：只能作为线索，不能替代源码/类型定义确认

**执行强度补充**：

- 这不是页面生成专属规则；日常开发、Bug 修复、联调、样式调整、重构局部代码时同样适用。
- 只要使用非当前文件内定义的组件、函数、Hook 或工具方法，并传入 props、options、参数、插槽、回调等配置，就必须回到源码、类型定义或官方/项目文档确认。
- “以前用过”“别的页面这样写过”“需求文档写了限制值”都不能替代源码/类型查证；项目已有用法只能作为定位线索。
- 对于组件或函数已经内置的默认值、默认行为、自动校验、自动请求、自动清空、自动回填等能力，禁止重复声明同等配置。
- 需求值与默认值一致时不传；需求值不同于默认值、或确实需要改变默认行为时，才显式传参，并确保该参数真实存在且语义正确。

## 公共能力复用优先级规范

**核心原则**：凡是具备跨页面、跨模块复用可能的基础能力，必须优先搜索并复用已引入的成熟公共库，其次复用项目公共能力，最后才允许局部实现；禁止在业务文件中临时手写一份语义相同的工具逻辑。

**复用优先级**：

1. **已引入的成熟公共库**：优先使用项目依赖中已有的稳定库能力，例如 `class-validator`、`lodash-es` 这类已在项目中使用的公共库；适用于空值判断、类型判断、防抖节流、深拷贝、集合处理等通用逻辑。
2. **项目公共能力**：当公共库能力不承载项目约定，或项目已有统一业务语义时，再使用项目公共工具函数、Hook、基础组件封装。
3. **局部实现**：只有成熟公共库和项目公共能力都不匹配当前语义，或当前逻辑明确是一次性业务规则时，才允许局部实现。

**执行要求**：

- 动手前先用 `rg` 搜索同类能力：优先查项目已引入公共库的用法，再查项目公共工具 / Hook / 组件，最后查同类业务页面。
- 动手前必须先查看当前项目 `package.json` 的 `dependencies` / `devDependencies`，确认项目已经引入哪些通用库；再用 `rg` 搜索这些库在项目中的既有用法，例如日期、金额精度、集合处理、空值判断、深拷贝、防抖节流、唯一 ID、URL / Query 处理等。
- 对于日期时间、金额 / 小数精度、深拷贝、防抖节流、集合对象处理、唯一 ID、校验判断等高频通用能力，如果项目已安装并已有成熟库用法，禁止优先手写等价逻辑。
- 简单原生表达式可以保留，例如 `array.map/filter/includes`、普通字符串拼接、简单布尔判断；但只要涉及边界语义、格式化、精度、时区 / 日期零点、深层对象、节流防抖等容易出错的场景，必须先查已引入库和项目公共能力。
- **新建本地工具函数前必须先查公共能力**：凡是准备新增 `formatXxx`、`isXxx`、`getXxxText`、`normalizeXxx`、`parseXxx`、`cloneXxx`、`debounceXxx` 等本地工具函数，或准备新建 `utils.ts` / `helper.ts` 承载通用处理逻辑时，必须先暂停编码并完成公共能力检索。至少应搜索项目依赖、项目公共工具、项目公共组件和同类页面用法，确认没有语义匹配的成熟能力后，才允许局部实现。
- **禁止把公共语义包装成本地重复逻辑**：如果已确认公共库或项目公共能力能覆盖底层语义，禁止在业务文件中重复手写 `null/undefined/空字符串`、深拷贝、防抖、日期格式化、金额精度、枚举展示等判断。确实需要业务命名时，只允许做有业务语义的薄封装，且封装内部必须复用已确认的公共能力。
- 使用公共库或项目公共能力前，必须确认源码、类型定义或官方文档语义，禁止只按函数名猜测。
- 复用公共库前必须确认该库能力的真实语义和边界，例如日期比较单位、是否包含边界值、空数组 / 空对象是否视为空、小数舍入方式等；禁止只因函数名相似就使用。
- 语义匹配时直接复用；语义不匹配时禁止强行复用，也禁止绕过查证直接手写，应继续查找更匹配的公共能力。
- 例如空值判断必须先确认 `0`、`false`、空数组、空对象是否为有效业务值，再选择对应公共方法；禁止把不同库的 `isEmpty` 当成同一语义。
- 当公共库或项目公共能力同时提供正向 / 反向语义函数时，必须优先使用与业务判断方向一致的函数，避免用取反表达相反语义。
- 例如判断“有值”时，项目已确认存在 `isNotEmpty` 这类正向函数，应使用 `isNotEmpty(value)`；禁止写成 `!isEmpty(value)`。只有没有对应正向函数，或正向函数语义与当前业务不一致时，才允许取反。
- 判断“无值”时同理，直接使用 `isEmpty(value)`，不要写成 `!isNotEmpty(value)`。
- 如果项目已有同类库用法，应优先延续当前项目主流写法，避免同一文件或同一模块里混用多套等价工具；但禁止为了统一而顺手替换无关老代码。
- 查不到匹配库能力、或公共能力语义不匹配时，才允许局部实现；局部实现必须在代码附近说明为什么不复用已有库或公共能力，避免后续维护者误以为可以随意复制。
- 如果最终仍选择局部实现，代码附近必须说明为什么公共库或项目公共能力不适用，例如边界语义不同、返回结构不同、只服务当前一次性业务规则。禁止只写“空值展示”“格式化数据”这类看不出复用判断过程的注释。
- 本次如果新增了工具函数、公共判断或局部格式化逻辑，最终回复必须简要说明已查到哪些公共能力、为什么复用或为什么不复用。未说明查证结果时，视为公共能力复用自检未完成。

**示例**：

```ts
// ❌ 禁止 - 公共库已有同语义能力时，业务文件重新手写
function isBlank(value) {
    return value === undefined || value === null || value === ''
}
```

```ts
// ✅ 正确 - 优先使用已确认语义匹配的公共库
import { isEmpty } from 'class-validator'

const blank = isEmpty(value)
```

```ts
// ❌ 禁止 - 未查公共能力，直接手写本地空值判断
function formatXxxEmpty(value) {
    return value === undefined || value === null || value === '' ? '-' : value
}

// ✅ 正确 - 底层空值语义复用已确认的公共能力
import { isEmpty } from 'xxx-validator'

/** 业务详情纯展示空值格式化：仅展示占位，不参与提交 */
function formatXxxEmpty(value) {
    if (isEmpty(value)) return '-'

    return value
}
```

```ts
// ❌ 禁止 - 正向工具已存在时，用取反表达有值
if (!isEmpty(value)) {
    return value
}
```

```ts
// ✅ 正确 - 判断方向和工具函数语义一致
if (isNotEmpty(value)) {
    return value
}
```

```ts
// ✅ 允许 - 公共能力语义不匹配时，局部实现必须说明差异
// 当前字段数字 0 是有效值，已有公共判断会把 0 当空，因此这里保留局部判断。
const blank = value == null || value === ''
```

```ts
// ❌ 禁止 - 项目已有日期库时，手写日期零点和时间戳比较
const todayStart = new Date().setHours(0, 0, 0, 0)
const disabled = currentDate.getTime() < todayStart
```

```ts
// ✅ 正确 - 已确认项目依赖并已有同类用法时，复用日期库表达日期语义
import dayjs from 'dayjs'

const disabled = dayjs(currentDate).isBefore(dayjs().startOf('day'))
```

```ts
// ❌ 禁止 - 金额/汇率/比例等精度敏感计算直接用浮点数硬算
const total = price * count
```

```ts
// ✅ 正确 - 项目已有小数精度库且语义匹配时，使用成熟库处理精度
const total = decimal(price).mul(count).toNumber()
```

**禁止行为**：

- 禁止只参考其他页面就照抄参数，不回到函数/组件定义确认
- 禁止重复传入函数或组件已经默认处理的参数
- 禁止未确认合法值就自行填写枚举值、模式名、数字阈值
- 禁止为了“看起来完整”补一堆默认配置
- 禁止查不到定义时继续靠猜测写代码

**代码示例**：

```ts
// ❌ 禁止 - 未查看 useSimpleSelecter 默认值，重复传入默认配置
useSimpleSelecter(request, {
    least: 1,
    immediate: false
})

// ✅ 正确 - 查看源码确认 least 默认就是 1，只保留真正改变默认行为的配置
useSimpleSelecter(request, {
    immediate: false
})
```

**判断标准**：

- 使用非当前文件内定义的组件、函数、Hook 或工具方法并传入配置时，必须先查源码/类型/文档；不能因为“看起来熟悉”跳过查证
- 已有默认值时，不重复传入同等默认配置
- 其他页面用法只能帮助定位，不能作为最终依据
- 查不到定义、默认值或可用值时，必须暂停确认，不能靠推断继续写

# 通用组件业务边界规范

**核心原则**：通用/基础组件只承载跨场景稳定能力，禁止内置具体页面、接口或业务状态的判断和样式。页面业务差异应通过 `props`、`slots`、`class` 回调等扩展点由调用方传入，并在业务页面或业务组件中维护。

**禁止行为**：

- 禁止在通用组件内直接判断页面业务字段，如 `sendRelationRuleStatus`、`approvalStatus`、`businessType`
- 禁止在通用组件样式中写单一页面业务类，如 `.email-input-tag--send-relation-conflict`
- 禁止为了某个页面需求修改通用组件默认表现，导致其他调用方被动受影响
- 禁止把接口返回的业务语义字段加入通用组件基础类型，导致基础组件依赖业务模型

**正确做法**：

- 通用组件只新增稳定扩展点，如 `tagClass`、`optionClass`、`prefix/suffix slot`、`renderLabel`
- 业务状态判断、业务 class 生成、业务样式放在页面组件或页面专属业务组件中
- 如果多个业务模块复用同一业务态，再抽到对应业务目录组件，不直接上升到基础组件
- 新增扩展点前先确认已有 `props/slots` 是否能满足，避免重复能力

**代码示例**：

```vue
<!-- ❌ 错误：通用邮箱标签组件内写收发件规则业务样式 -->
<email-input-tag class="email-input-tag--send-relation-conflict" />

<!-- ✅ 正确：基础组件提供扩展点，业务页面决定业务 class -->
<email-input :tag-class="getSendRelationTagClass" />
```

```ts
/** 获取收发件规则邮箱标签业务样式 */
function getSendRelationTagClass(emailItem) {
    return {
        'email-input-tag--send-relation-conflict': emailItem.sendRelationRuleStatus === 'conflict'
    }
}
```

# 业务组件拆分与目录化规范

**核心原则**：当页面或弹窗内部出现复杂、重复、可独立理解的业务区域时，必须先判断是否拆成页面专属业务子组件，禁止先把所有结构直接堆进主文件，后续再被动补救。

**适用场景**：复杂弹窗、详情页局部模块、动态表格、独立选择器、重复业务块、页面专属组件目录化。

**硬性红线**：禁止为了减少行数强行拆组件；禁止只有单个入口文件却升级成目录；拆分后边界不清、需要大量透传状态时应回到当前文件。

**必须优先考虑拆分的场景**：

- 同一页面 / 弹窗内出现 2 处及以上结构相似、交互相似的业务块
- 某个区域包含独立表格、动态行、折叠面板、选择器、左右面板、复杂校验或独立滚动
- 子区域有明确业务名称，能够脱离主文件单独阅读和维护
- 该区域后续很可能扩展成多模式、多状态或多数据源
- 主文件因为该区域变得难以快速识别主流程

## 页面级拆分评估门禁

**核心原则**：当用户给出完整页面 / 弹窗视角，或当前文件已经明显承载多个独立业务区域时，AI 不能只按当前单点改动判断是否拆分，必须先做页面级组件拆分评估。

**触发场景**：

- 用户提供完整页面、完整弹窗或大范围 UI 截图，要求继续调整其中局部样式或交互
- 一个页面 / 弹窗内已经出现 3 个及以上清晰业务区块，例如头部信息、指标区、正文信息、图表区、附件区、右侧列表等
- 主文件同时承担数据拉取、路由动作、弹窗入口、左右布局和多个内容区块，导致继续新增局部功能会让主流程更难识别

**评估输出要求**：

- 必须说明哪些区域建议拆成页面专属业务组件
- 必须说明哪些区域不拆，以及不拆原因
- 必须说明本次当前改动是否需要立即拆分
- 如果拆分会影响多个文件、导入路径或既有结构，必须先输出方案并等用户确认，禁止借局部修改直接重构

**执行边界**：

- 单个图标、单条文案、普通按钮或简单样式微调，本身不构成立即拆分理由
- 如果本次只是局部微调，但页面级评估显示后续应拆分，应在回复中明确“本次不立即拆，建议后续按页面区块拆”
- 页面专属拆分优先放在当前页面 `components/` 目录；主入口保留数据获取、路由跳转、弹窗入口和页面布局编排
- 禁止把页面专属业务区块提前上升为跨模块公共组件，除非已经确认存在跨页面复用

**不应拆分的场景**：

- 只是普通表单字段、普通按钮组、简单展示文本
- 只为减少文件行数而拆分
- 拆出去后组件名没有明确业务含义
- 子组件需要反向依赖主文件大量私有状态，导致边界更复杂

**目录化规则**：

- 普通单一弹窗保持 `dialog-update.vue`
- 当弹窗内部已经拆出专属子组件时，优先升级为：

```text
dialog-update/
  index.vue
  components/
    xxx.vue
```

- `index.vue` 保留弹窗主流程，`components/` 只放该弹窗专属业务组件
- 子组件文件名使用业务名，不要用含糊的 `table.vue`、`panel.vue`、`item.vue`
- 目录化后禁止同时保留同级入口文件和同名目录，例如禁止同时存在 `dialog-applicable-supplier-select.vue` 与 `dialog-applicable-supplier-select/`
- 如果从单文件升级为目录入口，必须删除或迁移原同级单文件，并同步更新所有 import 路径

# TypeScript 类型问题处理规范

**核心原则**：类型报错必须优先回到真实数据结构、函数签名、组件泛型和业务边界上解决，禁止为了“让 TS 不报错”而新增无业务语义的包装函数、运行时判型、类型断言或兜底转换。

**适用场景**：接口类型、组件 props / emits、Hook 返回值、扩展字段、可选字段、泛型约束导致的类型不匹配。

**硬性红线**：禁止用 `as any`、无依据断言、空值兜底、无业务语义包装函数掩盖真实类型问题；应优先修正源头类型或业务边界。

**禁止行为**：

- 禁止为了适配类型而新增没有业务语义的函数，例如只把 `name?: string` 包装成 `name: string` 再传给工具函数
- 禁止用 `as any`、`as unknown as Xxx`、无依据的 `as Xxx` 掩盖真实类型不匹配
- 禁止为了绕过类型错误新增运行时判型函数，但该判型不服务真实业务逻辑
- 禁止把页面业务字段加入通用基础类型，只为让某个页面的类型通过
- 禁止用默认值、空字符串、空数组等方式强行满足类型，却改变业务含义

**正确做法**：

- 如果运行时本来允许字段为空，应修改源头类型，例如 `name: string` 改为 `name?: string`
- 如果组件支持扩展字段，应通过泛型、扩展类型、`Omix` 或稳定扩展点表达，而不是写页面专属断言
- 如果函数返回值被推断得过窄或过宽，应显式声明返回类型，而不是新增中间函数
- 如果类型暴露出业务状态建模不清晰，应先调整状态模型，例如用 `undefined` 表示“无状态”，不要新增 `default` 枚举再到处排除
- 如果确实需要类型断言，必须能说明外部系统、组件契约或前置校验已经保证该类型成立

**代码示例**：

```typescript
// ❌ 禁止 - 只是为了满足 name 必填而新增包装函数
function getTagUserString(emailItem: TagItem) {
    return getUserString({
        email: emailItem.email,
        name: emailItem.name ?? ''
    })
}

// ✅ 正确 - getUserString 运行时本来支持无 name，应该修正源头类型
export type UserInfo = {
    email: string
    name?: string
}

const text = getUserString(emailItem)
```

// ❌ 禁止 - 为了解决 class 回调类型，新增没有业务必要的判型和断言

**判断标准**：

- 这个改动是否只服务 TS 通过，而没有业务意义；如果是，应回到类型源头修
- 新增的函数、判型、断言是否让调用方更理解业务；如果没有，不应新增
- 类型定义是否和运行时真实数据一致；不一致时优先修类型，不靠兜底绕过
- 通用类型是否被页面业务污染；如果是，应改为扩展点或业务侧扩展类型
