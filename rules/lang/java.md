# Java 语言规范（个人通用）

> **归属维度**：语言层规则。约束 Java 语言本身的个人通用写法，与端无关，不限定特定企业。
> **生效条件**：当前项目事实语言为 Java 时生效。判定依据：项目存在 `pom.xml` / `build.gradle` / `project-catalog.json` 登记。
> **来源**：个人规则。与企业规范的叠加与冲突裁决遵循 `rules/global-rules.md`「规范来源与冲突优先级」：企业空白或兜底占位时直接补位，企业明确条文未禁止时叠加生效，真互斥冲突时按企业明确条文执行并显性告知。
> **边界**：本文件只收录不限定企业的个人通用 Java 写法。sky 企业后端文档原文在 `rules/enterprise/sky/lang/java.md`，sky 项目实践总结在 `rules/enterprise/sky/practice/java.md`。禁止默认「后端 = Java」，也禁止把 `rules/lang/js-ts.md` 的 JS/TS 细则（如变量级 JSDoc、`===`、前端枚举 Options 等）套用到 Java 代码。

## 高价值过程注释规范

**核心原则**：在本次新增或修改的 Java 代码中，凡是代码本身无法直接表达的业务意图、并发/事务约束、历史兼容和复杂查询目的，必须在贴近代码处写清“为什么”，不得因为老仓库缺注释就退化为无注释，也不得为直白代码制造机械注释噪音。

**适用场景**：本次改动范围内新增或修改的 Java 方法、业务分支、事务/锁/幂等控制、数据兼容处理，以及 MyBatis XML / SQL 查询逻辑（遵循最小侵入边界，不要求顺手给本次未改动的存量老代码补注释）。

**防老代码退化边界**：

- 禁止以“项目已有代码没写注释”“按老仓库风格处理”为由，对本次新增或修改的高价值逻辑省略关键过程注释。
- 存量老仓库注释参差不齐时，只参考其命名与代码格式，不作为省略高价值过程注释的依据。

**必须写过程注释的场景**：

1. **复杂业务状态分支与非显而易见的提前返回**：例如特定状态跳过处理、重复回调直接幂等返回、多条件组合决定不同流转路径时，在 `if` / `switch` 上方说明该分支的业务原因与处理意图。
2. **事务边界、分布式锁、乐观锁与幂等意图**：说明锁粒度与保护对象、选择当前事务边界或传播级别的原因、并发冲突或重复请求时的处理意图（如防重扣、防重复通知、允许调用方重试）。
3. **历史脏数据兼容、外部系统特殊约定与兜底逻辑**：说明兼容哪类历史状态或外部行为、为什么必须这样兜底，以及触发兜底后的业务结果；如属于非需求文档口径的交互或逻辑，同时按 `rules/common/40-comments.md`「非需求文档口径必须可找回」留出处。
4. **复杂 MyBatis XML / SQL 的查询意图与关键条件**：涉及多表关联、子查询、聚合统计、排序/索引依赖、特殊过滤口径（如排除特定状态、时间窗或归属边界）时，在 SQL 块或关键条件旁说明业务口径和查询目的，而不是逐字翻译 SQL 关键字。

**注释位置与内容要求**：

- **贴近代码**：解释 `if` / `switch` / 锁块 / 关键更新 / SQL 条件时，注释紧贴写在语句或块正上方，不把多条分支细节堆到方法顶部 Javadoc。
- **只写长期业务事实与意图**：遵守 `rules/common/40-comments.md` 注释内容边界，禁止写沟通过程、本次改动交代或给 AI 看的规则提醒。
- **不给直白代码加噪音**：普通 getter/setter、简单 DTO 转换、含义清晰的常规局部变量不需要机械注释。

**硬性红线**：

- 禁止在复杂业务分支、事务/锁/幂等、历史兼容、复杂 SQL 场景下以“与老代码风格一致”为由省略意图注释。
- 禁止写复述代码字面意思的废话注释（如 `// 判断状态`、`// 更新数据`、`// 返回结果`）。
- 禁止顺手给本次未改动的存量老代码批量补注释（遵守最小侵入边界）。
- 禁止把 `rules/lang/js-ts.md` 的变量级 JSDoc 习惯套用到 Java 局部变量。

**代码示例**：

```java
// ❌ 禁止 - 跟随老代码裸写关键业务判断、锁与兼容逻辑，或只写废话注释
// 判断状态
if (Objects.equals(record.getStatus(), XxxStatusEnum.CLOSED.getCode())) {
    return;
}
// 更新数据
xxxMapper.updateStatusByVersion(record.getId(), targetStatus, record.getVersion());

// ✅ 正确 - 贴近代码说明“为什么”，不给普通变量加噪音注释
// 已关闭单据允许重复回调直接幂等返回，避免上游重试触发告警
if (Objects.equals(record.getStatus(), XxxStatusEnum.CLOSED.getCode())) {
    return;
}

// 仅在状态变更成功后触发外部通知，防止并发重入重复扣减；乐观锁冲突由调用方重试
int affectedRows = xxxMapper.updateStatusByVersion(record.getId(), targetStatus, record.getVersion());
if (affectedRows == 0) {
    throw new BizException("状态已变更，请稍后重试");
}
```

**判断标准**：

- 本次新增或修改的复杂分支、事务/锁/幂等、历史兼容、复杂 SQL 是否都有贴近代码的意图注释。
- 去掉本次对话背景，只看这些注释能否立刻明白“为什么必须这样写”。
- 是否没有因为老代码没写注释就跟着省略，同时也没有给普通直白代码制造无意义注释噪音。
