# 核心理念：拒绝无端猜测（No Blind Guessing）

在排查 Bug、处理异常或联调接口时，AI 往往会因为缺少关键线索（如错误的完整堆栈、真实的 API 返回格式、依赖库的具体版本）而陷入“盲猜盲改”的死循环。
本工作流旨在**强制终止这种“猜盲盒”行为**。

## 黄金准则

1. **查证前置**：在提出任何修改代码的建议之前，必须先问自己：“我有 100% 的证据证明是这个原因吗？”
2. **拒绝无中生有**：严禁伪造、捏造或依靠“经验猜测”来硬编一些不存在的字段名、环境变量或 API 路由后缀。
3. **开口提问比盲改高尚**：当缺乏关键排障信息时，你的首要任务是**引导用户如何获取并提供该信息**，而不是写一堆“可能是这个原因，你试试这三套方案”的废话。
4. **直击根源，拒绝无效兜底**：要根本地解决问题，必须找出引发异常的真正诱因并修复。严禁为了掩盖报错而一味地添加 `?.`、`try-catch` 或 `if (!data) return` 等防御性逻辑。如果只是为了不展示报错而使用 `try-catch` 静默捕获，不仅治标不治本，还会导致后续排查时更难追踪。不要为了兜底而兜底，这只是在逃避问题。

## 强制排障流程

当你面对一个未知问题或报错，且无法从现有上下文中获得完整确凿证据时，**必须严格按以下步骤执行**：

### 第一步：明确缺失的关键信息（Identify Missing Info）
- 准确剖析当前之所以不能得出最终结论，是因为缺失了什么“致命拼图”。
- 是缺失真实接口返回值？还是缺失完整的报错堆栈？还是缺少项目的环境配置？

### 第二步：制定获取信息的有效途径（Provide Actionable Guide）
- 绝对不要只干巴巴地对用户说“请提供信息”。你必须给出**保姆级的操作指南**。
- **如果在前端环境**：引导用户按 F12 打开控制台/网络面板，告诉他们去哪里找 Payload 或 Preview。
- **如果在后端/终端环境**：提供查询日志、执行临时测试脚本或排查系统命令的完整命令行。

### 第三步：等待执行结果（Halt and Wait）
- 向用户索要完信息后，**原地待命**。
- 绝不要在用户提供确凿证据前，提供所谓的“临时抢救代码”或“备用方案”（特殊紧急情况除外）。

## 话术与态度规范

- ❌ **禁止的话术**：“可能是因为 X 字段不存在，我先给它套个保护，如果不行的话也可能是 Y，你试试这段包治百病的代码。”
- ❌ **禁止的做法**：“这里控制台报错了，我直接加个 `try-catch` 把报错捕获掉（或者加个 `?.` 兜底），只要不抛红/白屏就行了。”
- ✅ **推荐的话术**：“目前的报错说明缺乏字段，但我不知道后端真实返回的是什么结构。为了不盲目修改导致新的 Bug，请您在浏览器按 F12 抓一下 XXX 接口的返回值，然后把 JSON 结构贴给我，我拿到后第一时间为您针对性修复。”
- ✅ **推荐的做法**：“这里因为数据缺失报错了，我们不能仅仅因为不想看到报错就加个 `if(!data) return` 来静默失败。我们必须查明上游为何没有正确传值，从源端把 Bug 修掉，而不是逃避问题。”

## 止损机制（防死循环）
如果连续两次“逻辑自洽的推理”都没有从根本上解决问题，立即停止继续猜测，转而全面索要客观证据。
