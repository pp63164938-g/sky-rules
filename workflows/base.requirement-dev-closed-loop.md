# 需求文档驱动开发闭环工作流

当用户提供需求文档、在线文档、工单、PRD、接口文档或设计说明，并要求基于当前项目梳理、开发、联调、验收时，使用本工作流。

本工作流的目标不是只完成用户当前点名的一小步，而是由 AI 主动维护进度、暴露缺口、推动下一步，直到需求进入可交付闭环。

## 0. 最高优先级原则

- 必须先读取需求文档，再进入代码设计或编码。
- 在需求拆解、开发方案或编码前，必须先输出需求理解核对产物，并等待用户确认。
- 需求正文、正文引用资源、关键关联文档或接口文档没有完成读取时，必须停止在“读取需求 / 需求理解核对”阶段；禁止继续输出开发方案、任务拆解、接口 mock、路由设计或编码。
- “打开了页面壳层 / 识别到链接 / 只看到目录 / 只读到截图局部 / 只读到原型外壳”不等于已读取需求；必须拿到可支撑理解的正文、图片内容、HTML 内容或明确失败状态。
- 未读取资料只要会影响页面结构、字段、交互、接口、权限、菜单或验收，就属于阻断项；只能输出阻断说明和下一步读取方案，不能降级成“先写草案”。
- 必须区分事实、推断、缺口和冲突，禁止把未确认内容写成确定逻辑。
- 必须维护进度看板，用户不需要主动追问“当前做到哪一步、还缺什么”。
- 必须按阶段推进；每个阶段结束后输出阶段回执。
- 没有阻断项时，AI 应主动进入下一阶段；存在阻断项时，必须说明影响、已查证内容和建议选择。
- 需要修改代码、提交、推送、部署或处理高风险业务逻辑前，必须等待用户明确确认。

## 1. 触发后的进度看板

进入工作流后，AI 必须持续维护进度看板。阶段切换、遇到阻断、完成一批开发或准备进入下一步时，必须输出：

```md
进度看板：
- 当前阶段：
- 已完成：
- 正在处理：
- 下一步：
- 阻断项：
- 需要用户确认：
- AI 建议：
```

进度看板必须体现真实状态；禁止只给笼统描述，例如“继续开发中”。

## 2. 用户确认门禁

以下节点必须等待用户明确确认：

- 需求、接口、设计或用户口头说明之间存在冲突。
- 需要从多个实现方案中选择一种。
- 准备开始修改代码。
- 准备执行 `git add`、`git commit`、`git push` 或部署操作。
- 接口字段、提交结构、权限标识、金额、状态流转、业务分支等高风险内容无法查证。
- 需要采用临时替代接口、临时禁用入口、临时使用空 Options、临时保留 TODO 等会影响用户感知的方案。

以下节点可由 AI 主动推进：

- 读取用户提供的需求文档。
- 搜索项目已有文档、路由、API、组件和相似页面。
- 整理需求理解核对、需求拆解、待确认清单和实现方案。
- 在用户已确认实现方案后，按既定任务拆分继续开发。
- 执行只读检查、格式化检查、轻量验证和 TODO 搜索。

## 3. 阻断项表达规范

遇到阻断时，必须让用户无需看代码或 diff 也能理解问题。输出格式：

```md
阻断项：
- 问题：
- 影响：
- 当前依据：
- 我已查过：
- 可选处理：
- AI 建议：
```

禁止只说“需要确认一下”。必须说明如果不确认，会影响展示、提交、权限、联调、验收或上线中的哪一环。

## 4. 阶段 1：读取需求

输入可以是在线文档、本地文档、接口文档、需求截图或工单链接。

执行要求：

- 读取完整需求内容，不能只读标题或目录。
- 记录文档标题、版本、来源和读取时间。
- 提取功能点、页面、弹窗、接口、权限、菜单、异常边界和范围外事项。
- 如果文档无法访问、内容为空、只有目录或明显缺页，必须停止并说明，不能假装已掌握需求。

### 4.1 在线文档读取判定

在线文档、知识库、低代码原型、Git 托管预览或 SPA 页面读取时，必须区分“页面可打开”和“正文可读取”。

执行要求：

- 如果浏览器只打开了前端壳层、登录页、空白页、目录页或 hash 路由页面，不能认定为已读取。
- 必须继续查找真实数据来源，例如 raw markdown、下载接口、页面网络请求、导出接口、附件接口或本地缓存文件。
- 读取成功时必须记录文档标题、真实路径 / URL、读取方式、内容长度、版本 / commit / 更新时间。
- 读取失败时必须记录失败资源、失败方式、HTTP 状态 / 报错、已尝试方法和影响范围。
- 遇到超时必须使用有限重试、明确超时、直接数据接口、并发拉取等方式优化；禁止无限等待或反复尝试同一种方式。
- 关键资料最终仍读取失败时，必须阻断并让用户补充可访问内容或确认替代依据。

判断标准：

- 用户不看代码、不看终端，也能知道哪些资料已读、哪些没读、哪些失败、失败会影响什么。
- AI 不能因为“看到了链接名 / 文件名 / 页面标题”就继续推断需求。

阶段产物：

```md
需求读取结果：
- 文档标题：
- 版本：
- 来源：
- 读取时间：
- 主要功能：
- 范围外事项：
```

## 5. 阶段 2：需求理解核对

在进入需求拆解、项目定位、开发方案或编码前，必须先输出一份“需求理解核对”产物，让用户确认 AI 对需求的理解是否正确。

### 5.1 触发条件

只要本次任务存在以下任一输入，就必须执行本阶段：

- 用户提供需求文档、PRD、在线文档、工单或接口说明。
- 需求文档中引用了图片、原型、HTML、附件、截图或设计说明。
- 用户要求“根据需求开发”“梳理要做什么”“正式开始”。
- 当前任务会进入代码修改、接口 mock、路由 / API / 页面生成或联调。

禁止在未完成需求理解核对前直接输出开发方案或开始编码。

### 5.2 必须读取的资料范围

需求理解不能只读 Markdown 正文。必须尽可能读取需求文档引用的所有相关资料：

- Markdown / 文本文档正文。
- 文档中的相对链接、图片、截图、附件。
- HTML 交互原型。
- Figma / 设计图 / 原型图。
- 表格、流程图、Mermaid 图、接口片段。
- 需求正文中声明的 `related_docs`、`related_dev_docs`、关联接口文档、关联原型、附件、截图和设计说明。
- 用户补充说明和聊天中确认过的结论。

如果文档中引用了图片或 HTML 原型，必须尝试实际打开、下载、截图或解析；不能只说“识别到引用”。

如果资源无法访问，必须在产物中标记为“未读取 / 读取失败”，并说明影响范围，禁止假装已经理解。

如果关联资料读取失败，必须判断它是否影响本次页面结构、字段来源、接口链路、权限菜单或复用边界；只要影响，就必须作为阻断项列出。

HTML 原型如果只包含运行壳层或模板占位，不能只按 HTML 文本理解；必须结合截图、渲染结果或可见页面内容判断。

图片原型必须实际打开或截图核验；不能只在 Markdown 中看到图片链接就标记为已读。

### 5.3 需求理解核对产物

阶段产物建议以 Markdown 输出，标题格式：

```md
# 需求理解核对：xxx需求名称
```

必须包含以下内容：

```md
## 1. 需求背景

用业务语言说明本需求解决什么问题、给谁用、核心对象是什么。
禁止直接进入代码实现方案。

## 2. 已读取资料

| 资料 | 状态 | 说明 |
| --- | --- | --- |
| 需求正文 | 已读取 / 未读取 | xxx |
| 原型图片 | 已读取 / 未读取 / 读取失败 | xxx |
| HTML 原型 | 已解析 / 未解析 / 读取失败 | xxx |
| 接口文档 | 已读取 / 未提供 | xxx |

## 3. 用户角色与使用流程

按角色说明用户从哪里进入、做什么、看到什么、完成什么结果。

## 4. 页面 / 弹窗级理解

逐个页面或弹窗说明：

- 页面目标
- 页面入口
- 搜索项 / 表单项
- 列表 / 卡片 / 详情展示内容
- 按钮和操作
- 跳转关系
- 空状态、异常状态、禁用态
- 不做内容及原因

## 5. 字段理解

| 字段 / 文案 | 出现位置 | 用途 | 数据来源 | 当前确认状态 |
| --- | --- | --- | --- | --- |

字段理解必须区分页面文案和接口字段。
需求或原型只确认页面文案时，不能反推接口字段名。

## 6. 交互理解

| 交互 | 触发位置 | 预期行为 | 当前确认状态 |
| --- | --- | --- | --- |

## 7. 权限与菜单理解

| 功能 | 菜单位置 | 权限点 | 当前状态 |
| --- | --- | --- | --- |

菜单唯一标识、权限点、路由权限必须区分；不能互相替代。

## 8. 后端依赖

| 依赖 | 用途 | 当前状态 | 前端临时处理 |
| --- | --- | --- | --- |

## 9. 正文、原型、接口、用户说明的差异

| 问题 | 需求正文 | 原型 / 设计 | 接口 / 后端 | 用户确认 | 建议 |
| --- | --- | --- | --- | --- | --- |

只要发现正文、原型、接口或用户说明不一致，必须列出。
禁止把冲突静默消化成实现细节。

## 10. 本次不包含

每个“不做”项必须说明原因，例如：

- 不做 xxx：原因是该能力属于另一个页面 / 另一个角色 / 范围外 / 后端能力 / 未在需求中出现。
- 不做 xxx：原因是需求明确禁止提供该入口。

禁止只写“不做 xxx”而不说明原因。

## 11. 待用户确认

- [ ] 需求理解是否正确
- [ ] 差异项按哪个来源优先
- [ ] 缺口处理方式是否接受
- [ ] 是否进入开发方案阶段
```

### 5.4 确认门禁

以下情况必须等待用户确认，不能进入开发方案或编码：

- 需求正文和原型 / HTML / 图片不一致。
- 需求表现和接口文档不一致。
- 用户补充说明改变了需求正文。
- 不做内容的原因不明确。
- 关键页面、弹窗、字段、按钮、权限、路由入口理解不完整。
- 需求正文未读取成功。
- 原型资源引用存在但未能读取，且会影响布局、字段顺序或交互判断。
- 关键关联文档未读取成功，且会影响接口、数据来源、复用边界或影响面判断。

用户确认后，必须把确认结论写入“用户确认”或“差异处理结论”中，再进入下一阶段。

如果用户明确允许使用项目源码、现有页面或用户口头说明替代未读资料，必须把“替代依据”和“未读风险”写入需求理解核对产物，再进入下一阶段。

### 5.5 用户补充后的回写要求

当用户在需求理解阶段补充或纠正信息时，AI 必须更新需求理解核对产物中的对应条目，而不是只在聊天里临时记住。

例如用户确认：

```md
- 并发公式按“业务基数 × 手工系数”
- 管理页不需要详情入口
- 查询页需要国家搜索项
```

AI 应更新：

```md
## 用户确认结论

| 问题 | 确认结论 |
| --- | --- |
| 并发公式 | 业务基数 × 手工系数 |
| 管理页详情入口 | 不需要 |
| 查询页国家搜索项 | 需要 |
```

### 5.6 阶段回执

需求理解核对完成后，必须输出阶段回执：

```md
阶段回执：
- 本阶段完成：
- 产物：
- 已读取资料：
- 读取方式：
- 读取成功证据：
- 未读取资料：
- 读取失败资料：
- 失败影响范围：
- 发现的问题：
- 用户已确认：
- 是否允许替代依据：
- 仍待确认：
- 是否阻断：
- 下一阶段：
```

如果仍有阻断项，不得进入开发方案。

## 6. 阶段 3：需求拆解

执行要求：

- 按页面、弹窗、接口调用、权限点、菜单路由、状态流转、异常边界拆解。
- 区分前端要做、后端要做、只需联调、不在本次范围内。
- 需求中只说明页面表现时，不能反推接口字段。
- 需求中只说明接口资产时，不能反推页面交互。

阶段产物：

```md
需求拆解清单：
- 前端新增页面：
- 前端新增弹窗：
- 前端新增接口调用：
- 权限点：
- 菜单/路由：
- 后端依赖：
- 不在本次范围：
```

## 7. 阶段 4：项目定位

执行要求：

- 查当前项目已有相似页面、路由、API、组件、权限和样式写法。
- 明确本次建议新增或修改的文件位置。
- 区分“项目已有事实”和“AI 建议命名”。
- 使用非当前文件内组件、函数、Hook 或工具前，必须查源码、类型定义或项目已有真实用法。

阶段产物：

```md
项目定位：
- 相似页面：
- 路由文件：
- API 文件：
- 组件复用：
- 推荐新增目录：
- 待确认命名：
```

## 8. 阶段 5：缺口与冲突确认

执行要求：

- 汇总所有会影响开发的疑点。
- 按风险分级：阻断开发、可先静态占位、可后续联调。
- 明确每个疑点的影响范围和建议处理方式。
- 高风险缺口必须进入用户确认门禁。

阶段产物：

```md
待确认清单：
- 问题：
  影响：
  当前依据：
  需要谁确认：
  未确认前处理方式：
```

## 9. 阶段 6：前端方案设计

执行要求：

- 给出文件级实现方案。
- 明确新增文件、修改文件、复用组件、接口调用链和权限挂载方式。
- 标明 TODO / 占位策略。
- 方案未确认前，不进入编码。

阶段产物：

```md
前端实现方案：
- 路由：
- 页面：
- 弹窗：
- API：
- 权限：
- 组件复用：
- 待确认占位：
```

## 10. 阶段 7：分批开发

建议顺序：

1. API 层与类型。
2. 路由与菜单挂载。
3. 主列表 / 看板页面。
4. 弹窗 / 详情页。
5. 权限、空状态、异常状态。
6. 联调修正。
7. 格式化和轻量验证。

每批开发结束必须输出：

```md
本批完成：
- 修改文件：
- 完成功能：
- 待联调项：
- 下一批：
```

执行要求：

- 每批只做当前批范围，禁止顺手优化老代码。
- 每批结束必须回看 diff，确认没有误删注释、误改旧逻辑或混入无关变更。
- 修改代码后必须按项目已有格式化 / lint 工具处理本次修改文件；无法执行时必须说明。

## 11. 阶段 8：联调闭环

执行要求：

- 按接口逐个验证请求参数、响应字段、错误状态和页面使用位置。
- 字段必须来自当前目标接口，禁止跨接口硬凑。
- 缺字段必须显性标记并反馈。
- 联调阶段禁止遗留 `TODO待联调_`；接口文档不存在的字段必须使用 `TODO无此联调字段_用途描述`。

阶段产物：

```md
联调记录：
- 接口：
- 请求参数：
- 响应字段：
- 页面使用位置：
- 问题：
- 处理结论：
```

## 12. 阶段 9：验收收口

执行要求：

- 按需求功能点逐项勾验。
- 覆盖权限、异常、空状态、边界值、加载态和失败提示。
- 执行轻量验证、格式化检查和 TODO 搜索。
- 如果当前项目是 Vite 前端项目，默认不执行 full build；除非用户明确要求或任务目标需要。

阶段产物：

```md
验收清单：
- 需求功能点覆盖：
- 权限矩阵：
- 搜索/分页/详情/编辑：
- 异常场景：
- TODO 搜索：
- 格式化：
- 验证命令：
```

## 13. 阶段 10：交付说明

最终回复必须包含：

```md
完成内容：
- ...

验证：
- ...

待确认：
- ...

发散点：
- 无 / ...
```

如果存在 AI 推断、临时占位、接口缺失、权限缺失或未联调字段，必须写在“发散点”或“待确认”里。用户不看 diff 也必须知道哪些内容尚未完全确认。

## 14. 阶段回执

每完成一个阶段，必须输出阶段回执：

```md
阶段回执：
- 本阶段完成：
- 产物：
- 发现的问题：
- 是否阻断：
- 下一阶段：
```

如果无阻断，应主动说明将继续进入下一阶段；如果有阻断，应给出建议选择并等待用户确认。

## 15. 常用用户指令

用户可以用以下短指令推进：

- `继续`：按当前工作流进入下一步。
