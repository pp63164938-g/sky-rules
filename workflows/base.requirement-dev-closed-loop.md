# 需求文档驱动开发闭环工作流

本工作流仅允许用户显式触发。只有用户通过 `$base-requirement-dev-closed-loop` 明确调用，或明确要求“使用 / 按该工作流执行”时，才使用本工作流。

仅提供需求文档、在线文档、工单、PRD、接口文档或设计说明，并要求基于当前项目梳理、开发、联调或验收，不构成本工作流的触发条件。未显式触发时，按当前任务适用的通用规则和其他工作流执行，不进入以下阶段流程，也不主动维护本工作流的进度看板。

本工作流的目标不是只完成用户当前点名的一小步，而是由 AI 主动维护进度、暴露缺口、推动下一步，直到需求进入可交付闭环。

进入需求拆解前必须识别当前开发范围是前端、后端还是全栈；禁止因为当前打开的文件或仓库只属于其中一端，就默认另一端不在需求范围。

## 0. 最高优先级原则

- 必须先读取需求文档，再进入代码设计或编码。
- 在需求拆解、开发方案或编码前，必须先输出需求理解核对产物，并等待用户确认。
- 需求正文、正文引用资源、关键关联文档或接口文档没有完成读取时，必须停止在“读取需求 / 需求理解核对”阶段；禁止继续输出开发方案、任务拆解、接口 mock、路由设计或编码。
- “打开了页面壳层 / 识别到链接 / 只看到目录 / 只读到截图局部 / 只读到原型外壳”不等于已读取需求；必须拿到可支撑理解的正文、图片内容、HTML 内容或明确失败状态。
- 未读取资料只要会影响页面结构、字段、交互、接口、权限、菜单或验收，就属于阻断项；只能输出阻断说明和下一步读取方案，不能降级成“先写草案”。
- 必须区分事实、推断、缺口和冲突，禁止把未确认内容写成确定逻辑。
- 业务推导必须按全局规则执行双向告知：写入前披露拟推导逻辑、依据和影响，实际落地后立即披露最终位置、实际影响和前后变化；禁止只在最终交付时补充说明。
- 当正文、原型、设计、附件、接口文档和用户说明相对独立或可能不一致时，必须先取所有来源的功能并集，建立逐项可追踪的需求覆盖基线；禁止选择其中一份资料代替完整需求。
- 需求覆盖基线中的来源条目未达到 100% 归类、未覆盖数不为 0，或关键冲突尚未确认时，禁止进入开发方案和编码。
- 必须维护进度看板，用户不需要主动追问“当前做到哪一步、还缺什么”。
- 必须按阶段推进；相邻阶段没有阻断且不需要用户决策时，允许连续推进并合并输出阶段回执，禁止为了形式完整逐阶段停顿或重复展示相同内容。
- 没有阻断项时，AI 应主动进入下一阶段；存在阻断项时，必须说明影响、已查证内容和建议选择。
- 任何阶段输出“不做 / 不包含 / 范围外 / 暂不做 / 本期不做”时，必须同步说明原因、依据和影响；禁止只列不做清单，导致用户误以为是 AI 自行省略或故意不做。
- 发现需求正文、原型、接口文档或用户说明之间存在冲突时，必须立即停留在“需求理解核对 / 缺口与冲突确认”阶段，输出冲突点、影响范围、已查证依据和建议处理方式；禁止自行选择某一个来源继续输出方案或进入编码。
- “页面表现按需求、数据契约按接口”只适用于可明确分层的差异；如果冲突会影响功能范围、字段提交、枚举值、数据源、接口调用、权限菜单或验收口径，必须等待用户确认后再推进。
- 已按需求文档、原型、截图或用户确认完成的静态预留内容，在后续联调阶段必须作为需求范围依据处理；如果接口缺失、字段不符或后端实现异常，必须进入缺口与冲突确认，禁止为了规避后端问题而直接删除预留入口、控件、列、按钮、弹窗区域或 API 链路。
- 实现方案设计完成后，必须停留在方案阶段等待用户明确确认；禁止 AI 因为“方案已完整”“无阻断项”“用户之前说继续”就自行开始编码。
- 阶段 6 实现方案设计完成后，必须继续执行“阶段 6.5 开发准入核验”；未通过准入核验前，禁止进入编码。
- 开发准入前必须完成“AI 能力发散审计”，并将审计结论写入方案、任务拆分、进度看板和验收；不得只以当前页面按钮作为能力边界。
- 只有用户明确表达“确认方案并进入开发 / 开始编码 / 按这个方案写代码”等授权语义后，才允许进入阶段 7 分批开发。
- “可以 / 继续 / 按你的建议走”只有在上一条回复已经明确输出完整阶段 6 实现方案、阶段 6.5 准入核验且询问是否进入开发时，才可视为开发授权；如果上一条回复只是方向建议、局部方案、问题讨论或阶段未完成，则只能视为继续补充方案，禁止开始编码。
- 前期资料、需求理解、冲突处理、接口契约、权限菜单、字段来源、开发方案或任务拆分任一项未准备好时，禁止以“先写骨架 / 先 mock / 后面再补”为由直接开发。
- 静态骨架开发只有在缺口已完整列出、影响范围已说明、TODO / 占位策略已写入方案，并且用户明确授权“允许静态骨架 / 允许占位开发”后才允许进入；否则视为开发阻断。
- 当用户中断、追问“方案结束了吗 / 等等 / 暂停 / 先别开发”时，必须立即停留在当前阶段，重新输出真实进度看板和缺失项，禁止继续执行编码动作。
- 需要修改代码、提交、推送、部署或处理高风险业务逻辑前，必须等待用户明确确认。

## 1. 触发后的进度看板

进入工作流后，AI 必须持续维护进度看板。首次进入、出现阻断、准备修改代码、完成一批开发和最终交付时必须输出完整看板；相邻阶段连续推进且状态没有实质变化时，只更新变化项，禁止重复输出整张看板。

```md
进度看板：
- 当前阶段：
- 当前开发范围：前端 / 后端 / 全栈
- 已完成：
- 正在处理：
- 下一步：
- 阻断项：
- 需要用户确认：
- AI 建议：
- AI 能力发散审计结论：
- AI 业务推导项：无 / 拟推导项、已落地项、前后变化和确认状态
```

进度看板必须体现真实状态；禁止只给笼统描述，例如“继续开发中”，也禁止在没有状态变化时机械重复相同看板。

### 1.1 续接复用与查证熔断

**核心原则**：用户要求“继续”或任务从暂停状态恢复时，必须从进度看板记录的当前阶段续接，复用已经完成且证据未变化的结论；禁止重新执行已完成阶段，或把同一份需求、项目和代码链路从头查一遍。

执行要求：

- 续接前先核对当前阶段、已完成事项、证据版本和剩余最小问题，只处理尚未完成的部分。
- 已记录文档版本、仓库路径、Commit、目标文件和接口来源，且外部状态没有变化时，直接复用；只有用户调整范围、证据版本变化或结论依赖实时状态时才重新查证。
- 同一需求、同一版本或连续工单已经确认的公共事实必须直接复用，包括需求文档版本、项目路径、开发分支、接口文档入口、公共组件源码、验证命令和已完成工单结论；禁止因切换工单重新读取未变化的整份需求、重新定位相同项目或重复查证相同公共能力。
- 切换到下一工单时，只补查当前工单正文及其独立引用资料、当前工单涉及的页面与接口链路、具有时效性的仓库状态，以及与已完成工单之间的依赖和影响；禁止默认从版本需求第一阶段重新开始。
- 进入项目定位或接口查证前，先列出支撑当前阶段结论所需的最小事实清单，优先按已知文件、接口名、字段名和项目路径定向搜索，禁止默认读取整个仓库或扩大到无关项目。
- 一旦证据已经足以判断前端、后端或全栈范围，或已经暴露会改变开发范围的接口契约缺口，必须先输出阶段结论和进度回执；后续仓库、实现类和测试位置的深入定位放到下一步继续，禁止在用户无感知时持续扩查。
- 比较多个工单的先后顺序时，只查证依赖关系、代码重叠、阻断项和实施风险；一旦顺序已有充分依据，必须立即返回排序结论，禁止在同一轮继续展开所选工单的完整开发方案。
- 连续查证超过 60 秒仍未形成阶段结论时，必须先更新进度看板，说明已查证内容、剩余问题和继续查证的必要性。
- 遇到路径变化、重复超时或连续无结果时，必须停止扩大搜索范围，输出真实阻断和最小补充信息需求；禁止用更多全盘扫描替代阶段回执。
- 工具调用中断、超时或上下文压缩后，必须从已记录证据和剩余最小问题续接；证据版本未变化时禁止重跑已完成检查。

### 1.2 连续阶段合并输出

需求理解获得用户确认后，如果没有来源冲突、高风险缺口或需要用户选择的多种方案，需求拆解、项目定位、代码查证、缺口分析、实现方案和开发准入可以连续执行，并在同一轮合并输出紧凑产物。

合并输出要求：

- 合并只减少重复沟通，不得省略真实检查、字段依据、风险判断和开发准入结论。
- 只展示当前任务实际涉及的层级和有决策价值的“不适用”依据；禁止机械展开大量无关检查项。
- 相邻阶段没有阻断时，不得为每个阶段分别询问“是否继续”；完成实现方案和开发准入后，统一等待一次开发授权。
- 需求理解、方案或开发准入发生实质变化时，必须更新受影响条目；禁止为了沿用合并输出而隐藏冲突。

## 2. 用户确认门禁

以下节点必须等待用户明确确认：

- 需求、接口、设计或用户口头说明之间存在冲突。
- 需要从多个实现方案中选择一种。
- 阶段 6 实现方案和阶段 6.5 开发准入核验完成后，准备开始修改代码；两者合并输出时只等待一次开发授权。
- 阶段 6.5 开发准入核验未通过，或未输出准入核验结果。
- 准备创建或切换开发分支；必须先输出开发分支确认表，等待用户确认目标分支和执行范围后再操作。
- 准备执行 `git add`、`git commit`、`git push` 或部署操作。
- 接口字段、提交结构、权限标识、金额、状态流转、业务分支等高风险内容无法查证。
- 需要采用临时替代接口、临时禁用入口、临时使用空 Options、临时保留 TODO 等会影响用户感知的方案。
- 用户只表达笼统同意，但上一轮内容不是完整开发方案和开发准入核验。
- 需求细节、接口字段、提交结构、权限标识、菜单唯一标识、枚举值、部门 ID、数据源或业务分支仍不明确，且这些内容会影响当前开发批次。

以下节点可由 AI 主动推进：

- 读取用户提供的需求文档。
- 按当前开发范围搜索项目已有文档、前端页面、后端服务、接口、数据模型、Migration、测试和发布配置。
- 整理需求理解核对、需求拆解、待确认清单和实现方案。
- 在用户已确认实现方案后，按既定任务拆分继续开发。
- 执行只读检查、格式化检查、轻量验证和 TODO 搜索。
- 需求理解已确认且无阻断时，连续完成需求拆解、项目定位、缺口分析、实现方案和开发准入，并按“连续阶段合并输出”统一交付。

### 2.1 全局规范优先处理门禁

当缺口、临时处理、占位策略或推进方式已经被全局规则、项目规则、当前工作流或已启用技能明确覆盖时，AI 必须严格按对应规范执行，不得再把同一问题包装成选择题反复询问用户。

执行要求：

- 先识别当前问题是否已有全局规范、项目规范、当前工作流或已启用技能可承接。
- 已有规范可承接时，按规范处理，并在阶段回执、方案或交付说明中明确告知用户“我已按规范这样处理”。
- 不得把规范已经明确的默认策略，改写成“请选择 A / B / C”。
- 不得因为当前规范只列举了部分场景，就把规则理解为固定清单；后续全局规范拓展后，本工作流自动以最新全局规范为准。
- 如果多个规范同时适用，应按优先级执行：用户最新明确指令 > 当前项目规则 > 全局规则 > 当前工作流。
- 如果已完成查证，且没有全局规范、项目规范、当前工作流或已启用技能可以承接，AI 可以向用户提问确认；在用户确认前，禁止自行推断接口、字段、权限、路由、枚举、交互或业务规则。
- 提问时必须说明已查过什么、为什么没有答案、继续发散会带来什么风险，不能只笼统地问“怎么处理”。
- 如果规范之间冲突、规范缺失、或处理结果会影响高风险业务逻辑，必须进入用户确认门禁。

仍需用户确认的情况：

- 需求、原型、接口、用户说明之间存在冲突。
- 当前问题没有可适用的全局规范、项目规范、当前工作流或已启用技能。
- 多种处理方式会造成产品表现、数据语义、提交结构、权限真实值或状态流转差异。
- 即使已有规范，也无法判断当前场景应归属哪个规范。

## 3. 阻断项表达规范

遇到阻断时，必须让用户无需看代码或 diff 也能理解问题。输出格式：

```md
阻断项：
- 问题：
- 影响：
- 当前依据：
- 我已查过：
- 可选处理：
- AI 建议：
```

禁止只说“需要确认一下”。必须说明如果不确认，会影响展示、提交、权限、联调、验收或上线中的哪一环。

## 4. 阶段 1：读取需求

输入可以是在线文档、本地文档、接口文档、需求截图或工单链接。

执行要求：

- 读取完整需求内容，不能只读标题或目录。
- 记录文档标题、版本、来源和读取时间。
- 提取功能点、页面、弹窗、接口、权限、菜单、异常边界和范围外事项。
- 如果文档无法访问、内容为空、只有目录或明显缺页，必须停止并说明，不能假装已掌握需求。

### 4.0 读取加速与来源路由

读取需求资料时，必须先按已沉淀的文档读取经验选择最快的真实正文入口，禁止先从通用网页壳层、前端 bundle 或浏览器 DOM 反向摸索。

执行顺序：

1. 先识别链接类型和资料来源：
   - `gitlabpv.tyhdev.com/#/{projectId}/{path}`：按 `base-docs` 的 GitLab 预览工具规则，直接解析 hash 并请求 `/api/gitlab/file` 获取正文。
   - `alidocs.dingtalk.com`：按 `base-docs` 的钉钉文档接口规则读取正文。
   - Swagger / Knife4j 接口文档：按 `base-docs` 先读 JSON 元数据。
   - 本地项目资料：优先按 `base-docs` 搜索 `docs` / `openspec` / 根目录文档。
2. 已有工作流明确覆盖的来源，必须优先复用对应工作流经验；只有接口返回 401/403/登录页、正文缺失、资源不一致或需要渲染核验时，才升级到浏览器或前端资源反查。
3. 读取大文档时，应先缓存一次正文结果，再从本地缓存分段解析标题、引用资源、差异点和版本信息，禁止为了截取不同段落反复请求同一个远端接口。
4. 读取正文引用的图片、HTML、附件时，先区分是否影响本次页面结构、字段、接口、权限或验收；影响关键理解的资源必须读取或标记阻断，不影响当前阶段的资源可记录为后置输入项。
5. 超时处理必须有限：同一资源最多进行有限重试；重复超时后记录失败资源、失败方式和影响范围，不继续空转。

注意：这里的“经验优先”只用于选择读取入口和资料定位方式；业务字段、接口参数、权限标识、枚举值、提交结构仍必须以需求正文、原型、接口文档、抓包或后端确认为准，禁止按经验推断。

### 4.1 在线文档读取判定

在线文档、知识库、低代码原型、Git 托管预览或 SPA 页面读取时，必须区分“页面可打开”和“正文可读取”。

执行要求：

- 如果浏览器只打开了前端壳层、登录页、空白页、目录页或 hash 路由页面，不能认定为已读取。
- 必须继续查找真实数据来源，例如 raw markdown、下载接口、页面网络请求、导出接口、附件接口或本地缓存文件。
- 读取成功时必须记录文档标题、真实路径 / URL、读取方式、内容长度、版本 / commit / 更新时间。
- 读取失败时必须记录失败资源、失败方式、HTTP 状态 / 报错、已尝试方法和影响范围。
- 遇到超时必须使用有限重试、明确超时、直接数据接口、并发拉取等方式优化；禁止无限等待或反复尝试同一种方式。
- 关键资料最终仍读取失败时，必须阻断并让用户补充可访问内容或确认替代依据。

判断标准：

- 用户不看代码、不看终端，也能知道哪些资料已读、哪些没读、哪些失败、失败会影响什么。
- AI 不能因为“看到了链接名 / 文件名 / 页面标题”就继续推断需求。

阶段产物：

```md
需求读取结果：
- 文档标题：
- 版本：
- 来源：
- 读取时间：
- 主要功能：
- 范围外事项：
```

## 5. 阶段 2：需求理解核对

在进入需求拆解、项目定位、开发方案或编码前，必须先输出一份“需求理解核对”产物，让用户确认 AI 对需求的理解是否正确。

### 5.1 触发条件

只要本次任务存在以下任一输入，就必须执行本阶段：

- 用户提供需求文档、PRD、在线文档、工单或接口说明。
- 需求文档中引用了图片、原型、HTML、附件、截图或设计说明。
- 用户要求“根据需求开发”“梳理要做什么”“正式开始”。
- 当前任务会进入代码修改、接口 mock、路由 / API / 页面生成或联调。

禁止在未完成需求理解核对前直接输出开发方案或开始编码。

### 5.2 必须读取的资料范围

需求理解不能只读 Markdown 正文。必须尽可能读取需求文档引用的所有相关资料：

- Markdown / 文本文档正文。
- 文档中的相对链接、图片、截图、附件。
- HTML 交互原型。
- Figma / 设计图 / 原型图。
- 表格、流程图、Mermaid 图、接口片段。
- 需求正文中声明的 `related_docs`、`related_dev_docs`、关联接口文档、关联原型、附件、截图和设计说明。
- 用户补充说明和聊天中确认过的结论。

如果文档中引用了图片或 HTML 原型，必须尝试实际打开、下载、截图或解析；不能只说“识别到引用”。

如果资源无法访问，必须在产物中标记为“未读取 / 读取失败”，并说明影响范围，禁止假装已经理解。

如果关联资料读取失败，必须判断它是否影响本次页面结构、字段来源、接口链路、权限菜单或复用边界；只要影响，就必须作为阻断项列出。

HTML 原型如果只包含运行壳层或模板占位，不能只按 HTML 文本理解；必须结合截图、渲染结果或可见页面内容判断。

图片原型必须实际打开或截图核验；不能只在 Markdown 中看到图片链接就标记为已读。

### 5.2.1 多来源需求覆盖基线

当需求正文、原型、设计图、附件、接口文档和用户补充相对独立，或内容可能不一致时，“资料已读取”不等于“需求已覆盖”。在输出需求理解核对前，必须先枚举所有来源并建立覆盖基线。

执行要求：

1. 为每份正文、原型页面、Frame、弹窗和状态分支分配来源 ID，例如 `DOC-001`、`PROTO-001`；禁止只按文件级别登记一个笼统的“原型已读”。
2. 独立原型必须逐页、逐弹窗、逐状态枚举；没有被正文引用不能作为省略依据。
3. 同一页面的初始态、编辑态、审核态、异常态、空状态和禁用态等，只要会影响字段、交互或验收，就必须分别登记。
4. 按业务对象、角色、终端、流程节点和生命周期重新归组，不能只按文档章节、文件目录或原型画布位置理解需求。
5. 先取所有来源的功能并集作为候选需求池，再与接口和现有代码比较；禁止只选择正文或某一张原型作为代码对比基准。
6. 每个候选需求必须关联需求 ID，并进入需求拆解、文件级方案、开发任务或明确关闭结论。
7. 后续收到新版正文、原型或用户补充时，必须重新打开受影响条目并执行增量影响分析；禁止继续沿用已经失效的覆盖结论。

资料来源清单：

| 来源 ID | 类型 | 文件 / 页面 / Frame / 状态 | 读取状态 | 版本证据 | 影响范围 |
| --- | --- | --- | --- | --- | --- |

需求覆盖矩阵：

| 需求 ID | 来源 ID | 业务对象 | 角色 / 终端 | 页面 / 状态 | 正文 | 原型 | 接口 | 现有代码 | 差异类型 | 处理结论 | 开发任务 / 验收项 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

每个需求项只允许使用以下闭环状态：

- `待实现`：已确认属于本次范围，尚未完成开发。
- `已有实现，无需修改`：现有代码已满足，并记录代码和验收依据。
- `已确认范围外`：有明确来源依据和用户确认，不属于本次范围。
- `不适用`：目标角色、终端、流程节点或业务对象明确不匹配，并记录判断依据。
- `阻断待确认`：来源冲突或范围不明，等待用户确认。

禁止行为：

- 禁止用“原型已读取”代替逐页、逐状态登记。
- 禁止因正文未提及而删除原型中的功能，也禁止因原型未画而删除正文明确要求的逻辑。
- 禁止只输出功能汇总，不保留来源条目到需求、任务、代码和验收的逐项映射。
- 禁止把尚未分类的需求项静默移出本次范围。
- 禁止用现有代码是否方便实现反向决定需求是否存在。

覆盖统计必须包含：来源条目总数、已归类条目数、待实现数、已有实现数、已确认范围外数、不适用数、阻断待确认数、未覆盖数和覆盖率。

只有“来源条目总数 = 已归类条目数”且未覆盖数为 0，才能认定需求覆盖完成。覆盖率 100% 只表示每个来源条目已有明确去向，不代表所有需求都已确认或已实现。

### 5.2.2 文档与原型不一致处理

发现需求正文与原型不一致时，必须先判断是“互相补充”还是“真实冲突”。禁止一律按冲突处理，也禁止静默选择其中一个来源。

差异分类：

| 类型 | 判断方式 | 处理方式 |
| --- | --- | --- |
| 纯视觉补充 | 原型补充布局、间距、顺序等，不改变功能和数据语义 | 按原型补充展示，并记录依据 |
| 业务逻辑补充 | 正文描述校验、计算或状态流转，原型没有体现但也不矛盾 | 保留正文逻辑，原型未画不代表取消 |
| 单来源功能 | 字段、按钮、页面、弹窗或交互只在一方出现 | 纳入候选需求并等待确认，禁止直接排除 |
| 真实冲突 | 同一功能在两边的必填、显隐、交互、状态或结果不同 | 登记冲突并阻断对应开发范围 |
| 版本差异 | 能证明一方是明确替代旧版本的新版本 | 使用新版本，并保留版本依据和被替代内容 |
| 数据契约差异 | 页面要求与接口字段、类型或提交结构不一致 | 页面表现按确认后的产品结论，数据契约按接口；无法分层时阻断 |

判断顺序：

1. 先定位到同一个比较单元：业务对象、角色、终端、页面、弹窗、字段、按钮、状态或流程节点。
2. 检查两边是否真的表达相反含义；一方没有画出或没有写明，不自动等于冲突或取消。
3. 检查版本号、更新时间、变更记录或“替代旧版”说明。
4. 检查用户是否已经给出最新明确结论。
5. 无法证明优先级时进入冲突台账，等待用户确认。

优先级只允许按“用户最新明确确认 > 有明确替代关系的新版本资料 > 其他来源”处理。禁止默认“文档一定高于原型”，也禁止默认“原型更直观所以按原型”。接口文档只决定接口字段、类型和提交结构，不能代替产品决定页面是否展示、按钮是否存在或交互如何执行。

冲突台账：

| 冲突 ID | 页面 / 状态 | 需求正文 | 原型 | 接口 / 现有代码 | 差异类型 | 影响范围 | AI 建议 | 用户确认 | 最终依据 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

每个冲突必须说明：影响展示、提交、校验、状态流转、权限还是验收；当前能继续分析的无冲突范围；被阻断的页面、功能或开发批次；推荐采用哪一方及其依据；如果采用某一方，另一方哪些内容会被放弃。

用户确认后必须同步更新需求覆盖矩阵、需求理解核对中的用户确认结论、需求拆解、文件级实现方案、开发准入核验和最终验收项。禁止只在聊天中记住结论。

### 5.4 确认门禁

以下情况必须等待用户确认，不能进入开发方案或编码：

- 需求正文和原型 / HTML / 图片不一致。
- 需求表现和接口文档不一致。
- 用户补充说明改变了需求正文。
- 不做内容的原因不明确。
- 关键页面、弹窗、字段、按钮、权限、路由入口理解不完整。
- 需求正文未读取成功。
- 原型资源引用存在但未能读取，且会影响布局、字段顺序或交互判断。
- 关键关联文档未读取成功，且会影响接口、数据来源、复用边界或影响面判断。
- 需求正文、独立原型页面、Frame、弹窗或关键状态没有逐项登记来源 ID。
- 需求覆盖矩阵没有达到 100% 归类，或未覆盖数不为 0。
- 文档与原型差异尚未完成“补充 / 冲突 / 版本差异 / 数据契约差异”分类。
- 真实冲突会影响当前开发范围，且用户尚未确认最终依据。

用户确认后，必须把确认结论写入“用户确认”或“差异处理结论”中，再进入下一阶段。

如果用户明确允许使用项目源码、现有页面或用户口头说明替代未读资料，必须把“替代依据”和“未读风险”写入需求理解核对产物，再进入下一阶段。

### 5.5 用户补充后的回写要求

当用户在需求理解阶段补充或纠正信息时，AI 必须更新需求理解核对产物中的对应条目，而不是只在聊天里临时记住。

用户补充改变已有正文、原型或覆盖结论时，还必须同步更新资料来源清单、需求覆盖矩阵和冲突台账；受影响的任务、方案和验收项必须重新打开并进行增量影响分析。

## 6. 阶段 3：需求拆解

执行要求：

- 先明确当前开发范围是前端、后端还是全栈，并记录判断依据；范围不明确且会改变交付内容时必须等待用户确认。
- 按页面、弹窗、接口调用、后端服务、数据模型、Migration、权限点、菜单路由、状态流转、异常边界、测试和发布影响拆解。
- 每个开发任务必须引用需求覆盖矩阵中的需求 ID；每个需求 ID 必须映射到开发任务或明确关闭结论，禁止两边存在孤立项。
- 同一需求涉及多个角色、终端、流程节点或状态时，必须分别拆解影响面；禁止默认只实现当前代码所在的一端或一个节点。
- 区分前端要做、后端要做、只需联调、不在本次范围内。
- 需求中只说明页面表现时，不能反推接口字段。
- 需求中只说明接口资产时，不能反推页面交互。

阶段产物：

```md
- 前端新增弹窗：
- 前端新增接口调用：

- 发布与回滚影响：
- 权限点：
- 菜单/路由：
- 后端依赖：
- 不在本次范围：
```

### 6.1 PingCode 子任务标题生成（可选）

当用户提出“生成 PingCode 子任务 / 任务拆解 / 复制批量建任务”时，允许在需求拆解阶段额外输出一组可复制的子任务标题。

拆解口径必须以前端交付边界为主，默认按页面可交付能力拆分，不按后端接口、菜单资源或权限点机械拆分。

执行要求：

1. 简单配置类页面默认每个菜单模块拆成两条：
   - `列表页、删除、启用/停用`
   - `添加/编辑`
2. 输出标题格式为：`一级菜单>二级菜单>...>页面名称，任务内容`。

## 10. 阶段 7：分批开发

进入阶段 7 前必须同时满足：

- 阶段 6 实现方案已经输出。
- 阶段 6.5 开发准入核验已经通过。

- 仍待确认项不阻断当前开发批次，或已按规范记录为后置输入项 / 已按规范处理。

如果不满足以上条件，AI 只能继续补充方案、更新需求核对产物和进度看板，禁止开始任何业务代码修改。

### 10.1 开发分支确认与准备

用户明确授权进入开发后、首次修改业务代码前，AI 必须根据项目定位结果，对本次涉及的每个 Git 仓库执行开发分支准备。

如果当前仓库已经位于用户在本次需求或同一连续工单上下文中确认过的目标分支，且工作区、未推送提交和远端跟踪状态相对上次确认没有变化，则直接复用分支结论，不重复输出分支确认表；仍须执行只读复查并在进度看板中简要说明。只有需要创建、切换或调整分支，或仓库状态发生变化时，才进入下面的两阶段确认流程。

#### 第一步：只读检查并等待确认

用户确认前，只允许执行项目定位和 Git 只读检查，禁止创建、切换、删除或重命名分支。

必须检查：

- 仓库路径和当前分支。
- 已暂存、未暂存和未跟踪的文件。
- 当前分支相对上游分支的未推送提交。
- 本地及远端是否存在 `main` 和建议目标分支。
- 仓库已有的分支命名规范。

AI 可以根据已确认的需求编号、工单编号、任务标识及仓库命名规范提出建议分支名，但建议分支名必须由用户确认。没有可靠命名依据时，填写“待用户指定”，禁止自行编造。

创建或切换分支前必须输出：

| 项目 | 仓库路径 | 当前分支 | 建议目标分支 | 基于分支 | 未提交变更 | 未推送提交 | 建议动作 | 阻断项 / 说明 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

输出表格后必须停下来，等待用户确认以下内容：

- 每个项目的目标分支名。
- 哪些项目需要创建或切换分支。
- 存在未提交或未推送内容时的处理范围。

“进入开发”“继续”“按你的建议走”等指令不能替代本次分支确认。只有用户在看到确认表后明确表示“确认按表执行”“确认创建并切换”或给出调整后的分支名，才允许执行分支操作。

#### 第二步：确认后执行并输出结果

用户确认后，逐个仓库执行：

1. 重新检查仓库状态；如果状态相对确认表发生变化，停止处理对应仓库并重新让用户确认。
2. 工作区干净时，更新已确认的远端 `main` 引用。
3. 当前已在目标分支时，不重复创建。
4. 本地目标分支已存在时，切换到该分支。
5. 远端目标分支已存在时，建立本地跟踪分支并切换。
6. 目标分支不存在时，从最新远端 `main` 创建并切换目标分支。
7. 存在未提交变更时，禁止自动 stash、提交、重置、丢弃或携带变更创建分支；该仓库标记为未新建。
8. 存在未推送提交但工作区干净时，保留并输出提交信息，不自动推送；其他安全的分支操作可以继续。
9. 单个仓库失败时继续处理其他仓库，禁止因为一个项目失败而跳过全部项目。

执行后必须输出：

| 项目 | 仓库路径 | 原分支 | 确认目标分支 | 未提交变更 | 未推送提交 | 分支结果 | 原因 / 说明 |
| --- | --- | --- | --- | --- | --- | --- | --- |

所有项目必须各占一行，包括：

- `已新建并切换`
- `未新建（已存在并切换）`
- `未新建（已在目标分支）`
- `未新建（阻断）`

未新建的项目必须说明原因和对开发的影响。未成功切换到用户确认分支的仓库，禁止修改业务代码。

建议按业务纵向切片推进；每个切片只执行当前开发范围适用的步骤：

1. 确认接口契约、错误语义和验收基线。
2. 完成数据模型与 Migration（如涉及）。
3. 完成后端服务、接口、鉴权及后端测试（如涉及）。
4. 完成前端接口接入、页面和交互（如涉及）。
5. 完成契约测试、前后端联调和端到端验证。
6. 完成发布说明、回滚方案和可观测性检查。

每批开发结束必须输出：

```md
本批完成：
- 当前开发范围：
- 需求 ID：
- 修改文件：
- 完成功能：
- Migration / 数据影响：
- 测试与验证：
- 待联调项：
- AI 业务推导项：无 / 推导前告知、实际落点、前后变化和确认状态
- 下一批：
```

执行要求：

- 每批只做当前批范围，禁止顺手优化老代码。
- 每批必须维持接口、代码和数据的过渡期兼容；无法兼容时必须停下来说明发布窗口和阻断范围。
- 每批结束必须把需求 ID、代码文件、实现状态和验证结果回写需求覆盖矩阵；禁止只维护聊天中的完成清单。
- 每批结束必须回看 diff，确认没有误删注释、误改旧逻辑或混入无关变更。
- 每批结束必须执行新增业务判断依据审计；本批实际落地的推导必须完成推导后告知，新增、调整、取消或移除的推导必须逐项说明，禁止延迟到最终交付才汇报。
- 修改代码后必须按项目已有格式化 / lint 工具处理本次修改文件；无法执行时必须说明。

## 11. 阶段 8：联调闭环

执行要求：

- 按接口逐个验证请求方法、路径、参数、响应字段、错误码、鉴权和调用位置。
- 字段必须来自当前目标接口，禁止跨接口硬凑。
- 缺字段必须显性标记并反馈。
- 联调阶段禁止遗留 `TODO待联调_`；接口文档不存在的字段必须使用 `TODO无此联调字段_用途描述`。
- 后端范围必须验证服务端校验、权限拒绝、事务回滚、重复请求、幂等和并发边界。
- 涉及 Migration 时必须验证历史数据、兼容窗口、重复执行、部分失败和恢复路径。
- 涉及缓存、队列、异步任务或第三方系统时，必须验证超时、重试、失败终态、缓存失效和日志关联标识。
- 全栈范围必须验证前端、后端、数据库和异步任务在实际发布顺序下仍保持兼容；禁止只验证最终全量版本。

阶段产物：

```md
联调记录：
- 接口：
- 请求参数：
- 响应字段：
- 错误码与鉴权：
- 前端 / 后端使用位置：
- 事务、幂等与并发：
- Migration 与历史数据：
- 缓存、队列与异步任务：
- 日志与可观测性：
- 问题：
- 处理结论：
```

## 12. 阶段 9：验收收口

执行要求：

- 按需求功能点逐项勾验。
- 必须从正文、每个独立原型页面 / Frame / 状态和用户确认记录的来源 ID 反向逐项验收；禁止只从已经完成的代码正向总结功能。
- 每个来源条目必须能追踪到需求 ID、开发任务、代码文件和验收结论；每个代码改动也必须能反向关联需求 ID。
- 按 AI 能力发散审计逐项验收已授权能力、能力对等结论、共享业务实现与客观数据边界例外；未确认接口、字段、权限、枚举或写操作不得伪装为已验收能力。
- 覆盖权限、异常、空状态、边界值、加载态和失败提示。
- 按当前开发范围执行单元、集成、契约和端到端验证；无法执行的层级必须说明原因、影响和替代证据。
- 涉及数据库变更时，必须验收 Migration、历史数据处理、重复执行、恢复路径和不可逆风险。
- 验收发布顺序、健康检查、观察指标、失败判定和回滚触发条件；禁止把回滚代码等同于恢复数据。
- 执行与项目风险匹配的验证、格式化检查和 TODO 搜索。
- 必须反向审计新增业务判断是否有需求依据或已完成双向告知，确保未披露 AI 业务推导项为 0；非 0 时不得验收闭环。
- 如果当前项目是 Vite 前端项目，默认不执行 full build；除非用户明确要求或任务目标需要。

阶段产物：

```md
验收清单：
- 需求功能点覆盖：
- 资料来源反向验收：
- 需求覆盖矩阵闭环：
- 未覆盖项：0 / 非 0
- 文档与原型冲突结论复核：
- AI 能力发散审计结论：
- 新增业务判断依据审计：
- AI 业务推导双向告知记录：
- 未披露 AI 业务推导项：0 / 非 0
- 已授权能力进入方案/任务/验收：
- Chat/MCP 等多入口能力对等与客观数据边界例外：
- 多入口共享业务服务、输入归一、输出白名单、超时与错误语义：
- 单元 / 集成 / 契约 / 端到端测试：
- Migration 与历史数据：
- 发布顺序与回滚方案：
- 健康检查与可观测性：
- 权限矩阵：
- 搜索/分页/详情/编辑：
- 异常场景：
- TODO 搜索：
```

## 15. 常用用户指令

用户可以用以下短指令推进：

- `继续`：只推进当前工作流的下一步；如果阶段 6 或阶段 6.5 未完成，不代表授权编码。
- `按你的建议走`：接受当前推荐方向；如果当前推荐方向不是完整阶段 6 方案和阶段 6.5 准入核验，不代表授权编码。
- `这里调整为：xxx`：修改当前阶段方案。
- `先暂停`：停止推进，只保留当前进度看板。
- `进入开发`：仅在阶段 6 方案完成且阶段 6.5 准入核验通过后，才表示进入开发分支准备；必须先输出开发分支确认表，不能直接创建分支或修改代码。
- `提交推送`：在交付后按 Git 规范执行提交和推送。
