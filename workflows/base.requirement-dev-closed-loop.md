# 需求文档驱动开发闭环工作流

当用户提供需求文档、在线文档、工单、PRD、接口文档或设计说明，并要求基于当前项目梳理、开发、联调、验收时，使用本工作流。

本工作流的目标不是只完成用户当前点名的一小步，而是由 AI 主动维护进度、暴露缺口、推动下一步，直到需求进入可交付闭环。

## 0. 最高优先级原则

- 必须先读取需求文档，再进入代码设计或编码。
- 必须区分事实、推断、缺口和冲突，禁止把未确认内容写成确定逻辑。
- 必须维护进度看板，用户不需要主动追问“当前做到哪一步、还缺什么”。
- 必须按阶段推进；每个阶段结束后输出阶段回执。
- 没有阻断项时，AI 应主动进入下一阶段；存在阻断项时，必须说明影响、已查证内容和建议选择。
- 需要修改代码、提交、推送、部署或处理高风险业务逻辑前，必须等待用户明确确认。

## 1. 触发后的进度看板

进入工作流后，AI 必须持续维护进度看板。阶段切换、遇到阻断、完成一批开发或准备进入下一步时，必须输出：

```md
进度看板：
- 当前阶段：
- 已完成：
- 正在处理：
- 下一步：
- 阻断项：
- 需要用户确认：
- AI 建议：
```

进度看板必须体现真实状态；禁止只给笼统描述，例如“继续开发中”。

## 2. 用户确认门禁

以下节点必须等待用户明确确认：

- 需求、接口、设计或用户口头说明之间存在冲突。
- 需要从多个实现方案中选择一种。
- 准备开始修改代码。
- 准备执行 `git add`、`git commit`、`git push` 或部署操作。
- 接口字段、提交结构、权限标识、金额、状态流转、业务分支等高风险内容无法查证。
- 需要采用临时替代接口、临时禁用入口、临时使用空 Options、临时保留 TODO 等会影响用户感知的方案。

以下节点可由 AI 主动推进：

- 读取用户提供的需求文档。
- 搜索项目已有文档、路由、API、组件和相似页面。
- 整理需求拆解、待确认清单和实现方案。
- 在用户已确认实现方案后，按既定任务拆分继续开发。
- 执行只读检查、格式化检查、轻量验证和 TODO 搜索。

## 3. 阻断项表达规范

遇到阻断时，必须让用户无需看代码或 diff 也能理解问题。输出格式：

```md
阻断项：
- 问题：
- 影响：
- 当前依据：
- 我已查过：
- 可选处理：
- AI 建议：
```

禁止只说“需要确认一下”。必须说明如果不确认，会影响展示、提交、权限、联调、验收或上线中的哪一环。

## 4. 阶段 1：读取需求

输入可以是在线文档、本地文档、接口文档、需求截图或工单链接。

执行要求：

- 读取完整需求内容，不能只读标题或目录。
- 记录文档标题、版本、来源和读取时间。
- 提取功能点、页面、弹窗、接口、权限、菜单、异常边界和范围外事项。
- 如果文档无法访问、内容为空、只有目录或明显缺页，必须停止并说明，不能假装已掌握需求。

阶段产物：

```md
需求读取结果：
- 文档标题：
- 版本：
- 来源：
- 读取时间：
- 主要功能：
- 范围外事项：
```

## 5. 阶段 2：需求拆解

执行要求：

- 按页面、弹窗、接口调用、权限点、菜单路由、状态流转、异常边界拆解。
- 区分前端要做、后端要做、只需联调、不在本次范围内。
- 需求中只说明页面表现时，不能反推接口字段。
- 需求中只说明接口资产时，不能反推页面交互。

阶段产物：

```md
需求拆解清单：
- 前端新增页面：
- 前端新增弹窗：
- 前端新增接口调用：
- 权限点：
- 菜单/路由：
- 后端依赖：
- 不在本次范围：
```

## 6. 阶段 3：项目定位

执行要求：

- 查当前项目已有相似页面、路由、API、组件、权限和样式写法。
- 明确本次建议新增或修改的文件位置。
- 区分“项目已有事实”和“AI 建议命名”。
- 使用非当前文件内组件、函数、Hook 或工具前，必须查源码、类型定义或项目已有真实用法。

阶段产物：

```md
项目定位：
- 相似页面：
- 路由文件：
- API 文件：
- 组件复用：
- 推荐新增目录：
- 待确认命名：
```

## 7. 阶段 4：缺口与冲突确认

执行要求：

- 汇总所有会影响开发的疑点。
- 按风险分级：阻断开发、可先静态占位、可后续联调。
- 明确每个疑点的影响范围和建议处理方式。
- 高风险缺口必须进入用户确认门禁。

阶段产物：

```md
待确认清单：
- 问题：
  影响：
  当前依据：
  需要谁确认：
  未确认前处理方式：
```

## 8. 阶段 5：前端方案设计

执行要求：

- 给出文件级实现方案。
- 明确新增文件、修改文件、复用组件、接口调用链和权限挂载方式。
- 标明 TODO / 占位策略。
- 方案未确认前，不进入编码。

阶段产物：

```md
前端实现方案：
- 路由：
- 页面：
- 弹窗：
- API：
- 权限：
- 组件复用：
- 待确认占位：
```

## 9. 阶段 6：分批开发

建议顺序：

1. API 层与类型。
2. 路由与菜单挂载。
3. 主列表 / 看板页面。
4. 弹窗 / 详情页。
5. 权限、空状态、异常状态。
6. 联调修正。
7. 格式化和轻量验证。

每批开发结束必须输出：

```md
本批完成：
- 修改文件：
- 完成功能：
- 待联调项：
- 下一批：
```

执行要求：

- 每批只做当前批范围，禁止顺手优化老代码。
- 每批结束必须回看 diff，确认没有误删注释、误改旧逻辑或混入无关变更。
- 修改代码后必须按项目已有格式化 / lint 工具处理本次修改文件；无法执行时必须说明。

## 10. 阶段 7：联调闭环

执行要求：

- 按接口逐个验证请求参数、响应字段、错误状态和页面使用位置。
- 字段必须来自当前目标接口，禁止跨接口硬凑。
- 缺字段必须显性标记并反馈。
- 联调阶段禁止遗留 `TODO待联调_`；接口文档不存在的字段必须使用 `TODO无此联调字段_用途描述`。

阶段产物：

```md
联调记录：
- 接口：
- 请求参数：
- 响应字段：
- 页面使用位置：
- 问题：
- 处理结论：
```

## 11. 阶段 8：验收收口

执行要求：

- 按需求功能点逐项勾验。
- 覆盖权限、异常、空状态、边界值、加载态和失败提示。
- 执行轻量验证、格式化检查和 TODO 搜索。
- 如果当前项目是 Vite 前端项目，默认不执行 full build；除非用户明确要求或任务目标需要。

阶段产物：

```md
验收清单：
- 需求功能点覆盖：
- 权限矩阵：
- 搜索/分页/详情/编辑：
- 异常场景：
- TODO 搜索：
- 格式化：
- 验证命令：
```

## 12. 阶段 9：交付说明

最终回复必须包含：

```md
完成内容：
- ...

验证：
- ...

待确认：
- ...

发散点：
- 无 / ...
```

如果存在 AI 推断、临时占位、接口缺失、权限缺失或未联调字段，必须写在“发散点”或“待确认”里。用户不看 diff 也必须知道哪些内容尚未完全确认。

## 13. 阶段回执

每完成一个阶段，必须输出阶段回执：

```md
阶段回执：
- 本阶段完成：
- 产物：
- 发现的问题：
- 是否阻断：
- 下一阶段：
```

如果无阻断，应主动说明将继续进入下一阶段；如果有阻断，应给出建议选择并等待用户确认。

## 14. 常用用户指令

用户可以用以下短指令推进：

- `继续`：按当前工作流进入下一步。
- `按你的建议走`：接受 AI 当前推荐方案。
- `这里调整为：xxx`：修改当前阶段方案。
- `先暂停`：停止推进，只保留当前进度看板。
- `进入开发`：在方案已确认后开始修改代码。
- `提交推送`：在交付后按 Git 规范执行提交和推送。
