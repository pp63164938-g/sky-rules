# 全栈开发

从拿到需求到需求结束，按一条用户链路收口。先看现在怎么跑，再定要改成什么样。后端、前端、数据、兼容和验证属于同一条链路，不按仓库或当前打开的文件拆开交差。

```text
读需求 → 看现状 → 划定链路 → 定契约和数据 → 定兼容与影响面 → 出方案 → 实现 → 联调与回归 → 收口
```

事实没齐，不出确定方案。方案没出，不写实现。相邻阶段没有阻断、也不需要用户决策时，连续做完并汇报。有阻断时停在当前阶段，说明缺什么、影响什么、建议怎么处理。

本 skill 只排全栈顺序。语言、注释、前端组件、i18n、Git 仍走已有规则，不在这里重写。

做需求走下面九步。修已经在跑的问题走「修复」，不套九步，也不把修复扩成一次需求重做。

用户显式要求 `base-requirement-dev-closed-loop` 时，走那个工作流，不用本 skill 替代它的阶段和看板。用户显式要求 `base-pingcode-fix-bug` 时，走那个工作流。

## 1. 读需求

先读需求文档、原型、用户说明和已有接口文档。没读完会影响页面、字段、接口或验收的资料，不进入方案，也不进入编码。

分清四类，不把推断写成事实：

- 事实：文档、原型、接口、代码或表里已经写明的
- 推断：为了接上链路临时补的规则
- 缺口：需求要，但契约或表里没有
- 冲突：需求、接口、现有页面结论互相否定

页面文案、展示和交互按需求。路径、字段、类型、枚举、提交结构按接口文档、抓包或后端确认。两边冲突会影响做不做、传不传、调哪个接口时，停下来让用户定。

## 2. 看现状

读完需求后先看线上或当前代码实际怎么跑，再设计。没有现状，就容易按文档重做一版。

至少看清：

- 当前页面从哪进入，现在调哪个接口
- 这个接口现在的入参、出参、失败返回
- 数据现在在哪张表，关键列和一条真实数据是什么
- 需求要改的是其中哪一段

现状和需求不一致时，并列两者让用户定。不用文档覆盖已经在跑的事实，也不用线上事实否定需求。

## 3. 划定链路

先写清这一次的用户链路，再决定改哪些文件。

一条链路至少写明：

- 谁在什么页面做什么
- 调哪个接口
- 读写哪张表的哪些列
- 成功时用户看到什么，失败时用户看到什么
- 这次不包含什么，以及为什么不包含

同时找出这条数据的其他读写方，不只看当前页面：

- 定时任务、导入、导出、消息消费、别的服务、报表
- 会读或写同一张表、同一字段的已有接口

一条链路能一次验收，就一次做完。跨多条独立业务链路，或写入语义还没定时，先拆开，不混在一个 diff 里。

## 4. 定契约和数据

没有契约和数据结论，不写方案里的确定设计。

- 字段、类型、枚举、错误码只来自接口文档、抓包、后端确认、当前仓库已有实现、当前表结构。
- 列表、详情、配置、预览、字典是不同接口。一个接口的字段不能补另一个接口。
- 两端都由本次负责时，不另等一个不存在的后端。契约由需求、当前表和同类实现定下来，写进字段表，这就是本次确认。
- 同一次改动同时拥有提交、返回和落库，且已有契约、表、枚举都没有这个字段名时，按「全栈自有契约可生成正式字段」生成一个正式名。请求、响应、表单、落库用同一个名字，不另做映射。开发前说明名字和落点，交付时单列。本条不放行枚举值、接口路径、权限标识和下拉数据源。
- 只改一端、已有契约已有名字、或只是「可能以后要用」时，不生成字段名。需求要但没有名字，标 `TODO无此联调字段_用途描述`。
- 先锁定同类实现，读完 URL、入参、Service、表、返回、失败返回和权限校验。新接口沿用这个分层和错误返回，不从零另起一套。没有同类实现、也没有接口文档时，不从零设计分层、错误码或枚举。
- 能连库时核对列、主键和一条真实数据。列不存在就停。不能连就写明未核对。
- 文档和表不一致时，并列两者让用户定。
- 时间字段确认时区、单位和格式。金额字段确认单位和精度。状态字段确认每个值的含义。这三项没确认，不写进确定方案。
- 接口字段用 `Integer` 或 `String`，不把枚举类型直接写进接口字段。
- 会进接口、会分支、有文案的取值，复用已有枚举，用 `XxxEnum.ITEM.getCode().equals(value)` 判断。不在 Service 里再写一套 `private static final int`。已有枚举盖不住时，不套残缺枚举，也不补未确认的值。
- 入参或出参有变化时，按当前开发分支的 `vx.x.x` 给该方法加版本 tag，沿用仓库已有 `@ApiOperation` 写法。分支对不上就问。
- 长整型 ID 当不透明标识透传。前端不 `Number()`。

这一阶段的产物是一张本次字段表：字段名、类型、属于哪个接口的哪条路径、对应哪张表哪一列、依据。依据不足的行不写进确定方案。按上一条生成的正式名单独标成「本次生成」，不伪装成已有契约。

## 5. 定兼容与影响面

方案之前先判断。不涉及就写「不涉及」，禁止跳过。新功能且没有旧行时，写明「无旧数据」。

旧数据：

- 旧行有多少，缺什么，脏数据长什么样。先只读预览，不直接刷。
- 旧行在新代码上会展示错、提交错、算错，还是只是空值。
- 处理方式只选一种：兼容读取、默认值、回填、改名搬迁、双写后再切、人工处理、明确不处理。
- 回填值从哪来。没有来源就不编默认值。
- 能否重复执行。中断后怎么续，失败怎么恢复。
- 刷数脚本和业务代码分开。不把一次性修复写进线上请求链路。

其他影响：

- 其他读写方是否仍按旧字段写。会写坏就先改那些入口，或让新列可空。
- 缓存：有没有旧值。有的话写明 key、失效时机，以及库更新后还会返回旧值多久。
- 权限和菜单：接口权限、数据归属、菜单入口、按钮资源。前端把按钮藏掉不算完成。
- 数据隔离：查询和写入沿用现有租户、组织、软删除条件。不写出一条绕过现有隔离的查询。
- 索引和唯一约束：新查询条件、新排序、新的业务唯一键才需要判断。唯一约束要同时看脏数据会不会让变更失败。
- 字典、错误码、配置：新枚举或新错误是否已有承载。没有就不编。

上线与回滚：

- 不默认前后端和表一起发。
- 加可空列、旧代码不读它：可以先上表，再上后端，再上前端。
- 旧代码会写坏新列，或新代码依赖回填后的旧行：先兼容，再回填，再切新代码，最后才删旧列。
- 灰度期间新旧实例会同时在线。新列必须让旧实例能继续写，旧实例不能把新列写坏。
- 做不到新旧同时兼容：写明维护窗口、谁会受影响、先发哪一端。
- 回滚代码不等于恢复数据。写明代码退回后，新列和已回填数据怎么处理。不能安全回滚时，写明只能前向修复。

需求里出现导入、导出、异步通知、审计或明确的性能要求时，方案里单独写触发时机、失败后用户怎么感知、能不能重试。没有这些要求就写「不涉及」，不预做。

## 6. 出方案

方案出在实现之前，出在第 1 到第 5 步之后。它不是需求复述，也不是写完代码后的说明。

用户刚拿到需求就要求出方案时，也先做完查证再出。查证有阻断时，方案只列缺口和待确认项，不把未知写成设计。

方案至少写明：

- 现状：现在怎么跑
- 链路：改成什么样，不改什么
- 字段表：字段、类型、接口路径、表列、依据
- 数据改动：不改表，或加列、改列、索引、唯一约束
- 旧数据结论，以及其他读写方、缓存、权限菜单、数据隔离是否涉及
- 失败时用户看到什么。重复提交会怎样
- 上线顺序和回滚
- 验收标准：每条都能用一次操作验证，至少覆盖成功、失败、旧数据或「无旧数据」
- 回归范围：同一页面的旧操作，以及方案里写明的其他读写方
- 需要用户拍板的点。没有就写「无」

确认门禁：

- 有多种做法且结果不同，或包含改表、刷数、回填、新权限、发布顺序取舍：出方案后停，等用户确认再实现。
- 做法只有一种，且用户本轮已经授权做这个需求：方案写进回复后继续实现，不重复问「方案可以吗」。
- 用户已经确认过的方案，不重复提请审核。范围或事实变了，重新出受影响的部分。

## 7. 实现

按已确认方案改，不在实现时另起一套设计。

实现中发现字段、表或权限和方案对不上，停回第 4 步。不在代码里悄悄换字段、换查询或加兜底。

后端：

- Controller 只做协议适配和参数绑定。业务判断放 Service。
- 查询条件、排序字段走白名单或类型约束，不拼接未参数化 SQL。
- 身份从服务端上下文取，不信任请求体里的用户 ID、租户 ID。
- 响应显式组装，只返回本次契约字段，不直接返回实体。
- 写入前先定事务和幂等。失败不能留下半条数据。事务里不调外部接口。
- 不重构无关老代码，不改鉴权框架，不关鉴权。

前端：

- 只消费本次字段表里的字段。表单字段名和接口字段名保持一致，提交时不再映射一套。
- 页面文案按需求，绑定字段按契约。
- 表格、搜索、回显、提交、刷新都要走到新字段。旧字段不再被当前页面消费。
- 需求要展示但契约没有、且本次也不能按第 4 步生成正式名的字段，保留位置并标 `TODO无此联调字段_用途描述`，不拿别的接口或本地计算补。

注释只写业务事实。禁止把沟通过程和「为了方便前端」写进代码。只为本地跑起来改的地址、请求头、开关，不进业务提交。

下面这些先写在方案里，等用户明确授权再执行，不在未授权时写库：

- 刷数、回填、改历史数据
- 新表、改表、删列、改列类型
- 新服务、新权限、批量写入、多表事务

## 8. 联调与回归

按验收标准逐条打，不按文件声称完成。先用一条真实数据把接口打通，再从页面走同一条。两端仓库分开时，收口分别说明改了哪一边。

- 只读：正常参数、缺字段、查不到、无权限。返回和库里同一条数据对得上。
- 写入：再验证失败回滚，以及重复提交不会产生第二份业务结果。
- 旧数据：至少拿一条旧行走新页面和新接口。需要回填时，先核对预览数量和一条回填结果，不拿「脚本跑完」当验收。
- 回归：同一页面改动前就能做的操作还要能做。方案里写了涉及的其他读写方、缓存、权限菜单，都要验证到。
- 前端：从页面操作走到接口，再走到表里的那一列。失败时用户看到的提示和方案一致。

没打通的请求写「未验证」和原因，不写成已完成。

## 修复

已经在跑的链路出了问题，走这里。不套上面九步，也不顺手把页面或接口重做一遍。

先复现，再改。复现不了，不改代码。

```text
复现 → 定源头 → 只改源头 → 用同一条数据验证
```

复现要拿到同一条数据上的三样东西：页面怎么操作、接口实际入参和返回、库里那一列现在的值。缺哪样就停，说明缺什么、怎么拿到。不拿「可能是字段空」当原因。

源头只定一处：

- 前端传错、展示错、没刷新：只改前端
- 后端算错、查错、写错、权限判错：只改后端
- 契约两边不一致：先写明哪边和已确认契约不符，再改不符的那一边。两边都没有依据时，停下来给候选，不选一个看起来能用的
- 库里的值和代码都对不上：这是数据问题。先只读对出这一条，修数等授权。不在页面或接口里加兜底把错值藏掉

修的时候：

- 只改让这条复现消失的代码。不重构旁边的老逻辑，不补一套新交互。
- 前端不拿默认值、本地计算、别的接口把后端的错盖住。后端不为了迁就一个传错的页面放宽校验。
- 不加 `?.`、空 `catch`、`if (!data) return` 让报错消失。报错还在，说明源头没找到。
- 同一原因要改前端也要改后端时，两处都只服务这一处源头。改完分别说明改了哪一边。
- 修着修着发现要加字段、改表、改旧数据：停，改走做需求的第 4 步。不在修复里把范围扩成一次需求。

验证用复现时的同一条数据，再走一次原来的操作。页面、接口返回、库里那一列三者一致，才算修好。没复现到的相关路径写「未验证」。

## 9. 收口

需求结束要同时满足：

- 验收标准逐条有结果：通过、明确不做、或仍是缺口
- 后端字段和前端消费一致
- 未验证项没有伪装成通过
- 用户不看 diff 也能知道改了哪个接口、哪张表哪一列、哪个页面
- 旧数据、其他读写方、缓存、权限菜单、上线顺序和回滚都有结论。不涉及也要写明
- 本次生成的正式字段名已单列。没有就写「新字段：无」
- 下一步是合并、刷数、联调，还是等授权

没满足就还在对应阶段，不宣布需求结束。

生产发布走现有发布平台。本 skill 只定顺序和回滚，不代替发布操作。
