# Kunlun 页面生成工作流（kl.gen-page）

适用于 `skyline-kunlun-ui-main` 中标准列表页、搜索区、表格、Tab、详情页、弹窗和对应数据链路的生成或结构性改造。纯文案、单点样式和不影响标准骨架的局部修复不需要机械执行全部页面生成流程。

## 0. 核心不变量

- 先确认项目、需求文档和接口依据，再选择页面模板；未确认项目时禁止套用 Kunlun 专属结论。
- 标准页面必须以当前项目 `src/components/dev-template/` 中匹配场景的源码为骨架，保留模板的 SFC 顺序、组件生态、数据链路和默认职责。
- 只实现用户、需求文档、接口文档、抓包或项目真实代码能够证明的内容；禁止猜测字段、接口、枚举、权限、唯一标识、路由参数和导入路径。
- 全局规则是通用约束的唯一口径。本工作流只维护 Kunlun 的执行顺序和项目专属事实，不复制第二套枚举、注释、API 类型、Mock、样式或禁止发散规则。
- 引用资料描述的组件能力、默认值或目录结构与当前项目源码不一致时，以当前源码和类型定义为事实依据，暂停套用失效结论并向用户说明需要更新 `sky-rules`；禁止在业务代码中静默兼容新旧事实。

## 1. 前置确认与模板选择

1. 先按 `base-project-context` 确认当前项目为 `skyline-kunlun-ui-main`，并读取本次任务相关需求文档。
2. 根据页面结构读取当前项目中的对应模板，禁止使用某台电脑的绝对路径：

| 页面场景 | 必读模板 |
| --- | --- |
| 搜索 A 标准列表 | `src/components/dev-template/list-a.vue` |
| 搜索 B 折叠列表 | `src/components/dev-template/list-b.vue` |
| Tab 页面 | `src/components/dev-template/tab-template/index.vue` 及命中的 Tab 子模板 |
| 详情页面 | `src/components/dev-template/detail.vue` |
| 新增 / 编辑弹窗 | `src/components/dev-template/dialog/dialog-update.vue` |
| 复杂弹窗目录化 | `src/components/dev-template/dialogs/README.md` |

3. 模板或项目组件被使用前，必须读取源码、类型定义或项目文档，确认 Props、默认值、返回结构和副作用；其他页面用法只能作为定位线索。
4. 开发前向用户说明本次实际生效的模板、引用资料和会改变实现路径的项目约束；已有唯一正确路径时，告知后直接执行。

## 2. 按场景读取引用资料

只读取当前任务命中的引用文件；同一任务命中多个场景时，逐个完整读取。禁止因为主工作流已读完就跳过命中的引用，也禁止无差别加载全部引用。

| 当前改动 | 必读引用 |
| --- | --- |
| 列表、搜索、表格、汇总、导出、表头操作 | [列表与表格](references/kl-gen-page--list-and-table.md) |
| 新增 / 编辑弹窗、表单、上传、复杂弹窗拆分 | [表单与弹窗](references/kl-gen-page--forms-and-dialogs.md) |
| 详情、Tab、路由、跨页带入、动态页签 | [详情与导航](references/kl-gen-page--detail-and-navigation.md) |
| API、字段、Options、权限、Mock、类型定义 | [API 与数据契约](references/kl-gen-page--api-and-data.md) |
| 公共组件、标签、长文本、空值、Element Plus namespace | [组件与展示](references/kl-gen-page--components-and-display.md) |

## 3. 实施顺序

1. 按需求确定页面展示、交互和模块顺序；按接口文档、抓包或后端确认确定数据契约。
2. 复制匹配模板的结构和 SFC 块顺序，再做需求要求的最小增删；禁止外拆模板内联配置或改造模板原生数据生态。
3. 使用项目公共组件、Hook、工具函数和 API 结构前先查源码；项目能力可覆盖时直接复用，不重复实现。
4. 静态开发缺少接口时保持正式组件调用链，只在 API 层 Mock；联调时清理 Mock 和 `TODO待联调_`，缺失契约升级为 `TODO无此联调字段_用途描述` 并显性反馈。
5. 新建页面时检查路由可达性；详情、弹窗、批量操作、权限和唯一标识按命中的引用资料处理。
6. 仅格式化和验证本次修改文件，不运行无关的全项目重检查；Vite 项目未经用户要求不执行完整构建。

## 4. 优先级与冲突处理

按以下顺序处理约束：

1. 用户最新明确确认、需求文档和接口契约的分层结论。
2. 全局 P0 红线和项目专属全局规则。
3. `dev-template`、组件源码和类型定义能够证明的当前项目事实。
4. 本主工作流的核心不变量与执行顺序。
5. 当前任务命中的引用资料。

当第 4、5 项依赖的项目事实被第 3 项证明已经变化时，不继续套用旧结论；先说明失效位置、当前源码事实、影响范围和正确路径，再按规则维护流程更新源工作流。

## 5. 交付前检查

- 已确认项目、需求文档、目标模板和命中的引用资料。
- SFC 顺序、页面骨架、`useTable` / 表单 / 弹窗等模板数据链路未被擅自改造。
- 新增字段、接口、枚举、Options、权限、唯一标识、路由参数和导入路径均有依据。
- 未在组件内 Mock，未用 `any` / `Omix` / 默认值掩盖已确认的数据契约或类型问题。
- 项目组件 Props、默认值、工具函数和副作用已查源码或类型定义。
- 已按最终 diff 复查枚举分支、注释、兜底、发散范围、临时标记和 Element Plus namespace。
- 已执行本次修改文件的格式化入口检查、轻量技术验证和全局规范自检。
- 最终回复列出模板依据、项目专属事实来源、AI 业务推导项、其他发散点、兜底逻辑、待确认项和未执行验证。
