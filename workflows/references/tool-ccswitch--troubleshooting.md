# CC Switch：故障预防与分层排障

本引用只在 Codex 供应商已经生成但切换、启动、认证、请求或流式传输失败时读取。排障必须基于准确错误和配置事实，禁止轮流改 URL、Token、`requires_openai_auth` 或活动 TOML 猜答案。

## 1. 先保护当前任务的恢复通道

切换 CC Switch 供应商可能让当前 Codex 窗口无法回车、无法粘贴图片或停在登录 / 设置页面。实施前必须把以下恢复步骤完整告诉用户：

1. 在 CC Switch 切回已确认可用的官方 Codex 供应商。
2. 完全退出 Codex，包括仍在后台的 Codex 进程，再重新启动。
3. 重新进入原任务继续排障；原任务打不开时先在新任务报告错误和当前供应商。

不得要求用户“先切过去，失败后在这里回复”，却没有说明失败后如何切回。当前任务失去发送能力时，优先恢复通信，不继续要求在失效窗口中执行更多步骤。

## 2. 收集最小证据

每轮只读收集以下信息，所有秘密字段脱敏：

- CC Switch 版本、Codex 版本和操作系统。
- 目标 Codex provider ID、`meta.apiFormat`、上游 Base URL 的主机与路径形态、默认模型。
- 是否开启本地路由、是否接管 Codex、当前路由 Provider、请求计数是否增长。
- 活动 `config.toml` 中的 `model`、`model_provider`、当前 provider 表名、脱敏 Base URL、`wire_api`、`requires_openai_auth` 和是否存在 provider 级凭据。
- 启动日志中的第一个 `config_load` / Schema 错误，或请求日志中的准确 HTTP 状态、请求路径和错误文本。
- 失败发生在新任务普通请求、原任务续聊、模型切换、远程压缩、云任务还是长流式响应。
- 切回官方再切回后是否复发，手工编辑活动配置是否会被下一次切换覆盖。

禁止输出：完整 `auth.json`、完整 provider JSON、SQLite 整行、`experimental_bearer_token` 值、API Key、Cookie 或 OAuth Token。

## 3. 启动与 Schema 层

### 3.1 `config_load` 优先于登录和网络

Codex 打开后直接进入登录页、Windows 设置页、空白页，或者输入区无法使用时，先查启动日志的第一个 `config_load` 错误。配置在解析阶段失败时，请求尚未发出，继续换网络、Token 或寻找系统授权按钮都不会解决。

Windows 页面没有出现 UAC“是 / 否”弹窗时，不得假设用户漏点了确认。Codex 自己因配置错误跳转到设置或阻止进入，不等同于 Windows 权限拦截。

### 3.2 `max_concurrent_threads_per_session` 不能为 0

出现以下错误或同义 Schema 提示时：

```text
agents.max_concurrent_threads_per_session must be at least 1
```

按顺序处理：

1. 在活动 `config.toml` 中确认是否存在：

   ```toml
   [agents]
   max_concurrent_threads_per_session = 0
   ```

2. 不需要自定义并发时删除该字段；确实需要时设置为当前 Codex Schema 允许的正整数，禁止凭空选择性能数值。
3. 继续只读搜索 CC Switch 的目标 provider、通用配置、模板和备份来源，找到是谁持久化了该字段。
4. 通过 CC Switch 表单或其受支持配置入口修复源记录，再切换并重启验证。只改活动文件不是根治。

`enabled = false`、未选中某个功能或把 Skill / MCP 标为禁用，不会让 Codex 跳过整个 TOML 的 Schema 校验。无效字段即使位于当前不使用的块中，也可能阻止启动。

### 3.3 其他配置冲突

- Codex 可能校验所有 provider 表，不只校验当前活动表。空闲 provider 中的保留 ID、冲突认证字段或无效字段也可能让整个配置加载失败。
- 不通过删除用户其他配置块来“试试看”。先用准确错误定位表名和字段，再回到对应 CC Switch 源记录修复。
- 活动配置可解析后再进入协议和认证层；不得在 Schema 未通过时宣布网络或上游故障。

## 4. 协议与路由层

### 4.1 `/responses` 404

现象：Codex 请求上游 `/responses` 返回 404。

优先判断：真实上游不是 Responses，或者 Chat / Anthropic provider 没有被 CC Switch 路由接管。

检查顺序：

1. `meta.apiFormat` 是否真实反映上游：`openai_responses`、`openai_chat` 或 `anthropic`。
2. Chat / Anthropic provider 是否显示需要路由，路由总开关和 Codex 接管是否开启。
3. 活动 provider 的 Base URL 是否指向当前本地路由，而不是直接指向只支持 `/chat/completions` 或 `/v1/messages` 的上游。
4. 路由面板的当前 Provider 和请求计数是否命中目标 provider。

禁止通过给 Anthropic 地址末尾手工加 `/responses` 解决。协议不同，需要的是转换，不是路径拼接。

### 4.2 路由已命中但上游 404

- 检查 CC Switch provider 中保存的是服务根地址、`/v1` 根地址还是完整 URL。
- 上游文档给的是完整 `/v1/messages` 或 `/chat/completions` 时，按当前 CC Switch 的“完整 URL”能力配置；否则不要同时保留完整接口路径和自动拼接。
- 用路由日志确认实际转发路径，禁止在没有日志依据时轮流增删 `/v1`。

### 4.3 本地路由未启动或未接管

- 需要路由的 provider 在路由停止时不能直连替代。先恢复路由服务和 Codex 接管，再重试。
- 当前 Provider 一直是“等待首次请求”且计数不增长时，优先检查 Codex 活动 Base URL 和接管状态，不先排查上游。
- 路由端口是当前环境事实，不把默认端口写成永久结论。端口变化后以活动配置和监听状态为准。

## 5. 认证与 ChatGPT 账号路径

### 5.1 401 / 403

按以下顺序定位：

1. Key 是否属于当前目标 provider，是否被其他卡片的旧 Key 串入。
2. Responses / Chat 上游需要的认证方式是否与当前 provider 配置一致。
3. Anthropic 上游使用 `Authorization: Bearer` 还是 `x-api-key`；来源为 `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_API_KEY` 只能作为依据之一，最终按网关契约确认。
4. 当前 CC Switch 是否把第三方凭据写到 provider 级配置或由路由注入；Codex CLI 0.149 及以上不能继续依赖旧式“只把第三方 Key 放进 `auth.json`”的方案。
5. Key 是否有效、有权限、有余额；只做不会泄露凭据的最小请求验证。

不得把所有 401 都通过翻转 `requires_openai_auth` 处理。该字段、provider 自有凭据和保留官方登录是三个不同问题。

### 5.2 自定义模型报 ChatGPT 账号不支持

准确错误示例：

```text
The '<model>' model is not supported when using Codex with a ChatGPT account.
```

该错误首先证明“失败的这一次操作走了 ChatGPT 账号路径”，不直接证明上游自定义模型不存在，也不优先归因于网络、上下文窗口或 Responses 配置。

必须拆分验证：

1. 新任务中的普通短请求是否命中自定义 provider 并成功。
2. 失败操作是否是 Codex Desktop 远程压缩、云任务、远程恢复或其他依赖 ChatGPT 账号的能力。
3. 活动 provider 是否有自有凭据；普通请求是否仍意外回退到官方登录。
4. 切换模型时，任务是否保留了原 provider、推理档或远程操作上下文。

如果普通自定义请求成功、只有远程压缩或云任务失败，应把它记录为 ChatGPT 账号能力边界，而不是继续改 Sub2API Base URL。需要该远程能力时，使用官方支持的模型 / 账号完成，或新建自定义任务并通过人工摘要延续上下文；不得伪装成自定义 provider 已完全覆盖所有 Desktop 能力。

### 5.3 ChatGPT 额度与第三方请求

- 普通请求明确命中带自有凭据的第三方 provider 时，其上游计费和 ChatGPT Codex 额度是不同链路。
- Codex Desktop 的远程能力仍可能由 ChatGPT 账号执行，因此官方额度用尽时，第三方普通请求可以正常，而远程压缩 / 云任务仍失败。
- 判断依据必须是失败操作、路由命中和错误文本，不能只看模型选择器显示了自定义模型。

## 6. 流式连接层

准确错误示例：

```text
stream disconnected before completion ... os error 10054
```

这表示连接建立后，流在完成前被远端或中间网络重置。它与启动 Schema 错误、`/responses` 404 和普通 401 不同。

按链路拆分：

1. **Codex → 本地路由**：路由请求计数是否增长，是否收到完整请求，Codex 与本机端口之间是否被安全软件或代理干扰。
2. **本地路由 → 上游**：路由是否已收到上游状态码和首个流事件，随后在哪个时间点断开。
3. **上游生成**：短回答是否稳定、长回答是否固定在相似时长断开，供应商是否有流式超时或网关限制。
4. **外部网络**：代理、VPN、防火墙、路由器或中转链路是否重置长连接。一次成功不能证明长流稳定。

验证至少包含短请求和长流式请求。只有短请求成功时不能宣布网络重连问题根治。

以下现象要分开：

- `stop_reason=max_tokens` 或明确的输出上限停止：属于正常完成但被模型 / 网关上限截断，调整前先确认真实最大输出。
- 无完成事件并出现 10054 / EOF / disconnected：属于传输中断，不通过提高 `max_tokens` 解决。
- 路由没有看到请求：问题在 Codex 到本地路由之前。
- 路由看到上游开始返回后中断：问题在本地路由到上游、外部网络或上游。

## 7. 切换持久化层

现象：手工编辑活动 `config.toml` 后可以进入 Codex，但在 CC Switch 再切一次 Sub2API 就复发。

根因方向：修复只落在生成产物，CC Switch provider、通用配置、模板或备份仍保存错误值。

正确处理：

1. 对比切换前后活动配置的脱敏差异，定位被重新注入的字段。
2. 只读定位该字段来自目标 provider、通用配置还是其他 provider 表。
3. 通过 CC Switch 支持的编辑入口修复持久化来源。
4. 完全重启 Codex，执行“目标 → 官方 → 目标”的二次切换验证。

禁止启动后台监控脚本持续覆盖活动配置。该方案会与 CC Switch 写入竞争、掩盖源数据问题，并在版本升级或进程时序变化后再次失效。

## 8. 当前任务与新任务分层

- 新任务短请求失败：优先视为基础 provider、协议、认证或路由问题。
- 新任务成功、原任务失败：检查原任务记录的模型 / provider、推理档、上下文长度和远程压缩路径。
- 模型选择器能看到条目不等于该模型的所有能力配置正确；仍须真实请求验证。
- 当前任务在切换后不能回车或粘贴，先恢复官方 provider 和重启；不要把输入框失效单独当成剪贴板 Bug。
- 同一任务跨模型切换失败时，先使用两边都支持的推理档并检查上下文；仍失败则在新任务验证，禁止为了保住旧任务改坏全局 provider 配置。

## 9. 症状决策表

| 症状 | 首要层级 | 第一动作 |
| --- | --- | --- |
| 打开即设置 / 登录页，无法输入 | 启动 Schema | 查第一个 `config_load` 错误 |
| 提示并发必须至少为 1 | 配置生成 | 修 CC Switch 持久化来源中的 `0` |
| `/responses` 404 | 协议 / 路由 | 核对 `meta.apiFormat` 和 Codex 接管 |
| 路由命中后上游 404 | 上游路径 | 核对根地址与完整 URL 模式 |
| 401 / 403 | 凭据 / 认证头 | 核对 provider Key 与请求头类型 |
| 自定义模型提示 ChatGPT 账号不支持 | 账号操作路径 | 区分普通请求与远程压缩 / 云任务 |
| `stream disconnected ... 10054` | 流式网络 | 用路由日志切分本地链路和上游链路 |
| 手工修好，切换后复发 | 持久化源配置 | 修 provider / 通用配置，不只改活动 TOML |
| 新任务成功，原任务失败 | 任务状态 | 检查旧任务绑定和远程能力 |

## 10. 排障完成门禁

只有满足以下条件才可写“已解决”：

- 第一个失败层级已被准确定位，后续层级没有被越级猜测。
- 修复发生在 CC Switch 持久化源配置或真实外部原因处，不依赖后台覆盖活动文件。
- 目标 provider 完全重启后新任务可用，且官方往返切换后仍可用。
- ChatGPT 账号能力、普通第三方请求和 Desktop 远程能力分别给出验证结论。
- 短请求和长流式请求分别验证；输出上限停止与网络中断没有混为一谈。
- 用户不查看日志或 diff，也能知道根因、修复位置、剩余限制和恢复步骤。
