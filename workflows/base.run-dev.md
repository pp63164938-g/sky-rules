# 本地跑通验证

仅在用户显式调用 `base-run-dev`，或明确要求把本地项目跑起来做验证时使用。只询问启动命令、不要求实际跑通的普通问答，不进入本工作流。

## 0. 核心原则

- 目标是服务到达可验证状态，不是只给出操作步骤。
- 能在本机查到的日志、端口、依赖和进程，直接查，不把操作甩回给用户。
- 缺类、端口冲突、命令行过长、模块反射限制，属于可处理的启动问题，继续处理。
- 缺少登录账号、密钥、生产权限，或存在多个会改变验证结果的业务决策时，才停下来问。
- 依赖包不是服务。接口包、公共 SDK 只需要安装或挂到 classpath，不单独启动。
- 两个服务默认端口相同，必须错开端口后再同时启动。端口以当前项目配置为准，禁止沿用其他项目的端口。
- 禁止为了掩盖启动失败去改业务代码、加空 catch 或删除调用。

## 1. 启动前确认

1. 用 `git status` 确认本次改了哪些仓库。
2. 按调用链区分：前端、要启动的服务、只提供类的依赖包。
3. 从项目配置确认启动类、默认端口、JDK、依赖版本。禁止凭经验写死端口。
4. 动手前告诉用户：本次启动哪些、不启动哪些、为什么。
5. 用户已确认多版本本地联调时，先读 `references/base-run-dev--multi-version.md`。普通启动不读取。

## 2. 失败处理顺序

1. 先拿完整失败原因：`APPLICATION FAILED`、第一段 `Caused by`、退出码。关闭日志不是失败原因。
2. 查端口占用、实际 JDK、实际 classpath 和依赖 jar 里是否真有缺失的类。
3. 一次只处理当前这一层失败。上一层过了再看下一层。
4. 本地未安装的新类，优先在依赖仓库安装到本地仓库；jar 被 IDE 锁住时，才使用标明 `local` 的临时 jar，并说明它不是项目配置。
5. 同一模块只留一个 IDE 编译和启动，避免编译产物互相覆盖。
6. 连续两次修复没有改变失败签名时，停止猜，改查日志、classpath 和进程锁。
7. 开始排障前先读 `references/base-run-dev--lessons.md`。只复用前提仍成立的条目。

## 3. 本地运行产物不提交

只为本次启动或本地联调产生的文件、配置和临时代码，默认不执行 `git add`、`commit`、`push`。即使用户随后要求提交全部变更，也先排除这些内容：

- IDE 启动配置里为本次启动追加的 classpath、VM 参数、端口和缩短命令行。
- 临时 jar、补丁 jar、编译 classpath 文件、运行日志。
- 只为绕过本机文件锁、命令行过长、JDK 模块限制而改的配置。
- 只为本次多版本联调追加的环境变量、版本参数和浏览器本地存储。

业务源码和本来就要提交的依赖版本变更，不是本地运行产物。

已被 Git 跟踪的文件如果只为本次启动或联调改过，跑通后恢复原内容，除非用户明确要求保留。

交付和后续提交时都必须单独列出「本地运行 / 联调变更」：写明文件、用途，以及是已恢复、保留在工作区，还是按用户要求纳入提交。没有此类变更时写「无」。禁止跳过后不告诉用户。

## 4. 跑通后回写经验

只有已经验证、而且换个项目还可能再遇到的启动问题，才回写。

1. 回写走 `base-update-rules`，只改 `references/base-run-dev--lessons.md`。
2. 先给出经验预览：信号、处理、失效条件。用户确认后才写入并同步。
3. 不写真实仓库名、类名、本机路径和这次的现场端口。
4. 一次性环境问题、尚未确认根因的处理，不回写。

## 5. 验证交付

- 每个要启动的服务，必须看到启动成功日志，并确认端口在听。
- 验证用临时拉起的进程，验证完要停掉，避免占用用户接下来的启动。
- 交付时说明：改了哪些启动条件、哪些是临时 jar 或 IDE 配置、下次同类项目先查什么。
- 本次走了多版本本地联调时，同时说明版本标识、后端环境变量和前端入口是否一致。
