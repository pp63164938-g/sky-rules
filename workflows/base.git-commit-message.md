# Git Commit Message Workflow (git-commit-plugin style)

该工作流旨在自动化 Git 提交过程，严格遵循 `git-commit-plugin` 的提交规范（Emoji + Type + Scope + Subject）。

## 1. 确定变更范围

**核心原则**：`git commit` 只提交暂存区（staged）内容，因此 commit message **必须且仅基于已暂存的变更**生成。

**优先级顺序**（优先基于实际代码差异）：

1. **已暂存变更（Staged Changes）**（最准确，默认优先）：
    - 执行 `git diff --cached --name-only` 查看暂存文件列表，用 `git diff --cached` 查看内容。
    - **如果存在暂存文件**，则【严格且仅分析】已暂存的变更生成 message，忽略其他未暂存文件。
2. **未暂存变更（Unstaged Changes）**（智能回退方案）：
    - 如果步骤 1 发现暂存区为空（没有任何已 staging 的文件），则**必须**扩大视野，使用 `git status -s` 与 `git diff` 读取当前工作区的所有**未暂存/新添加**的修改，并结合我们当次会话的上下文去生成真实的全局 Commit Message。
3. **用户主动说明 / 纯对话推断**（备选）：用户手动指定，或完全无法使用 Git 命令时。

**未暂存提醒机制**：
- 如果使用了步骤 1（只针对暂存区），但在 `git status` 发现仍有其他文件未暂存，请在末尾提示："发现部分文件存在变更但未暂存，本次生成的 Message 仅包含你已经 `git add` 的部分。"
- 如果使用了步骤 2（全量读取了未暂存文件计算 message），请在末尾**强烈提醒**："检测到当前暂存区为空，上述 Message 是基于工作区全部的未提交修改生成的。**请务必在提交前执行 `git add .`（或具体文件）将其暂存！**"

**重要**：

- **允许**执行 `git status`、`git diff` 等只读命令获取变更信息
- **禁止**执行 `git add`、`git commit`、`git push` 等写操作
- **禁止**将 commit message 写入文件，直接在对话中输出
- **防止 Diff 截断机制（强制临时文件读取）**：直接在终端执行 `git diff` 如果遇到长内容极易被终端工具自动截断，从而引发 AI 分析不全或被迫依靠上下文脑补。因此，**针对长差异，严禁直接在终端查看 diff 输出**。必须执行 `git diff --cached > $env:TEMP\git_diff.txt` 将完整日志导出，然后运用文件读取工具（如 `view_file` 或 `Get-Content` 分页）精确查阅，生成完毕后务必执行 `Remove-Item $env:TEMP\git_diff.txt -ErrorAction SilentlyContinue` 销毁。
- **严禁根据聊天上下文推断**：即使执行的 diff 命令被意外截断，也**绝不允许**依靠短时记忆或聊天上下午去“脑补” commit message。遇见截断必须立刻走上述的临时文件法重新获取完整差异！聊天记录永远不能作为 diff 的合法依据。

### 1.1 版本号提取

通过 `git branch --show-current` 获取当前分支名，从中提取版本号，追加到 subject 末尾。

**提取规则**：

| 分支名格式                | 提取结果     | 示例                                    |
| :------------------------ | :----------- | :-------------------------------------- |
| `feature/v4.568.1`        | `v4.568.1`   | 匹配 `v` 开头的版本号                   |
| `hotfix/v4.567.0`         | `v4.567.0`   | 同上                                    |
| `release/4.568.1`         | `v4.568.1`   | 无 `v` 前缀时自动补 `v`                 |
| `main` / `develop` 等     | 不追加       | 非版本分支不追加版本号                   |

**提取方式**：从分支名中匹配 `v?\d+\.\d+(\.\d+)?` 模式的版本号。若分支名无版本号则不追加。

## 2. 分析更改并生成提交信息

根据步骤 1 确定的变更范围，确定提交类型（Type）、范围（Scope）、主题（Subject）和详细描述（Body）。

### 2.1 提交类型 (Type) 与 Emoji 映射

严格使用以下映射关系：

| Type         | Emoji | 描述                                             |
| :----------- | :---- | :----------------------------------------------- |
| **init**     | 🎉    | 项目初始化                                       |
| **feat**     | ✨    | 添加新特性                                       |
| **fix**      | 🐛    | 修复bug                                          |
| **docs**     | 📄    | 仅仅修改文档                                     |
| **style**    | 🌈    | 仅仅修改了空格、格式缩进、逗号等，不改变代码逻辑 |
| **refactor** | 🦄    | 代码重构，没有加新功能或者修复bug                |
| **perf**     | 🎈    | 优化相关，比如提升性能、体验                     |
| **test**     | 🧪    | 增加测试用例                                     |
| **build**    | 📦    | 依赖相关的内容                                   |
| **ci**       | 👷    | CI配置相关                                       |
| **chore**    | 🔧    | 构建过程或辅助工具的变动                         |
| **revert**   | ⏪    | 回滚到上一个版本                                 |

### 2.1.1 fix 类型使用限制

**核心原则**：默认不要把提交类型判断为 `🐛 fix`。只有当用户明确说明这是“修复 bug / 修复问题 / fix”时，才允许使用 `fix`；不能因为改动看起来像纠正问题，就自行推断为修复。

**判断标准**：

- 用户没有明确说“修复”时，优先根据实际改动选择 `feat`、`refactor`、`docs`、`style`、`chore` 等类型。
- 联调、配置补充、字段替换、交互限制、页面调整等，一般不使用 `fix`，除非用户明确说明它是在修复某个 bug。
- 即使改动内容包含“避免异常”“限制错误操作”“调整不合理行为”，也不能自动归类为 `fix`，需要看用户是否明确定位为修复。

**反面案例**：

```text
🐛 fix(运营中心 - 广告管理): 修复广告图编辑逻辑
```

问题：用户没有明确说明这是 bug 修复，只是做配置补充或交互调整时，不应使用 `fix`。

**推荐写法**：

```text
✨ feat(运营中心 - 广告管理): 联调广告图跳转配置
```

**特殊业务场景 Type 选择指南**：

- **前后端联调 / 替换 TODO 占位符**：
  - 若为**首次**接入真实接口、替换静态/TODO占位字段（即完成某个业务的数据对接），应使用 `✨ feat`（视为完成了此特性开发）。
  - 只有当用户明确说明本次变更是修复 bug / 修复问题，或提交诉求中直接包含 `fix` 语义时，才使用 `🐛 fix`；其他联调、配置、字段、交互调整默认不使用 `fix`。
  - **提示**：在 Commit Message 的 Subject 中，对于联调相关的提交，可直接使用“联调：xxx接口/字段”作为描述，更加清晰准确。

### 2.2 范围 (Scope)

- **中文优先**：Scope 描述使用中文，从业务模块到具体功能逐级细化
- **层级用 `-` 分隔**：体现模块归属关系，层级不超过 3 级
- **必须包含业务含义**：不能只写文件名或技术术语

**Scope 层级规则**：

| 变更范围      | Scope 格式                    | 示例                             |
| :------------ | :---------------------------- | :------------------------------- |
| 单一页面/组件 | `模块 - 功能 - 页面`          | `流程审批 - 语音IP共享 - 详情页` |
| 同模块多文件  | `模块 - 功能`                 | `流程审批 - 语音IP共享`          |
| 跨模块多文件  | `多模块` 并在 body 中分组说明 | `多模块`                         |
| 公共组件/工具 | `公共组件 - 具体组件`         | `公共组件 - 表格分页`            |
| 配置/构建     | `配置` 或 `构建`              | `配置 - 环境切换`                |

**路径到 Scope 的映射参考**：

| 文件路径模式               | Scope                 |
| :------------------------- | :-------------------- |
| `views/srm/`               | `SRM - 设备采购`      |
| `views/csc/`               | `客服中心`            |
| `views/oc/`                | `运营中心`            |
| `components/ger/process/`  | `流程审批`            |
| `components/oc/marketing/` | `运营中心 - 营销活动` |
| `components/common/`       | `公共组件`            |
| `config/`                  | `配置`                |
| `api/`                     | `API接口`             |
| `hooks/`                   | `Hooks`               |

### 2.3 主题 (Subject)

- **简短描述**：概括本次变更的核心内容
- **中文描述**：不以句号结尾
- **不超过 30 字**

### 2.4 详细描述 (Body)

- **列出具体改动点**：使用有序列表
- **每条说明实际改了什么**：而非泛泛描述
- **按文件或功能分组**：让阅读者快速理解变更范围

### 2.5 提交信息格式

```text
<emoji> <type>(<scope>): <subject> [<version>]

<body>
```

- `[<version>]`：从步骤 1.1 提取的版本号，放在 subject 末尾，用空格分隔
- 若无版本号则省略 `[<version>]` 部分

**示例**：

```text
🦄 refactor(客服中心 - ROI分析报表): R展会活动与R渠道推广ROI页面Tab布局改造 [v4.568.1]

1. 新增 index-tab.vue 容器，实现 Tab 页签切换结构
2. 改造 consumption-detail/conversion-detail 及列表页组件，适配 Tab 子页面布局
3. 更新路由配置，将页面入口指向新的 index-tab.vue
```

```text
✨ feat(流程审批 - 语音IP共享 - 详情页): 证明文件换行展示及共享失败原因红色标注 [v4.567.0]

1. 证明文件区域图片与附件改为纵向换行展示，自适应高度
2. 共享失败原因label通过插槽渲染为红色文字
```

## 3. 输出 commit message

**直接在对话中输出** commit message 代码块，用户自行复制使用。

**格式要求**：

- **强制要求**：整个 commit message 必须被独立的 Markdown 代码块（如 ```text ... ```）完全包裹，以便唤起用户界面的“一键复制”按钮体验。绝对禁止仅仅使用粗体、列表或纯文本等易混淆的排版方式输出。
- 不写入文件、不执行 git commit、不执行 git push

**注意：**

- 此工作流**不**执行任何 git 命令，仅生成 commit message 文本
- 用户自行完成 `git add`、`git commit`、`git push`
## 4. 明确提交/推送场景

默认情况下，本工作流只生成 commit message，不执行 `git add`、`git commit`、`git push`。

但当用户明确要求“提交”、“提交推送”、“commit”、“push”，且目标仓库已明确时，允许在完成 diff 核对后执行对应 git 写操作。

### sky-rules 特例

当用户要求对 `sky-rules` 提交推送时：

- 工作目录必须切换到 `D:/self/Ai/sky-rules`
- commit message 仍必须严格遵循本工作流的 `Emoji + Type + Scope + Subject` 格式
- 只允许暂存 `rules/`、`workflows/`、`skills/`、同步脚本等与规则仓库相关的变更
- 提交前必须输出将要提交的文件列表
- 推送前必须确认当前分支与远端状态
- 推送完成后必须输出 commit hash、分支和远端推送结果
